vCluster provisions <GlossaryTerm term="tenant-cluster">clusters</GlossaryTerm> on your infrastructure or directly on bare metal. Two choices shape your deployment architecture: where the control plane runs, and how worker nodes are deployed. Together, these determine the isolation level each tenant receives.

Every cluster is built on a certified Kubernetes distribution. This is true whether it's delivered to tenants as managed Kubernetes directly or as the foundation for a Slurm, Ray, or inference cluster running on top. This page covers that shared control plane and worker-node architecture.

## Control plane

Every cluster runs a dedicated <GlossaryTerm term="control-plane">control plane</GlossaryTerm>. The control plane manages all operations within the cluster and is completely invisible to tenants. It contains:

- A **Kubernetes API server**, the management interface for all API requests within the cluster.
- A **controller manager**, which maintains the state of Kubernetes resources like pods, ensuring they match the desired configuration.
- A **data store**, which stores all API resources. By default, an embedded SQLite database is used, but you can [choose other data stores](../configure/control-plane/components/backing-store/overview.mdx) like <GlossaryTerm term="etcd">etcd</GlossaryTerm>, MySQL, and PostgreSQL.
- A **syncer**, which synchronizes resources between the cluster and the underlying infrastructure.
- A **scheduler**, an optional component for scheduling workloads. By default, vCluster reuses the control plane cluster's scheduler to reduce resource usage. You can [enable the virtual scheduler](../configure/control-plane/advanced/virtual-scheduler.mdx) when you need node labels, taints, drain operations, or custom scheduling behavior.

All of these components run together in a single container within the control plane pod. The API server, controller manager, data store, and syncer are one unified process. CoreDNS deploys as a separate pod in the same namespace. If you opt into deployed etcd, it runs as its own StatefulSet. On the control plane cluster, `kubectl get pods -n <vcluster-namespace>` shows something like:

```
NAME                                 READY   STATUS    AGE
vcluster-0                           1/1     Running   5m
vcluster-coredns-6b9f8d6f6b-xk2p9    1/1     Running   5m
```

Where that control plane runs is your first architectural choice.

### On an existing Kubernetes cluster

<TenancySupport hostNodes="true" />

The default deployment mode. The cluster control plane runs as a pod on a <GlossaryTerm term="control-plane-cluster">control plane cluster</GlossaryTerm> you operate. vCluster deploys the control plane as a StatefulSet (default) or Deployment inside a dedicated namespace on that cluster.

  <ControlPlanesAsPods style={{width: '100%', maxWidth: '600px', height: 'auto', display: 'block', margin: '0 auto'}} role="img" aria-label="Multiple cluster control planes running as pods on a control plane cluster, each connected to external worker nodes" />
  <figcaption>Cluster control planes as pods on a control plane cluster</figcaption>
</figure>

Each cluster runs inside its own namespace on the control plane cluster. A namespace contains exactly one cluster. Nesting clusters inside one another is also supported.

All resources synchronized to the control plane cluster namespace carry owner references back to the cluster. Deleting the cluster, or its namespace, removes all associated resources automatically. No orphaned resources remain.

### vCluster Standalone
<!-- vale on -->

vCluster Standalone is a complete, zero-dependency Kubernetes distribution. It runs as a self-contained binary on bare metal or VMs, with no dependency on any other Kubernetes distribution. Once deployed, it behaves like any other Kubernetes cluster. You can install vCluster Platform on top of it, deploy clusters, and join additional nodes, exactly as you would with any other cluster.

For AI cloud providers standing up infrastructure from scratch, Standalone solves the "cluster one" problem. You can bootstrap your entire platform using only vCluster tooling, with no external dependencies.

### vind (vCluster in Docker)
<!-- vale on -->

vind runs a complete cluster entirely in Docker containers, with no Kubernetes dependency. The control plane and worker nodes run as containers on a single Docker host. vind always uses private nodes. Its worker nodes are Docker containers provisioned automatically.

vind is suited for local development and CI/CD pipelines. It also supports hybrid deployments: external cloud nodes can join a vind cluster through a VPN, combining a local control plane with remote compute.

Key capabilities that distinguish vind from KinD:

- **Sleep and wake:** pause a cluster to free resources and resume it instantly, without deleting and recreating it.
- **Load balancers out of the box:** Services of type `LoadBalancer` work automatically with no extra setup.
- **Pull-through image cache:** vind uses the host Docker daemon's image cache directly, so there is no need to run `kind load docker-image` before tests.
- **External nodes:** cloud instances can join a vind cluster through a VPN for hybrid development scenarios.

| Feature | vind | KinD |
|---|---|---|
| Sleep and wake | Yes | No, must delete and recreate |
| Load balancers | Automatic | Manual setup required |
| Image caching | Pull-through Docker daemon | Direct registry pulls |
| External nodes | Yes, using VPN | Local only |
| CNI/CSI choice | Yes | Limited |

## Worker nodes

Your second architectural choice is how worker nodes are deployed. This determines compute isolation between tenants. For a customer-facing or otherwise production offering, work through [Choose a worker node model](/docs/plan/choose-worker-node-model) before deciding.

### Private nodes

Each cluster runs on dedicated nodes that join exclusively through a token-based process. Each cluster gets its own worker nodes, CNI, and CSI. Segment external networks and shared storage backends separately.

From the tenant's perspective, the environment is indistinguishable from a single-tenant Kubernetes cluster.

Nodes can come from any Linux infrastructure: bare metal servers, cloud VMs, or any manually joined Linux machine. With [Auto Nodes](../deploy/worker-nodes/private-nodes/auto-nodes/overview.mdx), vCluster Platform can provision and deprovision nodes automatically.

This model suits GPU tenants, regulated workloads, and any environment where full infrastructure separation is required.

### Shared nodes

Tenant workloads run on the same cluster that hosts the control planes, sharing the existing node pool. Multiple clusters run side by side on the same physical nodes. A <GlossaryTerm term="syncer">syncer</GlossaryTerm> component translates workload resources from each cluster into a dedicated namespace on the control plane cluster. Each tenant sees only their own namespaces, pods, and services. The translated copies are invisible to them.

<img
  src={require('@site/static/media/diagrams/shared-nodes.png').default}
  alt="Architecture for Shared Nodes"
  style={{maxWidth: '600px', display: 'block', margin: '0 auto'}}
 />

</figure>

This model suits trusted tenants such as development environments, CI/CD pipelines, testing, and internal platforms. Tenants share the same kernel and worker nodes. So shared nodes aren't a security boundary for untrusted tenants with cluster or scheduler access or arbitrary workload execution. Use private nodes for external, resale, regulated, or otherwise untrusted tenants who get that access. A provider-operated offering where you own all workloads, such as a SaaS product or inference API, can still use shared nodes. If you choose shared nodes for a trusted-tenant or provider-operated use case, follow the [shared-node hardening guide](../deploy/security/shared-nodes-hardening.mdx) to configure the baseline. See [Choose a worker node model](/docs/plan/choose-worker-node-model) if you haven't made this decision yet.

For tenants that need predictable per-tenant compute without full Private Nodes, you can scope workloads to a labeled node pool using [Dedicated Nodes](../deploy/worker-nodes/host-nodes/isolated-workloads.mdx). Node selectors enforce placement on a reserved subset of the control plane cluster's nodes without provisioning separate infrastructure. A dedicated node pool is still the shared-node architecture. Tenants on that pool still share a kernel and worker nodes with each other. It scopes placement, not isolation, and doesn't provide private-node isolation guarantees.

### Worker node comparison

| Feature | Private Nodes | Shared Nodes | vind (Docker) |
|---|---|---|---|
| Isolated control plane | Yes | Yes | Yes |
| Suitable for untrusted or external tenants | Yes | No | No |
| Custom CNI | Yes | No | Yes |
| Custom CSI drivers | Yes | No | Limited |
| Isolated network | Yes | No | Yes |
| Reuse control plane cluster controllers | No | Yes | No |
| Tenant workloads visible on control plane cluster | No | Yes | No |
| Automatic node provisioning | Yes | No | Yes |
| Requires control plane cluster | Yes | Yes | No |
| Suitable for local development | No | Limited | Yes |
| Suitable for CI/CD | Limited | Yes | Yes |
| Infrastructure overhead | High | Low | Low |

See [Choose a worker node model](/docs/plan/choose-worker-node-model) for the customer-access questions that decide which column applies to your offering.

## Virtual Nodes

Virtual Nodes add a strong isolation boundary between tenant workloads at the node level. Using [vNode](https://www.vnode.com/docs/) to virtualize node boundaries, each cluster gets its own view of the node environment. vNode enforces taints, tolerations, and scheduling boundaries per tenant.

Virtual Nodes are not a separate deployment choice. They are an isolation layer that applies to shared nodes, private nodes, and Standalone alike. This makes them particularly valuable for GPU workloads where strict per-tenant separation is required regardless of how the underlying nodes are deployed.

## Syncer

<figure>
<img
  src={require('@site/static/media/rebranding/vcluster-architecture.png').default}
  alt="Syncer Architecture"
 />
  <figcaption>vCluster Architecture for the syncer</figcaption>
</figure>

The syncer links the cluster to the control plane cluster. It keeps the two environments consistent so tenants see a complete, functional Kubernetes cluster without direct access to the control plane cluster. Its role depends on how worker nodes are deployed.

**With private nodes**, only control plane state is synchronized. The syncer coordinates the cluster's API server with the underlying infrastructure. From an operator's perspective this is nearly transparent. Workloads run directly on dedicated nodes with no sync overhead.

**With shared nodes**, the syncer also translates workload resources between the cluster and the control plane cluster. By default this includes Pods, ConfigMaps, Secrets, Services, and PersistentVolumeClaims, and you can also sync resources such as Ingresses and Gateway API objects. Each resource type has specific sync behavior. Networking resources in particular require careful configuration. If you are deploying with shared nodes, read the [full sync documentation](../configure/sync/overview.mdx) to understand what is synced and how to configure it for your workloads.
