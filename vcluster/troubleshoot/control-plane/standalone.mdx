Bringing up a Kubernetes cluster can face challenges, so here are some troubleshooting tips to help get you started. 

## Check vCluster logs

All vCluster logs are located in the control plane, view service logs using journalctl.

```bash title="View vCluster service logs"
journalctl -u vcluster.service --since="2 minutes ago" -f
```

## Common Issues

### Network connectivity

Clients and worker nodes access the cluster API through the vCluster proxy on port 8443, not on port 6443. The Kubernetes API server only listens on `127.0.0.1:6443`, so opening port 6443 isn't necessary.

If `kubectl` or a node join can't connect, confirm that port 8443 on the control plane node is open to your workstation and all worker nodes. To check the listening addresses on the control plane node, run:

```bash title="Check the API listeners"
sudo ss -tlnp | grep -E ':(6443|8443)\b'
```

In the output, expect `0.0.0.0:8443` or `*:8443` for the vCluster proxy and `127.0.0.1:6443` for the API server. For the full list of ports, see [Required ports](../../deploy/control-plane/binary/node-requirements.mdx#required-ports).

### Check the systemd service

The vCluster service needs to be running at all times.

```bash title="Verify the vCluster service is running"
systemctl status vcluster.service
```

### Node join failures

Check that join tokens haven't expired and network connectivity exists between nodes.

When running the join node script, if a 400 status code is received, check the URL directly to see if an error message exists. Alternatively you can pipe the entire response to the terminal and print it:

```bash title="Print node join response"
curl -sSLk "https://<endpoint>/node/join?token=<token>" | { response=$(cat); echo "$response" | sh - 2>/dev/null || echo "Error: $response"; }
```

### Resource constraints

Ensure adequate CPU, memory, and disk space on nodes.
