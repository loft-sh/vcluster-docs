The `vcluster.yaml` file is the central configuration source for a cluster. It controls the control plane architecture, worker node pool, resource sync rules, networking, and access settings. Some choices, such as the worker node type and backing store, must be made at deployment time and can't be changed later.

The file is optional. If you don't provide one, the cluster runs on shared nodes (the control plane cluster's node pool) with all resources syncing to a single namespace. Shared nodes are the vCluster OSS default and the only worker node model OSS provides. They suit internal, trusted tenants. For externally facing, resold, or regulated tenant offerings, [configure private nodes](../deploy/worker-nodes/private-nodes/overview.mdx), which require a vCluster license. Most production deployments benefit from explicit configuration.

:::tip New to vCluster?
If you haven't chosen a deployment path yet, start with [What is vCluster?](../overview/what-is-vcluster.mdx) or the [architecture overview](../overview/architecture.mdx) before configuring `vcluster.yaml`.
:::

## Configuration structure for vcluster.yaml 

The `vcluster.yaml` file organizes configuration into logical sections. Each section controls a specific aspect of cluster behavior.

### Control plane settings

The control plane section defines how vCluster runs its Kubernetes API server, controller manager, and data storage. 

Key configuration areas include:

- **Deployment settings**: 
  - **Run as a container** - Configure how the control plane pods deploy, including resource limits, node selectors, and affinity rules.
  - **Run as a binary on a node** - Configure if you want the control plane to be deployed as a binary. Note: Worker node pool can only be private nodes. 
- **Backing store selection**: Choose between different storage backends for the vCluster control plane's [backing store](control-plane/components/backing-store/overview.mdx). Options include embedded databases, managed etcd or external databases.
- **Networking options**: Define how external traffic reaches the cluster's API server, including ingress configuration and service exposure methods.

### Worker node pool settings

You can configure which type of worker nodes to use for the cluster.

- **Shared nodes**: Use all or a labeled subset of the underlying cluster's worker nodes.
- **Private nodes**: Dedicated nodes that join exclusively through a token-based process. Nodes can be manually provisioned or automatically managed by vCluster Platform.

### Access configuration

You can configure access settings to control how users and applications connect to the cluster:

- **The kubeconfig file**: Configure how vCluster generates and stores [the kubeconfig file](access/export-kube-config.mdx) that clients use to connect. This file contains API server endpoints, authentication credentials, and cluster context. You specify the Kubernetes secret name for storage, the context name for identification, and the server URL for connection.
- **Authentication methods**: vCluster supports certificate-based and service account token authentication for secure access to the cluster. When exposing vCluster through an ingress or load balancer, you can use service account tokens if client certificate validation is not supported. Authentication methods can be customized to fit your access requirements.

### Resource sync rules

<TenancySupport hostNodes="true" />

When using shared nodes, the cluster shares certain resources with the underlying cluster to function properly. The sync configuration controls this in both directions:

- **From underlying cluster to tenant**: Configure which resources from the underlying cluster appear inside the cluster through [host-to-virtual synchronization](sync/from-host/overview.mdx). Common examples include nodes, storage classes, and priority classes.
- **From tenant to underlying cluster**: Define which cluster resources sync to the underlying cluster through [virtual-to-host synchronization](sync/to-host/overview.mdx). This typically includes pods, services, and persistent volume claims.

## Example vcluster.yaml configuration

The following examples demonstrates common configurations and explains each section's purpose:

Each configuration section has a specific purpose in the cluster setup:

- **Control plane with embedded storage**: The configuration uses [embedded etcd](control-plane/components/backing-store/etcd/embedded.mdx) as the data store for the cluster's control plane. This approach reduces operational complexity because etcd runs inside the vCluster pod rather than requiring a separate database.
- **API server exposure**: An [Ingress](control-plane/deployment/ingress.mdx) resource exposes the cluster's API server through a hostname. This allows external tools and users to access the cluster without port-forwarding or `NodePort` services.
- **ServiceAccount synchronization**: The configuration enables [`ServiceAccount`](sync/to-host/advanced/service-accounts.mdx) syncing from the cluster to the control plane cluster. This synchronization supports workloads that need specific permissions on the control plane cluster, such as operators or controllers that manage control plane cluster resources.
- **Real node synchronization**: Instead of using vCluster's default "pseudo" nodes, this configuration syncs real [node](sync/from-host/nodes.mdx) information from the control plane cluster. The `clearImageStatus` option removes image information from synced nodes to reduce data transfer and storage requirements.
- **Kubeconfig access**: The configuration defines how vCluster exports the [kubeconfig](access/export-kube-config.mdx) for accessing the cluster. The exported kubeconfig gets stored in a Kubernetes secret, making it available for CI/CD pipelines, ArgoCD apps, or Terraform configurations.

### Control plane as a container and shared nodes

<TenancySupport hostNodes="true" />

```yaml title="vcluster.yaml"
# Control plane configuration
controlPlane:
  # Configure the backing store for vCluster's data
  backingStore: # Enterprise feature - requires license
    etcd:
      embedded: 
        enabled: true  # Run etcd inside the vCluster pod
  
  # Expose the API server via ingress
  ingress:
    enabled: true
    host: vcluster-k8s-api.example.com  # Your API server hostname

# Resource synchronization settings when using the control plane cluster's worker nodes
sync:
  # Resources that sync from cluster to host
  toHost:
    serviceAccounts:
      enabled: true  # Sync ServiceAccounts for operators/controllers
  
  # Resources that sync from host to cluster
  fromHost:
    nodes:
      enabled: true  # Sync real nodes instead of fake nodes
      clearImageStatus: true  # Remove image data to save resources

# Kubeconfig export configuration
exportKubeConfig:
  context: my-vcluster-context  # Name in the kubeconfig file
  server: https://vcluster-k8s-api.example.com  # API server URL
  additionalSecrets:
  - name: my-vcluster-kubeconfig  # Secret name for storing kubeconfig
```

## Frequently asked questions

<details>
<summary><strong>Is a <code>vcluster.yaml</code> file required?</strong></summary>

The `vcluster.yaml` file is optional. If not provided, vCluster applies default settings that:

- Use an embedded database (SQLite).
- Sync essential resources such as pods and services.  
- Configure networking with basic `ClusterIP` services.  
- Enable default authentication and access controls.  

:::note
The `vcluster.yaml` configuration defaults are for development and simple test scenarios. For production use, defining a `vcluster.yaml` file is strongly recommended to meet specific security, performance, and integration needs.
:::
</details>

<details>
<summary><strong>Can an existing cluster be updated using <code>vcluster.yaml</code>?</strong></summary>

Yes. You can update an existing cluster by applying a modified `vcluster.yaml` file. This allows you to change the configuration without deleting or recreating the cluster.

To apply changes, use the `--upgrade` flag with the [`vcluster create`](../cli/vcluster_create.md) command:

```bash
vcluster create VCLUSTER_NAME --upgrade -f vcluster.yaml
````

The command performs the following actions:

1. Reads the updated `vcluster.yaml` file.
2. Compares it to the current configuration of the cluster.
3. Applies only the differences between the new and existing configuration.
4. Triggers a rolling update if required to apply the changes.

Some configuration changes, such as updates to sync settings, take effect immediately. Others, such as control plane modifications, may require pod restarts. The vCluster CLI handles these updates automatically and ensures minimal disruption to workloads.

For more details on updating clusters, see the [deployment changes documentation](../operate/deploy-changes.mdx).

</details>
