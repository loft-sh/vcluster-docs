vCluster produces three distinct types of logs. Each type has a different source, a different audience, and different tooling requirements.

| Type | Source | Typical access |
|------|--------|----------------|
| [Control plane logs](#control-plane-logs) | vCluster pod `stdout`, or the `vcluster` systemd service on vCluster Standalone | `kubectl logs` or `journalctl` |
| [Audit logs](#audit-logs) | Cluster API server | `kubectl logs` or file |
| [Workload logs](#workload-logs) | Apps inside the cluster | Log collector |

## Control plane logs

The vCluster pod writes operational logs to `stdout`. These cover syncer activity, API request handling, controller reconciliation, and runtime errors. Check these logs first when diagnosing unexpected vCluster behavior.

```bash
kubectl logs -n <vcluster-namespace> <vcluster-pod-name> -f
```

```text title="Example output"
2025-06-16 04:43:25	INFO	license	loader/inject.go:52	initializing license...	{"component": "vcluster"}
2025-06-16 04:43:25	INFO	license	loader/inject.go:59	detected license type	{"component": "vcluster", "licenseType": "Online"}
2025-06-16 04:43:29	INFO	online/license.go:141	Enabled features:	{"component": "vcluster"}
2025-06-16 04:43:29	INFO	syncer/syncer.go:84	starting syncer	{"component": "vcluster"}
```

By default, logs use a human-readable console format at `info` level. To change the output format or increase verbosity:

- [Log encoding](../configure/logging-and-telemetry/logging.mdx) — switch between console and JSON format
- [Enable debug logging](../troubleshoot/diagnostics/enable-debug-logging.mdx) — increase verbosity for troubleshooting

### vCluster Standalone

vCluster Standalone runs the control plane as the `vcluster` systemd service on the control plane node, not as a pod. Read its logs from the systemd journal on that node:

```bash title="Follow the control plane logs"
sudo journalctl -u vcluster.service -f
```

The `vcluster` service also runs the Kubernetes control plane components, so their output goes to the same journal. Each line has a `component` field that names its source, such as `vcluster`, `apiserver`, `controller-manager`, `scheduler`, or `kine`.

```text title="Example output"
Nov 19 01:36:10 vcluster-standalone vcluster[4818]: 2026-11-19 01:36:10        INFO        loader/loader.go:234        Detected standalone license        {"component": "vcluster"}
Nov 20 20:57:07 vcluster-standalone vcluster[4818]: 2026-11-20 20:57:07        INFO        commandwriter/commandwriter.go:128        watch chan error: etcdserver: mvcc: required revision has been compacted        {"component": "vcluster", "component": "apiserver", "location": "watcher.go:332"}
```

Lines from the control plane components always show `INFO`. When a component reports its own severity, it appears in a `level` field, such as `"level": "error"`.

journald stores every line from the service at the same priority, so `journalctl -p` can't filter by severity. Filter the text instead:

```bash title="Show errors from the last hour"
sudo journalctl -u vcluster.service --since "1 hour ago" --no-pager | grep -E 'ERROR|"level": "error"'
```

When the cluster isn't connected to vCluster Platform, the error filter also returns a platform cache error every 10 seconds. You can ignore it, or add `| grep -v 'platform cache'` to hide it.

```bash title="Show API server lines from the last hour"
sudo journalctl -u vcluster.service --since "1 hour ago" --no-pager | grep '"component": "apiserver"'
```

When the control plane node also runs as a worker node, which is the default, the kubelet and containerd run as separate systemd services with their own journals:

```bash title="View kubelet and containerd logs"
sudo journalctl -u kubelet.service --since "1 hour ago" --no-pager
sudo journalctl -u containerd.service --since "1 hour ago" --no-pager
```

The Standalone installer turns on persistent journal storage, so logs survive a reboot. To read logs from the previous boot, add `-b -1` to a `journalctl` command. How long the journal keeps logs depends on the node's journald settings.

To turn on debug logging, set the `DEBUG` environment variable in `/etc/default/vcluster` and restart the service. The API server is unavailable while the service restarts. These commands assume the file doesn't exist yet. If it does, edit the `DEBUG=true` line in the file instead of replacing or deleting the file.

```bash title="Turn on debug logging"
echo 'DEBUG=true' | sudo tee /etc/default/vcluster
sudo systemctl restart vcluster.service
```

Debug lines show `DEBUG` in the level column. To turn debug logging off, remove the file and restart the service again:

```bash title="Turn off debug logging"
sudo rm /etc/default/vcluster
sudo systemctl restart vcluster.service
```

For service status checks and common problems, see [Troubleshoot vCluster Standalone control plane nodes](../troubleshoot/control-plane/standalone.mdx).

## Audit logs

The cluster's Kubernetes API server can record an audit trail of every request it receives. This includes who made the request, what resource it targeted, and what action was taken.

These are distinct from [platform audit logs](/docs/platform/administer/configure/platform-configs/audit). Platform audit logs capture requests to the platform gateway. Cluster audit logs capture requests to the cluster's own Kubernetes API server.

To enable audit logging, pass the `--audit-policy-file` flag as an API server extra argument. For a complete setup example with a ConfigMap and volume mount, see [Control plane configuration](../deploy/control-plane/kubernetes-pod/security/hardening-guide/host-nodes/3-control-plane.mdx#32-logging).

Each audit event is a single-line JSON object:

```json title="Example audit event"
{"kind":"Event","apiVersion":"audit.k8s.io/v1","level":"Metadata","auditID":"a3d3e5f0-1b2c-4d5e-9f0a-1b2c3d4e5f6a","stage":"ResponseComplete","requestURI":"/api/v1/namespaces/default/secrets","verb":"get","user":{"username":"admin","groups":["system:masters","system:authenticated"]},"sourceIPs":["10.0.0.1"],"objectRef":{"resource":"secrets","namespace":"default","name":"db-credentials","apiVersion":"v1"},"responseStatus":{"code":200},"requestReceivedTimestamp":"2025-06-16T09:20:56.123456Z","stageTimestamp":"2025-06-16T09:20:56.145678Z","annotations":{"authorization.k8s.io/decision":"allow"}}
```

By default, audit events write to `stderr`. To route them to `stdout` for collection with `kubectl logs`, add `--audit-log-path` as a second extra argument:

```yaml title="vcluster.yaml"
controlPlane:
  distro:
    k8s:
      apiServer:
        extraArgs:
        - --audit-policy-file=/etc/kubernetes/audit-policy.yaml
        - --audit-log-path=/dev/stdout
```

## Workload logs

Apps running inside the cluster write logs to `stdout` and `stderr`, the same as in any Kubernetes cluster. You can access them directly through the cluster's API server:

```bash
kubectl logs -n <namespace> <pod-name>
```

```text title="Example output"
2025-06-16T09:21:03Z INFO  Server listening on :8080
2025-06-16T09:21:04Z INFO  GET /health 200 OK (2ms)
2025-06-16T09:21:10Z ERROR Failed to connect to database: connection refused
```

For centralized collection across multiple clusters, standard log collectors such as Fluentd, Promtail, and the ELK stack need extra configuration. When vCluster syncs pods to the control plane cluster, it rewrites pod names. A pod named `web-6d4f9b` inside the cluster appears as `web-6d4f9b-x-default-x-my-vcluster` on the control plane cluster. Log collectors reading from the node filesystem see only the rewritten name and cannot correlate entries back to the originating workload.

The HostPath Mapper solves this by creating symlinks on each node that map physical pod paths back to their virtual names.

<TabItem value="oss">

Two options are available.

**Option 1: Per-cluster HostPath Mapper**

First, enable the HostPath Mapper in `vcluster.yaml`:

```yaml title="vcluster.yaml"
controlPlane:
  hostPathMapper:
    enabled: true
```

Then install the HostPath Mapper DaemonSet in the same namespace as the vCluster:

```bash
helm install vcluster-hpm vcluster-hpm \
  --repo https://charts.loft.sh \
  -n <vcluster-namespace> \
  --set VclusterReleaseName=<vcluster-name>
```

See [Host path mapper](../configure/control-plane/components/host-path-mapper.mdx) for version compatibility notes and full configuration options.

**Option 2: Collect logs from inside the cluster**

Deploy a log collector inside the cluster that reads logs through the cluster's API server, the same way `kubectl logs` does. Those collectors see virtual pod names directly, so no path remapping is needed.

This doesn't apply to collectors that tail log files from a `hostPath` volume, such as most Fluentd, Fluent Bit, and Promtail DaemonSets. When vCluster syncs a pod that mounts `/var/log`, `/var/log/pods`, or `/var/lib/kubelet/pods` from the host, it redirects the mount to a directory for that cluster under `/tmp/vcluster` on the node. Only the HostPath Mapper fills that directory, so a file-tailing collector inside the cluster needs Option 1.
