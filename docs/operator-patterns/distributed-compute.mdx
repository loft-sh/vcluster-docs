One management plane for GPU compute from every source you own or contract. Whether that is a cloud region, a co-located data center, or a compute supplier, each site runs a Standalone <GlossaryTerm term="control-plane-cluster">control plane cluster</GlossaryTerm>. Your central Platform instance sees the full fleet.

**Customer access model:** Each tenant gets an isolated cluster on dedicated GPU nodes, regardless of which compute source backs it. **Worker-node model:** Private nodes per <GlossaryTerm term="tenant-cluster">cluster</GlossaryTerm> at every site.

**Typical stack:** Central Platform (global). Per-DC Standalone control plane cluster. Private GPU nodes co-located with each Standalone instance. vMetal for owned bare metal sites.

**What makes this path different:** Every compute source, regardless of where it lives or who operates it, follows the same onboarding playbook. One ops team, one management plane, no per-provider tooling. This architecture also maps to the cluster-level isolation criteria that AI cloud buyers evaluate in frameworks like [ClusterMAX](https://www.vcluster.com/clustermax).

## Day 0: Design decisions

| Decision | Read next | Outcome |
| --- | --- | --- |
| Design the central-regional topology | [Multi-region Platform](/docs/platform/next/administer/reliability-scaling/multi-region/overview), [Standalone deployment](/docs/vcluster/deploy/control-plane/binary/basics) | Central Platform registers each DC's Standalone instance as a connected cluster. Tenant control planes run co-located with their GPU nodes at each site. |
| Define the supplier onboarding playbook | [Standalone HA](/docs/vcluster/deploy/control-plane/binary/high-availability), [Private Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes), [Auto Nodes](/docs/platform/next/vmetal/concepts/machine-types-and-nodetypes) | Standardize the steps to register a new compute source: install Standalone, connect to central Platform, join GPU inventory, validate. |
| Plan networking between sites | [VPN](/docs/vcluster/deploy/worker-nodes/private-nodes/vpn) | Each site's clusters connect to their private nodes over VPN. Define whether tenants can span sites or are bound to a single DC. |
| Define the default network policy posture | [Network policy](/docs/vcluster/configure/vcluster-yaml/policies/network-policy) | Set a default-deny east-west posture per tenant template at every site and confirm each site's CNI enforces it. Some CNIs accept NetworkPolicy objects without enforcing them. |
| Define tenant isolation at each site | [Private Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes), [vNode docs](https://www.vnode.com/docs/) | Each cluster at a site gets its own dedicated GPU nodes. vNode adds runtime isolation for untrusted workloads. |
| Choose the GPU scheduling model | [DeviceClasses](/docs/vcluster/configure/vcluster-yaml/sync/from-host/device-classes), [DRA ResourceClaims](/docs/vcluster/configure/vcluster-yaml/sync/to-host/DRA/resourceclaims) | Device-plugin-style `DeviceClass` sync covers simple, whole-GPU allocation. DRA `ResourceClaim` sync (Pro) supports fine-grained and shared GPU allocation, consistently across every compute source. |
| Standardize tenant GPU software | [Stacks](/docs/platform/next/tenants/templates/what-are-stacks), [create a Stack template](/docs/platform/next/tenants/templates/create-stack-templates) | If you manage tenant software, define one ordered application baseline that can be deployed consistently across compute sources. |
| Plan tenant storage per site | [Storage classes from host](/docs/vcluster/configure/vcluster-yaml/sync/from-host/storage-classes), [CSI storage capacities](/docs/vcluster/configure/vcluster-yaml/sync/from-host/csi-storage-capacities) | Decide which storage classes are available at each site, since local NVMe or shared storage availability can differ by compute source, and whether to sync host `CSIStorageCapacity` for scheduler-aware placement. |
| Plan security hardening and audit logging | [Security baseline](/docs/vcluster/security), [CIS hardening guide](/docs/vcluster/deploy/control-plane/kubernetes-pod/security/hardening-guide/overview), [Platform audit logging](/docs/platform/next/administer/configure/platform-configs/audit) | Apply a consistent CIS benchmark baseline across every site's control plane cluster and decide audit log retention and SIEM integration before onboarding tenants. |

## Day 1: Stand up the first compute source

1. Deploy [vCluster Platform](/docs/platform/install/quick-start-guide) in the central region. Configure [Platform HA](/docs/platform/next/administer/reliability-scaling/high-availability) and [backup](/docs/platform/next/administer/backup-restore/backup-restore-platform).
2. At the first compute site, install [vCluster Standalone](/docs/vcluster/deploy/control-plane/binary/basics) and move to [HA](/docs/vcluster/deploy/control-plane/binary/high-availability).
3. Register the site's Standalone control plane cluster with central Platform.
4. Join the site's GPU inventory as private nodes. Configure [Auto Nodes](/docs/platform/next/vmetal/concepts/machine-types-and-nodetypes) or [vMetal](https://www.vmetal.ai/docs/) for automated provisioning and reclaim.
5. Configure [templates](/docs/platform/next/tenants/templates/overview) and [quotas](/docs/platform/next/tenants/projects/quotas) in central Platform for this compute source.
6. Apply a default-deny [network policy](/docs/vcluster/configure/vcluster-yaml/policies/network-policy) in the site's template and confirm the site's CNI enforces it.
7. Configure per-site [storage classes](/docs/vcluster/configure/vcluster-yaml/sync/from-host/storage-classes) for the template.
8. Configure GPU scheduling: sync [DeviceClasses](/docs/vcluster/configure/vcluster-yaml/sync/from-host/device-classes) for device-plugin allocation, or enable [DRA ResourceClaim sync](/docs/vcluster/configure/vcluster-yaml/sync/to-host/DRA/resourceclaims) for fine-grained allocation.
9. If you manage the tenant software layer, [create a StackTemplate](/docs/platform/next/tenants/templates/create-stack-templates) for the GPU applications that should be consistent across sites, then [deploy it to the tenant environments](/docs/platform/next/use-platform/apps/use-stacks#choose-how-to-install-a-stack).
10. Apply the [CIS hardening baseline](/docs/vcluster/deploy/control-plane/kubernetes-pod/security/hardening-guide/overview) to the site's control plane cluster and enable [Platform audit logging](/docs/platform/next/administer/configure/platform-configs/audit).
11. Provision a test cluster at the site. Validate that it appears in central Platform and that workloads land on the correct GPU nodes.
12. Document the supplier onboarding playbook. Repeat steps 2-11 for each additional compute source.
