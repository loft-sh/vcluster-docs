Give each enterprise customer their own complete cluster stack. Dedicated nodes, an isolated cluster, and full cluster-admin access if you choose to offer it. Your platform team handles provisioning and lifecycle. Customers see only their own environment.

**Customer access model:** External enterprise customers, optionally with cluster-admin on their own cluster. **Worker-node model:** Private nodes per customer. See [Choose a worker node model](../plan/choose-worker-node-model.mdx).

**Typical stack:** Platform + private nodes per customer. vMetal optional for physical server fleets. vNode for customers requiring privileged workload support.

**What makes this path different:** Each customer is fully isolated at the node level. Customers may have cluster-admin rights to their own cluster while remaining invisible to each other and to the platform layer. This path is closely related to the [AI Cloud path](./ai-cloud.mdx). The main distinction is whether your customers consume Kubernetes directly (this path) or through your own product API (AI Cloud).

## Day 0: Design decisions

| Decision | Read next | Outcome |
| --- | --- | --- |
| Define per-customer node allocation | [Private Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes), [Auto Nodes](/docs/platform/next/vmetal/concepts/machine-types-and-nodetypes) | Each customer cluster maps to a dedicated node pool. Auto Nodes provisions and reclaims nodes as customers are added or removed. |
| Define the default network policy posture | [Network policy](/docs/vcluster/configure/vcluster-yaml/policies/network-policy) | Set a default-deny east-west posture per customer template and confirm the control plane cluster's CNI enforces it. Some CNIs accept NetworkPolicy objects without enforcing them. |
| Choose the GPU scheduling model | [DeviceClasses](/docs/vcluster/configure/vcluster-yaml/sync/from-host/device-classes), [DRA ResourceClaims](/docs/vcluster/configure/vcluster-yaml/sync/to-host/DRA/resourceclaims) | Device-plugin-style `DeviceClass` sync covers simple, whole-GPU allocation. DRA `ResourceClaim` sync (Pro) supports fine-grained and shared GPU allocation, relevant if customers get cluster-admin access to schedule their own workloads. |
| Plan tenant storage | [Storage classes from host](/docs/vcluster/configure/vcluster-yaml/sync/from-host/storage-classes), [CSI storage capacities](/docs/vcluster/configure/vcluster-yaml/sync/from-host/csi-storage-capacities) | Decide which storage classes each customer can request, and whether to sync host `CSIStorageCapacity` for scheduler-aware placement. |
| Plan provisioning automation | [Templates](/docs/platform/next/tenants/templates/overview), [Terraform](/docs/platform/next/vmetal/drivers/virtual-machines/terraform) | Customer cluster creation is triggered by your CRM or provisioning system, not by manual Platform operations. |
| Define the customer application baseline | [Stacks](/docs/platform/next/tenants/templates/what-are-stacks), [create a Stack template](/docs/platform/next/tenants/templates/create-stack-templates) | If every customer receives the same multi-application baseline, define its Apps or Argo CD Applications, dependencies, and health gates once. |
| Define offboarding and node reclaim | [Manage private nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/manage), [vMetal docs](https://www.vmetal.ai/docs/) | Document how nodes are reclaimed and reimaged when a customer offboards. |
| Plan security hardening and audit logging | [Security baseline](/docs/vcluster/security), [CIS hardening guide](/docs/vcluster/deploy/control-plane/kubernetes-pod/security/hardening-guide/overview), [Platform audit logging](/docs/platform/next/administer/configure/platform-configs/audit) | Apply a CIS benchmark baseline to the control plane cluster and decide audit log retention and SIEM integration, especially where customers hold cluster-admin access to their own cluster. |

## Day 1: Stand up the first customer cluster

1. Install [vCluster Platform](/docs/platform/install/quick-start-guide).
2. Configure [Auto Nodes](/docs/platform/next/vmetal/concepts/machine-types-and-nodetypes) or [vMetal](https://www.vmetal.ai/docs/) for automated node provisioning and reclaim.
3. Create a per-customer cluster template with [private nodes](/docs/vcluster/deploy/worker-nodes/private-nodes), [backing store](/docs/vcluster/configure/vcluster-yaml/control-plane/components/backing-store), and [HA](/docs/vcluster/deploy/control-plane/kubernetes-pod/high-availability).
4. Apply a default-deny [network policy](/docs/vcluster/configure/vcluster-yaml/policies/network-policy) in the template and confirm the control plane cluster's CNI enforces it.
5. Configure per-customer [storage classes](/docs/vcluster/configure/vcluster-yaml/sync/from-host/storage-classes) in the template.
6. Configure GPU scheduling: sync [DeviceClasses](/docs/vcluster/configure/vcluster-yaml/sync/from-host/device-classes) for device-plugin allocation, or enable [DRA ResourceClaim sync](/docs/vcluster/configure/vcluster-yaml/sync/to-host/DRA/resourceclaims) for fine-grained allocation.
7. Apply the [CIS hardening baseline](/docs/vcluster/deploy/control-plane/kubernetes-pod/security/hardening-guide/overview) to the control plane cluster and enable [Platform audit logging](/docs/platform/next/administer/configure/platform-configs/audit).
8. If customers receive a standard application baseline, [create a StackTemplate](/docs/platform/next/tenants/templates/create-stack-templates) and [include it in the cluster configuration](/docs/platform/next/tenants/consume-services/apps/use-stacks#choose-how-to-install-a-stack).
9. Wire provisioning automation to Platform using Terraform, CLI, or API.
10. Validate the full customer lifecycle: provision, validate isolation, access as cluster-admin, offboard, and verify node reclaim.
