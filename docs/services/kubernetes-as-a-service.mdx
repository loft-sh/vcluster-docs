Offer your customers managed Kubernetes clusters on your own infrastructure, the way hyperscalers offer services like EKS. Each customer gets a fully isolated cluster with its own control plane and API server. You run the control planes, and by default the customer gets cluster-admin on their own cluster.

This page shows how the pieces fit together and the order to build them in. Each step links to the guide that owns the procedure.

## What the service provides

- **An isolated cluster per customer.** Each cluster has its own API server, control plane, and data store, backed by a virtualized control plane that you host.
- **Dedicated worker nodes.** With private nodes, a cluster's workloads run only on nodes that belong to that cluster.
- **Self-service provisioning.** Customers create clusters from templates you publish, in the platform UI or through the management API.
- **Standard access.** Customers download a kubeconfig and use `kubectl`, Helm, and their usual tooling against their cluster.
- **Capacity on demand.** With Auto Nodes, the platform adds and removes worker nodes as each cluster's workloads need them.

Kubernetes is one of the cluster types you can offer from the same infrastructure. The same machines can also back bare metal and VM offerings, and the same templates can add AI platforms to each cluster.

## How it works

| Layer | What it does | Where it's documented |
| --- | --- | --- |
| Control plane | Runs each cluster's API server, controllers, and data store, as a pod on your control plane cluster or as a standalone binary on its own machines. | [Deploy vCluster](/docs/vcluster/deploy) |
| Worker nodes | Run each cluster's workloads. Private nodes are dedicated to one cluster and run that cluster's own networking. | [Private nodes](/docs/vcluster/deploy/worker-nodes/private-nodes) |
| Node supply | Auto Nodes provisions worker nodes through a node provider, such as vMetal's Metal3, NICo, or KubeVirt drivers. | [Auto Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/auto-nodes) |
| Templates | Define each customer cluster's version, size, node model, policies, and preinstalled apps. | [Templates](/docs/platform/next/tenants/templates/overview) |
| Projects | Decide who can create clusters, from which templates, and with what quota. | [Projects](/docs/platform/next/tenants/concepts/what-are-projects) |

## Build the service

The worker node model you choose in step 2 sets each customer's isolation.

<SharedNodesSuitability />

1. **Install vCluster Platform** on your control plane cluster. See [Install](/docs/platform/next/install/quick-start-guide).
2. **Choose the worker node model.** Do this before you create any clusters. Private nodes must be enabled when a cluster is created, and an existing cluster can't switch to them. For customers with Kubernetes access, use private nodes. See [Choose a worker node model](../plan/choose-worker-node-model.mdx).
3. **Choose where control planes run.** Run them as pods on your control plane cluster, or as standalone binaries when you start from bare machines. See [Deploy vCluster](/docs/vcluster/deploy) and [Standalone control planes](/docs/vcluster/deploy/control-plane/binary/basics).
4. **Connect a node supply for private nodes.** Create a node provider so Auto Nodes can add worker nodes to each cluster on demand. See [Auto Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/auto-nodes).
5. **Publish your cluster offerings as templates.** Set the Kubernetes version, the node model, default network policy, and any apps or Stacks each cluster starts with. See [Create templates](/docs/platform/next/tenants/templates/create-templates) and [Network policy](/docs/vcluster/configure/vcluster-yaml/policies/network-policy).
6. **Give customers access.** Give each customer one or more projects, and allow only the templates their offering includes. See [Allowed templates](/docs/platform/next/tenants/projects/allowed/templates) and [Quotas](/docs/platform/next/tenants/projects/quotas).
7. **Let customers create clusters.** Customers create a cluster from a template and download its kubeconfig. To test the service, create one cluster from a customer project and run `kubectl get nodes` against it. See [Create a cluster from a template](/docs/platform/next/use-platform/clusters/create/create-with-template) and [Retrieve a kubeconfig](/docs/platform/next/use-platform/clusters/retrieve-kube-config).

To put your own product in front of the platform, drive cluster creation from your product's API instead of the platform UI. See [Build a product control plane on the Platform API](/docs/platform/next/integrations/api-workflows/product-control-plane).

## Operate the service

- **Upgrade clusters** to new Kubernetes and vCluster versions. See [Upgrade vCluster](/docs/vcluster/next/operate/upgrade/upgrade-version).
- **Back up and restore clusters.** See [Snapshots](/docs/vcluster/next/operate/backup-restore/backup).
- **Keep control planes available.** See high availability for [pod control planes](/docs/vcluster/deploy/control-plane/kubernetes-pod/high-availability) and [standalone control planes](/docs/vcluster/deploy/control-plane/binary/high-availability).
- **Monitor clusters and capacity.** See [Fleet Observability](/docs/platform/next/fleet-operations/observability/overview).
- **Manage access.** See [Manage access to clusters](/docs/platform/next/use-platform/clusters/manage-access).

## Know where the service ends

You own the control planes, the control plane cluster that hosts them, the node supply, and upgrades. The customer owns what runs inside their cluster, including their workloads, the namespaces and RBAC they create, and any operators they install. Decide which add-ons you manage for customers, and ship those through templates so every cluster starts with them.
