vCluster Platform is the management plane for the infrastructure and services you offer tenants. From one web UI, CLI, and API, you manage bare metal servers, virtual machines, <GlossaryTerm term="tenant-cluster">clusters</GlossaryTerm>, AI platforms, and inference platforms across one or more <GlossaryTerm term="control-plane-cluster">control plane clusters</GlossaryTerm>. Access control, quotas, and lifecycle automation are built in.

Without Platform, offering this infrastructure at scale requires custom tooling for provisioning, access, quota enforcement, and lifecycle. Platform replaces that custom work with a production-ready management layer.

## How Platform fits into the picture

Platform manages what vMetal and vCluster provision:

- **[vMetal](../vmetal/overview.mdx)** provisions bare metal servers and VMs through drivers for the systems you run, such as Metal3, NVIDIA Infra Controller, and KubeVirt. A provisioned machine can go to a tenant as an instance reached over SSH, join a cluster as a node, or host a cluster's control plane.
{/* vale off */}
- **[vCluster](/docs/vcluster)** creates and runs clusters, including the API server, control plane, <GlossaryTerm term="syncer">syncer</GlossaryTerm>, and node connectivity. Managed Kubernetes, AI platforms, and inference platforms all run on these clusters.
{/* vale on */}

Platform handles everything around them. It controls who can request what, which templates and capacity they can use, when clusters sleep, and when machines are provisioned or released.

Platform installs into a Kubernetes cluster and connects to other clusters in your environment. Those connected clusters become the control plane clusters. Cluster control planes run there, and so do the components of vMetal drivers such as Metal3 and KubeVirt. Platform doesn't replace those clusters. It manages what runs inside them.

[Understand the Platform architecture →](./architecture.mdx)

## Tenants

A tenant is a customer organization, not a cluster. It's the outermost boundary on a platform that serves more than one organization. A platform admin decides which control plane clusters, node types, OS images, and templates each tenant can reach, and a tenant admin divides what's granted across projects.

Tenants are optional, and most platforms don't need them. Use projects alone when one group administers the whole platform. Add tenants when separate organizations share it and shouldn't see each other, which is the common shape for an AI cloud operator serving paying customers.

[Understand tenants →](../tenants/concepts/what-are-tenants.mdx)

## Projects

A project is a policy boundary that groups clusters and the users or teams who access them. For most platforms, a project is the top-level unit. Where tenants are in use, projects sit inside one and a project only reaches what its tenant was granted.

Inside a project you can:
- Set resource quotas that cap compute and storage across all clusters in the project
- Assign default and allowed templates so teams can only create clusters that meet your requirements
- Grant users and teams access to just this project, with no visibility into other projects

For internal platforms, projects map to teams, cost centers, or environments. For AI cloud operators, each customer gets a tenant and divides it into projects themselves.

## Bare metal and virtual machines

vMetal gives Platform one model for physical and virtual machines. You create a node provider for the system that supplies them, such as Metal3 for bare metal you provision directly or KubeVirt for VMs. Node types on that provider describe what can be requested. For bare metal providers that keep an inventory, such as Metal3, Platform tracks which servers are claimed and which are free to reuse.

A provisioned machine becomes one of three things:

- **An instance** that a tenant reaches over SSH, with no Kubernetes installed. Instances belong to a project and appear in its **Instances** view.
- **A cluster node** that joins a cluster as a private node.
- **A control plane machine** that runs a cluster's control plane.

Claiming machines from a provider that keeps an inventory, such as Metal3, requires a plan that includes machine management.

[Get started with vMetal →](../vmetal/get-started.mdx)

## Cluster management

Platform provides a complete lifecycle interface for clusters. Create, configure, upgrade, connect, and delete clusters from the UI or through the Platform API.

### Templates

Templates define a baseline `vcluster.yaml` configuration applied to every cluster created from them. Administrators define the templates available in each project. Users choose from those templates at creation time and can optionally customize within allowed bounds.

Templates solve the consistency problem at scale. Instead of relying on users to configure settings correctly, you encode requirements into a template and enforce them across the fleet.

### Applications and stacks

Cluster templates configure the Kubernetes environment itself. [Apps](../tenants/templates/what-are-apps.mdx) install individual applications into that environment. When an environment needs several Apps or Argo CD Applications with dependency ordering, health gates, or output handoff, use a [Stack](../tenants/templates/what-are-stacks.mdx) to manage them as one unit.

[Create a Stack template →](../tenants/templates/create-stack-templates.mdx)

### Upgrade

Platform upgrades a cluster by upgrading its vCluster Helm release, and it applies any `vcluster.yaml` changes in the same upgrade. Start an upgrade from the UI, or automate it by changing the cluster's version or template version through your own GitOps tooling, such as Argo CD or Flux.

## AI and inference platforms

Platform delivers AI platforms to tenants as certified Stacks. Each one is a tested bundle that installs every component in dependency order and reports health per component. Platform bundles [NVIDIA Run:ai](../integrations/cluster-workloads/certified-stacks/runai.mdx) for GPU scheduling and workload management, and NVIDIA Dynamo for serving models across GPU nodes.

A platform can run inside each tenant's cluster, or once on the control plane cluster for many tenants. Add a Stack to a cluster template, and every cluster created from that template gets the platform. To offer your own inference stack, such as vLLM or KServe, build a custom Stack with the same API.

## Sleep and wake

Platform can automatically sleep idle clusters, suspending the control plane and stopping synced workloads to free resources. When a cluster sleeps after inactivity or a manual sleep, the tenant's next `kubectl` command wakes it and restores its previous state. A cluster asleep on a schedule, or for a set duration, doesn't wake on requests. It stays asleep until the schedule wakes it or someone wakes it from the UI or CLI.

Sleep can be configured three ways:
- **Manual:** Sleep or wake a cluster on demand from the UI or CLI
- **Inactivity timeout:** Sleep after a configurable period with no API activity
- **Schedule:** Sleep and wake on a CRON schedule, useful for environments with predictable working hours

The Platform UI doesn't offer sleep for clusters on private nodes yet.

Auto-delete works the same way. Clusters idle beyond a configured threshold are deleted automatically. This is useful for ephemeral developer and CI environments where clusters are created frequently and often abandoned.

## Access control

Platform uses a layered RBAC model. Administrators control access at the platform, project, and individual cluster level.

- **Platform roles:** Control access to global settings, connected clusters, and user management
- **Project roles:** Control access to clusters, spaces, and resources within a project
- **Cluster roles:** Control what a user can do inside a specific cluster

A tenant isn't a fourth role layer. It narrows every role inside it, so a user's effective access is their role intersected with what their tenant was granted. See [effective access](../tenants/concepts/what-are-tenants.mdx#effective-access).

Platform integrates with any OIDC provider for SSO, including Okta, Azure AD, Dex, and others. Groups from your identity provider map to Platform teams, and you assign roles to those teams.

## Node management

For clusters on [private nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/), [Auto Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/auto-nodes) can manage node lifecycle. With a dynamic node pool, nodes are provisioned and joined automatically based on workload demand, and removed when they're empty or underutilized. Static pools keep a fixed size, and nodes you join manually stay under your control.

Node providers use vMetal drivers to provision the machines that join as private nodes. Bare metal comes from drivers such as [Metal3](../vmetal/drivers/bare-metal/metal3/server-lifecycle.mdx), and VMs from KubeVirt or Terraform for cloud providers.

This is the operational foundation for AI cloud providers. With dynamic pools, a cluster's GPU nodes scale up when a customer submits a job and scale back down after the job finishes, without manual intervention.

## Connected clusters

Platform connects to as many Kubernetes clusters as your infrastructure requires. These become the control plane clusters for your cluster fleet. You can distribute clusters across regions, cloud providers, or on-premises environments and manage all of them from one Platform instance.
