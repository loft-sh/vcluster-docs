vCluster helps AI cloud providers deliver highly scalable, resilient compute clusters as self-service tenant products, including managed Kubernetes, Slurm, inference, Ray, and other cluster types. Each <GlossaryTerm term="tenant-cluster">cluster</GlossaryTerm> runs on your existing infrastructure with its own API server, RBAC, and CRDs. A tenant, the customer organization, can own many clusters.

## What a cluster looks like

From the perspective of a user or workload, a cluster is a full Kubernetes cluster. They receive a `kubeconfig` scoped to their cluster and interact with it using tools built for the standard Kubernetes API, such as `kubectl`, Helm, Argo CD, and Crossplane. They can't see other clusters or the underlying <GlossaryTerm term="control-plane-cluster">control plane cluster</GlossaryTerm> through the Kubernetes API. Network-level isolation between tenants depends on the worker node model you choose.

That same Kubernetes foundation is what higher-level cluster types like Slurm, Ray, and inference-serving stacks run on as workloads.

From the platform operator's perspective, the cluster control plane runs as a pod in a namespace on the control plane cluster. Creating one requires no additional infrastructure.

## Isolation model

Each cluster enforces isolation at the API level. Each cluster gets its own API server, its own backing store, and its own resource namespace. A resource created inside one cluster has no visibility into another. CRDs, admission webhooks, and RBAC policies scope fully to each cluster and can't affect other clusters or the control plane cluster.

For workloads that require node-level isolation (GPU infrastructure, regulated industries, or paying external customers), clusters support [private nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/) where each tenant's workloads run on dedicated compute with no cross-tenant visibility at the infrastructure level.

## How vCluster Platform manages clusters

vCluster Platform is the management layer for your cluster fleet. It handles:

- **Provisioning**: create clusters from the UI, CLI, or API, with optional templates that enforce configuration baselines
- **Access control**: tenants that separate customer organizations, RBAC at the platform, tenant, project, and cluster level, and SSO with any OIDC provider
- **Lifecycle**: sleep, wake, auto-delete, and version upgrades coordinated across the fleet
- **Multi-cluster**: manage clusters across multiple control plane clusters from a single Platform instance
