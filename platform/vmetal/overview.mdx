vMetal provides the common Machine API and lifecycle across physical and virtual infrastructure drivers in vCluster Platform. It isn't a single driver, repository, or service. vMetal spans Platform's Machine and NodeProvider APIs, vCluster's node-consumption workflows, and a portfolio of provisioning drivers.

vMetal documentation is part of the Platform documentation source. It always ships and versions in lockstep with Platform.

A **Machine** represents a claim on one provisioned server, either physical or virtual. A **provisioning driver** integrates the infrastructure that supplies and manages that server. See the [Glossary](../reference/glossary.mdx) for terminology and [Machine and server concepts](./concepts/machine-lifecycle.mdx) for the lifecycle and identity model.

## How Platform and vCluster use vMetal

The platform owns the NodeProvider, NodeType, and NodeClaim resources. A NodeClaim is the Kubernetes resource that represents one Machine request and tracks its lifecycle. A tenant cluster requests capacity through [Private Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/). Managing how many private nodes join the cluster is a manual, platform-admin-driven task unless automated by [Auto Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/auto-nodes/), which maintains private node lifecycle automatically in either a static mode (reconciling to a configured desired node count) or a dynamic mode (adding or removing nodes based on configurable resource requirements, such as reserved or used CPU and memory). Auto Nodes is one consumption workflow among several, not the whole of vMetal.

## Choose a provisioning driver

vMetal provisions Machines through a portfolio of drivers. Drivers differ in implementation, maturity, and available features. Check each driver's documentation before relying on a specific capability. See [Node types and node providers](./concepts/machine-types-and-nodetypes.mdx) for the current driver list.

NICo and Metal3 provision bare metal directly without a hypervisor in the vMetal-managed path. BCM integrates existing BCM-managed infrastructure. KubeVirt provisions Kubernetes nodes as virtual machines on infrastructure you provide separately. Each driver publishes its own requirements, capabilities, and day-two operations. NICo is in active development, and this section currently documents Metal3 in the most depth.

## What vMetal provides, across drivers

Regardless of which driver provisions a Machine, vMetal gives tenant clusters:

- **Common Machine API** - the same Machine, NodeProvider, and node type model across drivers, so tenant clusters request capacity without depending on the underlying infrastructure API.
- **OS image lifecycle** - each driver resolves its own OS image today. A shared, project-scoped image cache across drivers is planned but not yet available.
- **Automatic node registration** - provisioned Machines join their target tenant cluster on their own, with no manual `kubeadm` join or agent installation.
- **Capacity tracking and reclaim** - vMetal tracks the infrastructure assigned to a Machine. During teardown, the driver either returns reusable inventory to a pool or destroys infrastructure created for the claim.
- **Resource-aware consumption** - Tenant and Project boundaries control which infrastructure resources users can see and consume. vCluster and vNode provide separate workload and runtime isolation boundaries.

Physical and virtual Machine use cases include general compute, GPU workloads, accelerator workloads, and other AI infrastructure needs. See [GPU presentation modes](./concepts/gpu-presentation-modes.mdx) for how vMetal exposes GPUs without owning the driver stack itself.

## How vMetal fits into the platform stack

- **vMetal** provides the common Machine API and lifecycle across physical and virtual provisioning drivers.
- **vCluster Platform** manages Tenant and Project boundaries, node providers, and infrastructure availability.
- **vCluster** provides tenant clusters that consume Machines as private nodes.
- **vNode** adds runtime isolation for workloads that need privileged capabilities, such as Docker-in-Docker or `hostPID`.
