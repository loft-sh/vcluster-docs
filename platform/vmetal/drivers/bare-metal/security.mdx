This guide covers the security practices that matter most for production Metal3 deployments. The four main risk areas are BMC credential handling, OS image integrity, platform role-based access control (RBAC), and the tenant isolation boundary.

## BMC credential management

### Store BMC credentials

The Metal3 Bare Metal Operator (BMO) connects to each server's BMC using credentials stored in a Kubernetes Secret. Every `BareMetalHost` references this Secret by name with `spec.bmc.credentialsName`. The Secret must be in the same namespace as the `BareMetalHost` on the control plane cluster.

The Secret requires exactly two keys:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: server-01-bmc-credentials
  namespace: <metal3-namespace>
type: Opaque
stringData:
  username: admin
  password: <redacted>
```

Use a distinct Secret per server or per logical group of servers. A single shared Secret across all BareMetalHosts means one rotation event affects all of them at once, and makes it harder to scope access.

### Rotate BMC credentials

Rotating a BMC credential doesn't modify the OS or workloads on an already-provisioned server. BMO still uses the credential to observe and manage hardware state, so a mismatch can temporarily set the BareMetalHost's operational status to `error` and prevent power or lifecycle operations.

To rotate, update the BMC password on the server's BMC management interface, then update the Kubernetes Secret with the new password. Keep the interval between those changes as short as possible. BMO picks up the new credentials during reconciliation; you don't need to restart its Deployment or deprovision the server.

Check the BareMetalHost after the Secret update:

```bash
kubectl get baremetalhost <name> -n <namespace>
kubectl describe baremetalhost <name> -n <namespace>
```

An error does not move the host into a separate provisioning state. BMO leaves it in its current provisioning state and retries reconciliation. If the error remains, verify the Secret contents and BMC reachability before attempting another lifecycle operation.

### Disable certificate verification only as a last resort

The `spec.bmc.disableCertificateVerification: true` field tells Ironic to skip TLS certificate validation when connecting to the BMC over HTTPS. Don't set this in production: it allows a man-in-the-middle to intercept BMC traffic, including credentials.

If your BMC uses a self-signed certificate or an internal CA, add that CA to Ironic's BMC trust directory instead of disabling verification. The Ironic image combines certificates mounted under `/certs/ca/bmc` into the CA bundle it uses for BMC connections. Mount the CA Secret through the NodeProvider's `metal3.deploy.metal3.helmValues` field:

```yaml
spec:
  metal3:
    deploy:
      metal3:
        enabled: true
        helmValues: |
          ironic:
            extraVolumeMounts:
            - name: bmc-ca
              mountPath: /certs/ca/bmc
              readOnly: true
            extraVolumes:
            - name: bmc-ca
              secret:
                secretName: bmc-ca-bundle
```

Create the `bmc-ca-bundle` Secret in the Metal3 release namespace on the control plane cluster, with the PEM-encoded CA certificate under key `ca.crt`. This is the namespace configured by the NodeProvider's `clusterRef`. Don't set `IRONIC_CACERT_FILE` for this purpose; that variable configures trust for the Ironic API rather than the BMC endpoints.

## Trust the OS image pipeline

### Checksums are required

When Ironic provisions a server, it downloads the OS image from `spec.image.url`. The checksum in `spec.image.checksum` ensures Ironic rejects corrupted or tampered images before writing them to disk, and aborts provisioning if the checksum doesn't match.

The checksum type defaults to MD5. Set `spec.image.checksumType` to `sha256` or `sha512` for stronger verification:

```yaml
spec:
  image:
    url: https://images.internal/ubuntu-22.04.raw.gz
    checksum: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
    checksumType: sha256
```

### Host OS images on infrastructure you control

Ironic fetches images at provisioning time from the control plane cluster. If the image URL is external, a network outage or a change at the remote host blocks all provisioning. Host OS images on infrastructure you control, such as an internal artifact registry or object storage on a private endpoint.

Platform admins create `OSImage` resources with the URL and checksum. Node types reference them by name, so tenants never supply raw image URLs, and the `OSImage` resource is the only place an image reference can be tampered with. Restrict write access to `OSImage` resources to platform admins.

### Image signing

Ironic doesn't natively verify image signatures. Checksum verification confirms integrity against a known-good value but doesn't prove provenance. Where image provenance matters, mitigate this by generating checksums in your image build pipeline and storing them alongside the image in your artifact registry, restricting write access to the image storage so that only your build system can publish new images, and restricting which OS image names and URLs can be referenced by the `OSImage` resource.

## RBAC and project isolation

### Which roles control what

`NodeProvider` and `NodeType` resources are cluster-scoped and non-namespaced. Only platform admins can create or modify them; tenants have no direct access to these objects.

Project roles determine what members of a project can do with `NodeClaim` (Machine) resources. See [Project Membership](../../../administer/users-permissions/permissions/project.mdx) for the current default Project Admin, Project User, and Project Viewer roles and how to customize them. No project role grants access to `NodeProvider` or `NodeType` resources: tenants can request and observe Machines but can't change the infrastructure configuration behind them.

### Restrict which node types a project can claim

By default, projects can reference any node type when creating a Machine. Restrict this with `spec.allowedNodeTypes` on the Project. See [Manage allowed node types](../../../administer/projects/allowed/node-types.mdx) for the field reference and examples.

### Prevent cross-project server access

Each Machine claim maps to a `NodeClaim` resource in the project's namespace (`loft-p-<project>`). The platform annotates the claimed `BareMetalHost` with `metal3.vcluster.com/node-claim: <nodeclaim-name>` and labels it with `vcluster.com/project: <project>`. The platform controller sets these annotations; tenants can't edit them.

`BareMetalHost` resources live on the control plane cluster, not in any tenant namespace. Tenants can't directly list or modify them. The platform mediates all access through `NodeClaim` objects, which are namespaced to the project.

## Tenant isolation boundaries

### What the Metal3 driver provides

Each Machine claims one physical server. The platform allocates that server exclusively to one Machine, and therefore one project, at a time: no two projects share the same CPU, memory, or storage on a provisioned server, and no hypervisor layer sits between the workload and the hardware. This is real physical isolation between projects, not the tenancy model [shared nodes](/docs/vcluster/deploy/worker-nodes/host-nodes) give tenants on a control plane cluster's own node pool.

This model suits workloads with strict requirements for physical resource predictability, PCIe device exclusivity (GPUs, FPGAs, DPUs), or regulatory requirements that prohibit shared compute.

### What the Metal3 driver doesn't provide

**Network isolation on the provisioning network.** Before a server is claimed, and while it's mid-provisioning, it shares a provisioning network segment with every other server awaiting provisioning, regardless of which project eventually claims it. A compromised server can observe PXE traffic from other servers on this network during that window. Segment the provisioning network from production tenant traffic and treat it as an operations-only network. See [Network configuration](./networking.mdx).

**Isolation between workloads on the same node.** Once a server joins a tenant cluster, it's a standard Kubernetes worker node, and every pod scheduled onto it shares that node's kernel. This is true of any Kubernetes node, not a gap specific to Metal3 or vMetal, but it's worth calling out here because a bare metal server is often the sole node backing capacity for its tenant's own workloads: if those workloads don't trust each other (for example, running third-party or user-supplied code such as inference model containers), the boundary between them is the same one described in the [shared nodes suitability guidance](/docs/vcluster/deploy/worker-nodes/host-nodes), and the same mitigation applies.

### When to add vNode

Add [vNode](https://www.vnode.com/docs/) as the container runtime when workloads scheduled onto a Metal3-provisioned node need privileged capabilities (Docker-in-Docker, `hostPID`, raw device access) but you don't fully trust what they do with those capabilities, for example because they run user-supplied inference code. vNode uses Linux user namespaces and seccomp to sandbox pods at the node level, so a container running as root inside vNode doesn't have real root on the host kernel. This hardens workloads on a single node; it doesn't change the cross-project isolation Metal3 already provides by dedicating one server per Machine.

### When physical isolation is the right answer

Physical dedication (one project per server) is already Metal3's default. It's the right answer, with no further mitigation needed, when workloads require direct kernel access that vNode can't proxy (such as custom kernel modules or bare metal DPDK), when compliance requirements mandate physical isolation and disallow any software-layer sharing, or when performance isolation requirements are absolute, with no noisy-neighbor risk at the kernel scheduler level.

## Harden the control plane cluster

The control plane cluster that runs Metal3 and Ironic has a uniquely elevated trust level. The Ironic container holds BMC credentials and can power cycle, reimage, or wipe every registered server. Treat access to this cluster as equivalent to physical access to your server room.

### Limit access to BareMetalHost resources

Only the `controller-manager` ServiceAccount and the vCluster Platform controller need permission to create, update, or delete `BareMetalHost` resources on the control plane cluster. Apply a restrictive ClusterRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: bmh-admin
rules:
- apiGroups: ["metal3.io"]
  resources: ["baremetalhosts"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
```

Bind this only to the service accounts that need it. Revoke any bindings that grant broad `*` verb access to `metal3.io` resources to human users.

### Segment the control plane cluster's network

The most effective way to restrict BMC network access is to dedicate specific control plane cluster nodes to Metal3 and Ironic, and block other workloads from scheduling there.

Taint the nodes that have BMC network access:

```bash
kubectl taint nodes <node-name> dedicated=metal3:NoSchedule
kubectl label nodes <node-name> dedicated=metal3
```

Configure the Metal3 deployment to schedule only on those nodes using the NodeProvider's `metal3.deploy.metal3.helmValues`:

```yaml
deploy:
  metal3:
    enabled: true
    helmValues: |
      tolerations:
      - key: dedicated
        operator: Equal
        value: metal3
        effect: NoSchedule
      nodeSelector:
        dedicated: metal3
```

This confines Metal3 and Ironic to nodes that have BMC network access, so no other workload can reach the BMC network even if it obtains a credential Secret.

### Enable audit logging on the control plane cluster

This is separate from the platform's own [audit logging](../../../configure/platform-configs/audit.mdx) feature, which records activity through the platform API. It doesn't see direct `kubectl` access to the control plane cluster's own API server, so enable native Kubernetes audit logging there as well, with a policy that captures write operations on both `secrets` and `baremetalhosts`:

```yaml
rules:
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets"]
- level: Request
  resources:
  - group: "metal3.io"
    resources: ["baremetalhosts"]
  verbs: ["create", "update", "patch", "delete"]
```

Forward audit logs to your SIEM or log aggregation system. Alert on any `BareMetalHost` delete or update event outside of the `controller-manager` ServiceAccount.

### Minimize human access

Treat the control plane cluster as an operations cluster, not a development cluster. Human access should be limited to platform operators by identity rather than role, time-bounded where possible (break-glass access with an audit trail), and prohibited for tenant users entirely.

Don't attach the control plane cluster to vCluster Platform as a cluster that tenants can target for workloads. The cluster exists to run infrastructure components, not to host tenant environments.
