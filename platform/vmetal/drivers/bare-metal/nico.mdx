The NVIDIA Infra Controller (NICo) driver connects vCluster Platform to an existing NICo installation.
It mirrors the site's machine inventory and offers node types that you define from those machines.
It provisions bare metal instances and supplies private nodes to clusters through Auto Nodes.
NICo manages the hardware, operating system installation, and site networking.

You can provision workloads for the platform itself, for platform Tenants, or both.
Platform workloads don't need a `Tenant` object.
A NodeProvider can serve the platform and multiple platform Tenants. You don't need a separate provider for each Tenant.

This guide is for the platform administrator who connects and operates NICo.
Complete the setup once, from [connecting the provider](#connect-the-provider) through [preparing an image](#prepare-an-operating-system-image), then [hand off to project users](#hand-off-to-project-users).
Project users then follow [Provision instances and cluster nodes with NICo](./nico-provisioning.mdx) to launch instances or supply cluster nodes with Auto Nodes.

## How the integration works

| vCluster Platform resource | NICo resource or operation |
| --- | --- |
| `NodeProvider` | Connection to one infrastructure provider organization and site. |
| `NodeType` | A pool of the provider's Machines, selected by label. You define it in the NodeProvider's `spec.nico.nodeTypes`. |
| `Machine` | A mirror of a physical machine in the configured NICo site, including its NICo labels and instance type. |
| `Tenant` | A NICo tenant organization with the same name as the Tenant, its provider account relationship, and managed allocations. |
| Platform-assigned network or instance | Uses the NodeProvider's organization as a NICo tenant, in addition to its provider role. |
| `NetworkEnvironment` | One tenant-owned VPC, plus one VPC prefix in FNN mode. |
| `OSImage` | A reusable image definition, materialized as an operating system in the consuming NICo tenant. |
| `NodeClaim` | A NICo instance on a Machine that the platform picks from the NodeType's pool, or on a pinned Machine. |

NICo uses an organization as an identity boundary. An organization can have both an infrastructure provider and a tenant record.
Provider operations manage inventory and allocations. Tenant operations manage VPCs, operating systems, and instances.
The platform authenticates as `PROVIDER_ADMIN` for inventory and allocations, and as `TENANT_ADMIN` for tenant resources.
See NVIDIA's [authentication model](https://docs.nvidia.com/infra-controller/rest-api-reference/authentication-and-authorization) and [tenant management workflow](https://docs.nvidia.com/infra-controller/documentation/configuration-day-1/tenant-management).

Adding a NodeProvider doesn't create a default network.
Create a NetworkEnvironment with an explicit assignment before provisioning instances.
NICo requires a tenant-owned VPC in both supported network modes.

## Prerequisites

- A vCluster Platform license that includes the NICo node provider and the features you use, such as instance management or private nodes.
- Administrator access to vCluster Platform and the NICo REST API configuration.
- An operational NICo 2.2.0 or later installation with a registered site and discovered machines.
- The NICo REST API base URL, provider organization, and site UUID.
- A provider-owned parent IP block for platform networks, tenant address space, and tenant site access, unless you adopt the required resources.
- A NICo-compatible OS image on a reachable image server or uploaded to the platform, or an existing NICo operating system usable by the target tenant.
- A project, for platform or Tenant workloads, in which project users create instances or clusters.

Install NICo and configure its hardware discovery, BMC credentials, provisioning services, and site network before connecting the driver.
The driver doesn't install NICo or register physical machines.
Use the [NVIDIA documentation](https://docs.nvidia.com/infra-controller/) for that setup.

Verify these network paths:

| Source | Destination | Purpose |
| --- | --- | --- |
| vCluster Platform | NICo REST API | Inventory, tenant onboarding, and resource lifecycle operations. |
| NICo REST API | Platform `/oidc/keys` endpoint | Retrieve the keys that verify platform-issued tokens. |
| NICo site provisioning services | OS image server, or the platform for an uploaded image | Download the installation image. |
| Provisioned hosts | NICo phone-home service | Report OS initialization when phone home is enabled. |
| Provisioned hosts | Cluster control plane or configured VPN endpoint | Join and operate as private nodes. |

Use trusted TLS certificates and stable endpoint names.
For private nodes, also satisfy the [node requirements](/docs/vcluster/deploy/worker-nodes/private-nodes/node-requirements) and [connectivity requirements](/docs/vcluster/deploy/worker-nodes/private-nodes).

## Choose the network mode

The NodeProvider's `spec.nico.networkMode` selects the network model for all its environments and instances.
It can't change after creation.

| Setting | `fnn` | `flat` |
| --- | --- | --- |
| Hardware and site | DPU-backed native networking. The NICo site must have native networking enabled. | Zero-DPU hosts or hosts operating in NIC mode, with a configured HostInband network. |
| NICo VPC type | `FNN` | `FLAT` |
| VPC prefix | Created from the tenant's allocated IP block, or adopted. | Not created. |
| Instance networking | One physical interface attached to the VPC prefix. | NICo automatic networking with `autoNetwork: true`. |
| Address assignment | VPC prefix configuration. | Site HostInband configuration. |

`fnn` is the default. Select `flat` explicitly for a FLAT site.
The driver doesn't support `ETHERNET_VIRTUALIZER` mode.

:::warning FLAT isn't DPU-enforced network isolation

A FLAT VPC provides NICo resource ownership, but NICo doesn't program its data plane.
Separate Tenant or VPC records don't create isolated networks on a shared HostInband segment.
Configure any required isolation in the physical network.
See NVIDIA's [FLAT VPC documentation](https://docs.nvidia.com/infra-controller/documentation/operations-day-2/managing-vp-cs/flat-vp-cs-and-zero-dpu-hosts).

:::

### Configure NICo to trust platform-issued tokens

NICo must trust platform-issued JWTs. Add an issuer with these settings:

<InterpolatedCodeBlock
  language="yaml"
  title="NICo issuer settings"
  code={'name: vcluster-platform\n' +
    'origin: custom\n' +
    'issuer: "[[GLOBAL:PLATFORM_URL]]/oidc"\n' +
    'jwks: "[[GLOBAL:PLATFORM_URL]]/oidc/keys"\n' +
    'audiences:\n' +
    '  - "[[GLOBAL:NICO_ENDPOINT]]"\n' +
    'claimMappings:\n' +
    '  - orgAttribute: organization\n' +
    '    orgDisplayAttribute: organization\n' +
    '    rolesAttribute: roles'}
/>

Follow [NVIDIA's authentication documentation](https://docs.nvidia.com/infra-controller/rest-api-reference/authentication-and-authorization) to configure the issuer in your NICo installation.

Use the platform's configured hostname for `issuer` and the NodeProvider's REST endpoint for `audiences`, without a trailing slash.
Use the dynamic organization and role mappings shown above to read these values from platform-issued tokens.
NICo permits only one dynamic organization mapping across its issuers. Check for an existing mapping before adding this issuer.
Don't add required token scopes that the platform doesn't issue.

The platform issues and refreshes short-lived tokens automatically.
The NodeProvider doesn't accept a static bearer token or a credentials Secret for this integration.
Trusting this issuer allows the platform to act as provider and tenant administrator, so restrict access to its configuration and signing keys.

</Step>

### Create the NodeProvider

In <NavStep>Nodes & Providers</NavStep>, create a node provider and select **NVIDIA NICo**.
Alternatively, apply this manifest through the management API:

<InterpolatedCodeBlock
  language="yaml"
  title="nico-provider.yaml"
  code={'apiVersion: management.loft.sh/v1\n' +
    'kind: NodeProvider\n' +
    'metadata:\n' +
    '  name: [[GLOBAL:PROVIDER]]\n' +
    'spec:\n' +
    '  nico:\n' +
    '    endpoint: "[[GLOBAL:NICO_ENDPOINT]]"\n' +
    '    org: [[GLOBAL:PROVIDER_ORG]]\n' +
    '    siteId: [[GLOBAL:SITE_ID]]\n' +
    '    siteIPBlockID: [[GLOBAL:SITE_IP_BLOCK_ID]]\n' +
    '    networkMode: [[VAR:NETWORK_MODE:fnn]]\n' +
    '    identity:\n' +
    '      platformIssued:\n' +
    '        enabled: true\n' +
    '    nodeTypes:\n' +
    '      - name: [[GLOBAL:NODE_TYPE_NAME]]\n' +
    '        machines:\n' +
    '          selector:\n' +
    '            matchLabels:\n' +
    '              nico.vcluster.com/instance-type-id: [[GLOBAL:INSTANCE_TYPE_ID]]'}
/>

Set `networkMode` to `flat` if your hosts use the FLAT model.
The endpoint is the REST API's scheme, hostname, and optional port, not a Core gRPC endpoint or a URL containing an organization path.
The driver appends `/v2/org/{org}/nico`.

`siteIPBlockID` identifies the provider's parent block, not a tenant IP block or a VPC prefix.
The platform uses it to allocate tenant address space and to establish site access for platform and Tenant networks.
It doesn't create this parent block.

Each entry in `nodeTypes` defines one NodeType. Its `machines.selector` matches labels on the provider's Machines.
The example selects every Machine of one NICo instance type.
Replace the instance type UUID with one from your site, or select on any other Machine label.
An empty selector matches every Machine of the provider.
Without `nodeTypes`, the provider offers no NodeTypes, and users can only provision by [pinning a machine](./nico-provisioning.mdx#launch-the-instance).

Apply the manifest:

```bash
kubectl apply -f nico-provider.yaml
```

</Step>

### Verify discovery

<InterpolatedCodeBlock
  language="bash"
  code={'kubectl get nodeprovider [[GLOBAL:PROVIDER]] -o yaml\n' +
    'kubectl get machines --show-labels\n' +
    'kubectl get nodetypes'}
/>

Discovery worked when `kubectl get machines` lists your site's machines.
Machine resources mirror NICo's physical inventory.
Their names combine the provider name and NICo REST machine UUID.
Don't create Machine resources manually to register NICo hardware.

Each Machine carries the labels of its NICo machine. Keys under `vcluster.com` and `loft.sh` aren't copied.
A Machine with a NICo instance type also carries it as the `nico.vcluster.com/instance-type-id` label.
You can add labels to a Machine directly, and node type selectors match them too.

The platform creates one NodeType for each `nodeTypes` entry. Its name combines the provider name and the entry name, such as `nico.gpu-h100`.
A NodeType's `status.capacity` counts the matching Machines that are available.
The platform doesn't copy CPU, memory, or GPU values from the instance type onto the NodeType.
To describe a node's size for scheduling, set `resources` on the entry.
The [provisioning task](./nico-provisioning.mdx) uses this NodeType.

### Provider configuration reference

| Field under `spec.nico` | Behavior |
| --- | --- |
| `endpoint` | NICo REST API base URL. Required. |
| `org` | Provider organization. Defaults to `vcluster-autonodes`. Immutable. |
| `siteId` | Site UUID used for provisioning and discovery. Supply it when creating the provider. Once set, it is immutable. |
| `siteIPBlockID` | Existing provider-owned parent IP block for the site. Required when the platform must allocate address space or site access for a network or Tenant. |
| `networkMode` | `fnn` or `flat`. Defaults to `fnn` and is immutable. |
| `nodeTypes` | The NodeTypes this provider offers. Each entry has a `name`, a `machines.selector` that matches Machine labels, and optional NodeType fields such as `properties` and `resources`. |
| `identity.platformIssued.enabled` | Must be `true`. Platform-issued identity is the supported authentication method. |
| `insecureSkipTLSVerify` | Defaults to `false`. Use only for isolated development environments with untrusted certificates. |

`spec.machineAllocationPolicy`, outside `spec.nico`, sets which machines a Tenant's claims can use. A NodeType entry can override it.
See [Give the Tenant machines](#give-the-tenant-machines).

## Choose the workload owner

Choose one of the following paths before creating a network.
The NetworkEnvironment's assignment determines which NICo tenant owns its VPC and instances, even when a platform administrator launches them.

### Platform-owned workloads

For a platform project, create a [platform-assigned NetworkEnvironment](#create-a-network).
The platform then initializes a NICo tenant in the NodeProvider's own organization and establishes its provider account relationship.
It does this when infrastructure is first needed, not when the NodeProvider is created.

No Tenant object or organization setting is required.
Platform claims use Machines that no Tenant holds. They never use a Machine assigned to a Tenant.
Skip Tenant onboarding below and continue with [network creation](#create-a-network).

Platform-assigned networks aren't available to tenant projects.

### Tenant-owned workloads

Configure an existing platform Tenant as a platform administrator.
Each Tenant onboards into the NICo organization with the same name as the Tenant.
There's nothing to configure for the mapping, and it can't change, because Tenant names are immutable.

The Tenant name can't match a provider organization.
The API refuses a Tenant named after a provider's `org`, and a NodeProvider whose `org` matches an existing Tenant name.

<Step>

#### Grant NodeTypes to the Tenant

Merge this configuration into the Tenant, preserving its existing users, permissions, and other settings:

<InterpolatedCodeBlock
  language="yaml"
  title="Tenant configuration"
  code={'apiVersion: management.loft.sh/v1\n' +
    'kind: Tenant\n' +
    'metadata:\n' +
    '  name: [[GLOBAL:TENANT]]\n' +
    'spec:\n' +
    '  nodeTypes:\n' +
    '    enabled: true\n' +
    '    allow:\n' +
    '      byName:\n' +
    '        - [[GLOBAL:NODE_TYPE]]\n' +
    '    quota:\n' +
    '      byType:\n' +
    '        "[[GLOBAL:NODE_TYPE]]": "2"\n' +
    '  osImages:\n' +
    '    enabled: true\n' +
    '    allow:\n' +
    '      byLabels:\n' +
    '        example.com/image-catalog: nico'}
/>

Onboarding starts automatically once the Tenant is granted a NICo NodeType or [assigned a NICo network](#create-a-network).
If a NICo tenant with the Tenant's name already exists, the platform links it. Otherwise, NICo creates it.
Either way, NICo must authorize the platform's tokens for that organization. Linking doesn't transfer the tenant's existing identity-provider credentials.
If a static issuer mapping in NICo reserves the same organization name, NICo rejects the platform's dynamic mapping. Resolve that conflict in NICo's issuer configuration first.

The platform finds the Tenant's NodeProvider from its granted NICo NodeTypes and assigned NICo networks.
Onboarding fails if those resolve to more than one NICo NodeProvider.
This is an integration restriction, not a requirement to dedicate a NodeProvider to each Tenant.

The platform enforces `quota.byType` itself. It doesn't create reservations in NICo.
The quota caps only on-demand placements. Claims on Machines assigned to the Tenant, and claims pinned to a Machine, don't count.
A claim over quota waits with the reason `TenantNodeTypeQuotaExceeded`.

The `osImages` permission makes images with the example catalog label visible to the Tenant.
Additional capabilities, such as control plane clusters, templates, and custom SSH keys, must be granted for the workflows the Tenant will use.

</Step>
<Step>

#### Give the Tenant machines

A NodeType's `machineAllocationPolicy` decides which Machines a Tenant's claims can use:

| Policy | Tenant claims use |
| --- | --- |
| `Assigned` | Only Machines assigned to the Tenant. This is the default for NICo. |
| `OnDemand` | Machines assigned to the Tenant, plus Machines that no Tenant holds. Never another Tenant's Machines. |

Set the policy on the NodeProvider's `spec.machineAllocationPolicy`, or on a `nodeTypes` entry to override it.

With `Assigned`, assign Machines to the Tenant before it provisions.
In <NavStep>Bare Metal > Machines</NavStep>, open a Machine's actions and click **Assign to tenant**.
Alternatively, label the Machine with the Tenant's name:

<InterpolatedCodeBlock
  language="bash"
  code={'kubectl label machine [[VAR:MACHINE:nico.machine-uuid]] tenant.vcluster.com/exclusive-to=[[GLOBAL:TENANT]]'}
/>

Without an assigned Machine, a Tenant claim on an `Assigned` NodeType stays pending, even when unassigned Machines are free.

</Step>
<Step>

#### Allocate address space for the Tenant

FNN and FLAT need different allocations, so follow the paragraphs for your provider's network mode.

For FNN, request a tenant IP block from the provider's parent block:

<InterpolatedCodeBlock
  language="bash"
  code={'kubectl annotate tenant [[GLOBAL:TENANT]] \\\n' +
    '  nico.vcluster.com/ip-block-prefix-length="[[VAR:TENANT_PREFIX_LENGTH:20]]"'}
/>

The parent block must have enough free space for the requested prefix.
The tenant block must, in turn, fit all VPC prefixes you plan to create for that Tenant.
For example, a `/20` tenant block can contain multiple `/24` VPC prefixes.

To use an existing NICo tenant IP block instead, set `nico.vcluster.com/ip-block-id` to its UUID.
The block must belong to the linked NICo tenant and be ready.
Use either the ID annotation or the prefix-length annotation, not both.

FLAT doesn't need a tenant IP block for instance addresses.
Creating a FLAT VPC still requires an allocation at its site.
The platform creates that site access automatically. It allocates a `/32` block from the provider's `siteIPBlockID` unless the Tenant already holds another allocation at the site.
Without `siteIPBlockID`, onboarding reports `SiteAccessUnavailable`.

Changing `nico.vcluster.com/ip-block-prefix-length` later resizes the platform's block, and removing the annotation releases it.

</Step>
<Step>

#### Wait for onboarding

<InterpolatedCodeBlock
  language="bash"
  code={'kubectl get tenant [[GLOBAL:TENANT]] -o yaml\n' +
    'kubectl wait tenant/[[GLOBAL:TENANT]] --for=condition=NICoOnboarded --timeout=10m'}
/>

Check `status.nico` for the organization, provider, tenant ID, account ID, IP block ID, and site access allocation.
Three conditions report progress:

| Condition | Reports |
| --- | --- |
| `NICoNodeProviderFound` | Whether the platform resolved exactly one NICo NodeProvider for the Tenant. `False` when a referenced provider is missing or isn't a NICo provider, or when there's more than one. |
| `NICoOnboarded` | `True` once the Tenant's NICo organization exists. `False` with a reason while authentication, account linking, site access, or IP block setup is pending or failing. |
| `NICoSiteCredentialsAvailable` | Whether the platform could load the Tenant's credentials for the NICo endpoint. |

The platform creates the tenant account relationship when needed. Existing account relationships and externally managed allocations stay external resources.

The platform places every instance on a specific machine, whether a claim names a NodeType or a Machine.
So every claim needs NICo's targeted-instance-creation capability for the tenant account.
The platform requests that capability during onboarding, on new and existing accounts.
The request is best effort. Successful onboarding alone doesn't confirm that targeted provisioning is enabled for the site, so verify it in NICo.

</Step>
</Flow>

Select the corresponding tab and save its manifest as `nico-network.yaml`.
Use a different name for each environment if you need both platform and Tenant networks.

Both manifests work with either provider mode:

- **FNN:** The driver creates a VPC and a VPC prefix. The prefix length defaults to `/24`.
  Tenant networks use their Tenant's IP block. Platform networks allocate a block from `siteIPBlockID` for that environment.
- **FLAT:** The driver creates a FLAT VPC without a VPC prefix.
  For a new platform network, it reserves a `/32` block from `siteIPBlockID` to establish site access.
  This reservation isn't the host's address pool. Host addresses come from NICo's HostInband network.

Apply the manifest for your chosen assignment and wait for the environment's `Ready` condition.

<InterpolatedCodeBlock
  language="bash"
  code={'kubectl apply -f nico-network.yaml\n' +
    'kubectl get networkenvironments.management.loft.sh [[GLOBAL:NETWORK]] -o yaml\n' +
    'kubectl wait networkenvironments.management.loft.sh/[[GLOBAL:NETWORK]] --for=condition=Ready --timeout=10m'}
/>

Give this network name to project users who [provision on it](./nico-provisioning.mdx).
Platform-assigned networks are for platform projects. Tenant-assigned networks are for that Tenant's workloads.
Set `providerRef` to the NICo NodeProvider. Only that provider's node claims can use the network, and the API refuses a claim from another provider.
See [Network environments](../../concepts/network-environments.mdx) for the assignment labels, immutability, and how a machine selects a network.

### Network properties

Set these in `NetworkEnvironment.spec.properties` before creating the environment:

| Property | Behavior |
| --- | --- |
| `nico.vcluster.com/vpc-prefix-length` | FNN prefix length, from `8` through `31`. Defaults to `24`. The source block must have sufficient free space. |
| `nico.vcluster.com/vpc-cidrs` | Optional comma-separated CIDRs for a new FNN VPC, with no spaces after the commas. Invalid for FLAT and incompatible with `vpc-id`. Doesn't replace tenant IP allocation. |
| `nico.vcluster.com/vpc-id` | Adopt an existing VPC in the assigned NICo tenant. Its network mode must match the provider. |
| `nico.vcluster.com/vpc-prefix-id` | Adopt an existing FNN VPC prefix. It must belong to the selected VPC. |

To adopt an existing FNN network, replace `spec.properties: {}` with:

```yaml
properties:
  nico.vcluster.com/vpc-id: <vpc-uuid>
  nico.vcluster.com/vpc-prefix-id: <vpc-prefix-uuid>
```

For FLAT, supply only `vpc-id`.
For FNN, adopting only the VPC still requires address space to create its prefix.
Tenant-owned FNN networks require the Tenant's IP block configuration even when adopting a prefix.

:::warning Use properties to adopt resources

Don't prepopulate `nico.vcluster.com/vpc-id` or `nico.vcluster.com/vpc-prefix-id` in metadata annotations.
The controller writes those annotations itself to track what it manages.
Supplying IDs as properties records adoption, so the platform doesn't delete the adopted resources during teardown.

:::

## Prepare an operating system image

An [OSImage](../../images/os-images.mdx) lets multiple claims reference one image definition.
Use an image that meets NICo's boot requirements and, for cluster nodes, the private node requirements.
The image must support the instance user data used by the platform.

<PageVariables OS_IMAGE="ubuntu-nico" />

:::warning Imaging overwrites the selected disk

Choose the target disk and root filesystem identifier for your actual hardware and image.
Don't copy an example device name without verifying it.
See NVIDIA's [image-based operating system guidance](https://docs.nvidia.com/infra-controller/documentation/configuration-day-1/image-based-operating-systems).

:::

<InterpolatedCodeBlock
  language="yaml"
  title="nico-os-image.yaml"
  code={'apiVersion: management.loft.sh/v1\n' +
    'kind: OSImage\n' +
    'metadata:\n' +
    '  name: [[GLOBAL:OS_IMAGE]]\n' +
    '  labels:\n' +
    '    example.com/image-catalog: nico\n' +
    'spec:\n' +
    '  displayName: Ubuntu for NICo\n' +
    '  properties:\n' +
    '    machines.vcluster.com/os-image-type: nico\n' +
    '    nico.vcluster.com/os-image-url: "[[VAR:IMAGE_URL:https://images.example.com/ubuntu-nico.img]]"\n' +
    '    nico.vcluster.com/os-image-sha: "[[VAR:IMAGE_SHA:REPLACE_WITH_IMAGE_SHA]]"\n' +
    '    nico.vcluster.com/os-image-disk: "[[VAR:IMAGE_DISK:/dev/nvme0n1]]"\n' +
    '    nico.vcluster.com/os-image-rootfs-label: "[[VAR:ROOTFS_LABEL:cloudimg-rootfs]]"'}
/>

Replace the image URL, digest, disk, and filesystem label with values for your image.
The catalog label matches the Tenant image permission in the earlier example.
Platform users also need permission to use the OSImage.

```bash
kubectl apply -f nico-os-image.yaml
```

| OSImage property | Purpose |
| --- | --- |
| `machines.vcluster.com/os-image-type` | Set to `nico` for image filtering in the UI. |
| `nico.vcluster.com/os-image-url` | Download URL for an image-based NICo operating system. Required unless the image was [uploaded to the platform](../../images/os-images.mdx), which supplies the URL and checksum itself. |
| `nico.vcluster.com/os-image-sha` | Image checksum. The driver passes it to NICo unchanged, so use the format the NICo operating system API expects. |
| `nico.vcluster.com/os-image-disk` | Whole-disk target for installation. If omitted, NICo selects the disk. |
| `nico.vcluster.com/os-image-rootfs-id` | Root filesystem UUID. Use an identifier that matches the image. |
| `nico.vcluster.com/os-image-rootfs-label` | Root filesystem label, as an alternative to its UUID. |
| `nico.vcluster.com/os-image-id` | Reference an existing NICo operating system instead of creating one from an image URL. |

NICo image-based operating systems require exactly one of the root filesystem UUID and label.
Refer to the [NICo operating system API](https://docs.nvidia.com/infra-controller/rest-api-reference/api-reference/operating-system/create-operating-system) for image field requirements.

For an image-based definition, the driver creates or finds `vcluster-<OSImage name>` in the consuming NICo tenant at first use.
It waits for that operating system to become ready.
It enables user data overrides so each instance can receive its bootstrap configuration.
Use a new OSImage name for a new image version. Editing the image URL doesn't update an existing NICo operating system.

### Use an existing NICo operating system

Set `nico.vcluster.com/os-image-id` in the OSImage properties, or directly in the workload properties.
The existing operating system must be usable by the target NICo tenant at the configured site.
Verify its readiness, image settings, and `allowOverride: true` in NICo.
The direct ID path doesn't configure those settings for you.

If the merged workload properties contain `nico.vcluster.com/os-image-id`, that ID takes precedence over the `vcluster.com/os-image` reference.
Avoid setting both unless that override is intentional.

### Phone home, user data, and SSH

The driver enables NICo phone home by default for newly created operating systems and instances.
The host must reach NICo's phone-home service for the NICo provisioning workflow to finish.
Set the workload property `nico.vcluster.com/phone-home-enabled: "false"` only if your site intentionally doesn't use phone home.
This setting doesn't remove the requirement for a private node to join its cluster.

The platform combines its bootstrap configuration with the supported [user data templates](../../images/machine-config-templates.mdx) and [SSH key](../../images/ssh-keys.mdx) settings.
For cluster nodes, the bootstrap configuration includes the join command.
For standalone instances, users reference an SSHKey with the `vcluster.com/ssh-keys` workload property. Selecting an image alone doesn't grant SSH access.
Tenant users need permission to use the key or create their own SSH keys.

## Hand off to project users

Project users provision with [Provision instances and cluster nodes with NICo](./nico-provisioning.mdx).
Before they start, give them these names and confirm their access:

- The NodeProvider name, such as `nico`, and the NodeType name, such as `nico.gpu-h100`.
- A ready NetworkEnvironment assigned to the platform for a platform project, or to their Tenant for a tenant project.
- An OSImage they have permission to use.
- For standalone instances, an SSHKey they can use, or permission to create their own.
- A project whose `allowedNodeTypes` and `allowedNetworkEnvironments` permit those selections.
- For a Tenant on an `Assigned` NodeType, at least one [Machine assigned to the Tenant](#give-the-tenant-machines).

## Cleanup and resource ownership

Delete workloads before deleting their networks, and delete networks before removing a Tenant or NodeProvider.
Keep the provider connection and issuer trust available until cleanup completes.
Deleting a Kubernetes resource can start a destructive, asynchronous NICo operation.

| Resource | Cleanup behavior |
| --- | --- |
| NodeClaim | Deletes its NICo instance and waits for deletion. The Machine shows the `Deprovisioning` phase until NICo reports it ready again. NICo controls hardware cleanup and return to service. |
| Platform-created VPC and prefix | Deleted with the NetworkEnvironment, prefix first. A platform network's managed IP block allocation is released afterward. |
| VPC or prefix supplied through adoption properties | Retained in NICo. Any additional resources created by the platform are still cleaned up. |
| Tenant site access allocation and carved IP block | Released during Tenant cleanup. Dependencies or active use can block release. |
| Account relationship created for a platform Tenant | Deleted during Tenant cleanup only if no allocations remain. Retained if external allocations remain. |
| Existing tenant IP block, account relationship, or external allocation | Not deleted as a platform-owned resource. |
| NICo tenant organization | Not deleted by the integration. |
| NICo operating system created from an OSImage | Retained after instance deletion. Deleting the OSImage or the NodeProvider deletes the `vcluster-<OSImage name>` operating system once no NodeClaim references it. |
| NICo operating system referenced by `os-image-id` | Not deleted by the integration. |

For Auto Nodes, remove the pool or cluster first so it stops maintaining its NodeClaims.
Then wait for those instances to deprovision before removing the environment.
Tenant cleanup waits while associated NetworkEnvironments remain.
Don't bypass cleanup by removing finalizers or manually deleting stored NICo IDs.

To take a Tenant off NICo without deleting it, remove its NICo NodeType grants and NICo networks.
The platform then releases the Tenant's platform-owned NICo resources and clears `status.nico`.
Moving a Tenant to a different NICo NodeProvider directly isn't supported. Onboarding reports `NodeProviderChanged`.
Deleting a NodeProvider waits while any Tenant still uses it.

Run these checks as a platform administrator. Skip the Tenant command for platform-owned workloads.
Set the project's management namespace, such as `p-default`, for the NodeClaim command.
For server logs, use the Kubernetes context hosting the platform and your actual deployment namespace.
Correlate controller messages with NICo REST and site logs using the recorded instance, VPC, or prefix ID.

| Symptom | Checks and next action |
| --- | --- |
| Provider rejected for licensing | Verify that the platform license includes the NICo node provider and machine management. |
| NICo returns `401` or `403` | Check issuer, audience, role and organization mappings, JWKS reachability, TLS, and clock synchronization. Check NICo's REST API logs for the rejected claim. |
| No NodeTypes | Check `spec.nico.nodeTypes` on the NodeProvider. The platform creates NodeTypes only from those entries. |
| NodeTypes exist but there is no capacity | Check the NodeType's `status.capacity`, its `machines.selector`, and the Machines' labels and phases. For a Tenant, check Machine assignments and `machineAllocationPolicy`, and for `OnDemand` types, `quota.byType`. |
| Tenant doesn't onboard | Check that the Tenant has a granted NICo NodeType or an assigned NICo network. Then check `NICoNodeProviderFound` and `NICoOnboarded`. The Tenant name can't equal a provider org. |
| Onboarding reports multiple providers | Grant NodeTypes and assign networks from only one NICo NodeProvider to that Tenant. |
| Network stays pending | Check its assignment and conditions, Tenant onboarding, site access, and NICo VPC status. A Tenant network waits with the reason `WaitingForTenantOnboarding` until the Tenant is onboarded. For FNN, also check its IP block and prefix. |
| FLAT network can't provision | Configure a valid `siteIPBlockID` with space for the site access allocation. FLAT still needs a VPC and allocation-based site access. |
| Visible network missing from instance selector | Check that one of the project's allowed node types, or a Machine assigned to the project's Tenant, uses the network's provider. Then check the project's Tenant, assignment, and `Project.spec.allowedNetworkEnvironments`. Network readiness is checked during provisioning, not used to filter this selector. |
| Instance remains pending after boot | Check OS readiness, image reachability, filesystem settings, user data override permission, and the NICo phone-home path. |
| Existing OS rejects user data | Verify `allowOverride: true`. This is especially important when selecting a NICo operating system ID directly. |
| NICo instance is ready but the node has not joined | Check bootstrap logs on the host, private node prerequisites, control plane or VPN connectivity, DNS, and the cluster's node status. |
| Launch fails at NICo | Verify that the tenant account has the targeted-instance-creation capability. For a pinned claim, also verify the Machine name and provider, and that it's available and unclaimed. A Machine in the `Deprovisioning` phase becomes available once NICo finishes cleaning it. |
| Claim fails with `InsufficientCapacity` | No matching Machine became available within the provisioning wait. Check the capacity row above. |
| A delete remains pending | Check remaining instances, prefixes, allocations, and NICo resource status. Restore provider connectivity rather than removing finalizers. |

## Limitations

- Tenant onboarding supports one NICo NodeProvider per Tenant, counting both granted NodeTypes and assigned networks. Multiple Tenants can share that provider.
- A Tenant's NICo organization is always the Tenant name. To link an existing NICo tenant, give the platform Tenant the same name.
- Network assignment and configuration are immutable. The integration doesn't move VPCs or running instances between tenants.
- One VPC per NetworkEnvironment. FNN provisioning attaches one physical interface to one VPC prefix.
- No configuration for additional VPC interfaces, InfiniBand partitions, Spectrum-X partitions, NVLink partitions, or VPC peering through this driver.
- No `ETHERNET_VIRTUALIZER` support. FLAT isolation depends on the site's physical network.
- Platform-issued identity only. No static-token or external credentials configuration on the NodeProvider.
- No automatic parent IP block creation. Supply an existing block with `siteIPBlockID`.
- Machine power state comes from NICo host BMC health alerts and can lag by a few minutes. The platform can't power machines on or off through NICo. Use NICo for hardware power management.
- Changes to an OSImage don't reimage running instances. Use a new image definition and replace the affected instances.
- NICo operating systems referenced directly by `os-image-id` require separate cleanup in NICo.
