A machine validation profile names the BIOS settings a kind of machine must have, and selects the machines they apply to.
vCluster Platform reads each selected machine's BIOS through NICo's `nico-bmc-proxy` and records the result on the Machine.
A NICo node type picks a machine for a new claim only when it matches every profile that selects it.

The platform never holds a BMC credential.
It sends Redfish reads to `nico-bmc-proxy` and authenticates with a client certificate.
The proxy fetches the BMC credential from NICo and forwards the request.

This guide is for the platform administrator, and for whoever operates the NICo installation.
It assumes the NodeProvider is already connected, as described in [NVIDIA Infra Controller](./overview.mdx).

## How the check works

1. You describe the settings a kind of machine must have in a `MachineValidationProfile`.
   The profile selects the machines it applies to by label.
2. The platform reads the BIOS of every machine a profile selects.
   It records a result per profile and per setting under the Machine's `status.validation.outOfBand`.
   This is the machine's out-of-band validation, because the platform reads the BMC and runs nothing on the machine.
3. A NICo node type picks a machine for a new claim only when every profile that selects it reads `Matched`.
   It also waits while a new check of the machine is pending.

A machine is read while nobody outside the platform uses it, including while it waits in a validation cluster.
The BMC answers while the operating system runs.
A machine assigned to a Tenant is still read.
A machine that runs an instance, or that's being handed to one, waits until it's free.

A `Matched` or `Mismatched` result doesn't trigger a new read by itself.
A `RebootRequired` or `ReadFailed` result is read again five minutes after the last read, once the machine is free to read.
A machine is checked again after it's released from an instance, and after it's unassigned from a tenant or moved to another.
Whoever had root on the machine could have changed its BIOS settings.

A NICo node type counts a free machine in its capacity only when the machine matches every profile that selects it.
Machines that its claims already hold stay counted.
If no free machine matches, a claim for the node type waits, and fails with `InsufficientCapacity` once its provisioning wait runs out.
The check never changes a BIOS setting or reboots a machine, so a machine that doesn't match stays out until someone fixes it.
See [Fix a machine that doesn't match](#fix-a-machine-that-doesnt-match).

## Prerequisites

- A NICo installation that runs `nico-bmc-proxy`, reachable from the control plane cluster that runs vCluster Platform.
- A DNS name for the proxy. Its serving certificate carries DNS names only, so the platform can't reach it by IP address.
- Platform administrator access to the management API, to create `MachineValidationProfile` resources and edit the NodeProvider.
- Access to change the NICo Helm values and to restart the proxy.

Set these values to match your installation.
`PROVIDER`, `NICO_ENDPOINT`, and `INSTANCE_TYPE_ID` are the values you used in [NVIDIA Infra Controller](./overview.mdx).

## Describe the required settings

A profile names the settings a kind of machine must have, grouped by where they live.
For a Redfish `Bios` group, `attribute` is the name from the BMC's attribute registry.

Attribute names and values are specific to the hardware vendor and BIOS version.
They're the keys and values under `Attributes` in the system's Redfish `Bios` resource, the same resource the platform reads.
Read that resource with your BMC tooling to find them, or run a first check against a draft profile.
The setting in the example below shows the shape of a profile, so replace it with your hardware's.
Each setting's result records the value the BMC reports, as described in [Fix a machine that doesn't match](#fix-a-machine-that-doesnt-match).

<InterpolatedCodeBlock
  language="yaml"
  title="machine-validation-profile.yaml"
  code={'apiVersion: management.loft.sh/v1\n' +
    'kind: MachineValidationProfile\n' +
    'metadata:\n' +
    '  name: [[GLOBAL:HARDWARE_CLASS]]\n' +
    'spec:\n' +
    '  displayName: DGX B200\n' +
    '  machines:\n' +
    '    selector:\n' +
    '      matchLabels:\n' +
    '        nico.vcluster.com/instance-type-id: [[GLOBAL:INSTANCE_TYPE_ID]]\n' +
    '  outOfBand:\n' +
    '  - name: bios\n' +
    '    target: Host\n' +
    '    type: Redfish\n' +
    '    redfish:\n' +
    '      resource: Bios\n' +
    '    settings:\n' +
    '    - name: acs-off\n' +
    '      attribute: IIOS1E\n' +
    '      value: IIOS1EDisabled\n' +
    '      purpose: Let GPUs and NICs talk directly'}
/>

The comparison is exact and case-sensitive.
Before it compares, the platform renders a string as it is, a boolean as `true` or `false`, and a number in decimal.

## Choose the machines a profile applies to

`spec.machines.selector` selects the Machines a profile applies to by their labels, across every NodeProvider.
A NICo Machine with an instance type carries it as `nico.vcluster.com/instance-type-id`.
The example uses that label to apply the profile to every machine of one instance type.
A profile without `spec.machines.selector` selects no machine, and `selector: {}` selects every machine.
A machine that several profiles select must match all of them.

:::warning Creating a profile takes the machines it selects out of capacity
NICo node types stop picking a machine for new claims once a new profile selects it.
They pick it again when it reads `Matched`.
Widening a profile's selector does the same for the machines it adds.
Until the NodeProvider has a working proxy, those machines read `Unsupported` or `ReadFailed` and stay out.
Claims that already run an instance keep their machine.
If the NodeProvider already serves claims, finish [Point the NodeProvider at the proxy](#point-the-nodeprovider-at-the-proxy) and [Configure nico-bmc-proxy](#configure-nico-bmc-proxy) first.
:::

Run the command against the management API, as in [NVIDIA Infra Controller](./overview.mdx):

<InterpolatedCodeBlock
  code={'kubectl apply -f machine-validation-profile.yaml'}
  language="bash"
/>

The platform reads a machine once a profile starts selecting it and the machine is free to read.
A change to a profile's settings doesn't trigger a check.
The next check of a machine uses the current settings, so ask for one to apply a change now, as described in [Verify the check](#verify-the-check).

## Point the NodeProvider at the proxy

Set `spec.nico.endpoints.bmcProxy` on the NodeProvider.
`endpoints` replaces the older `spec.nico.endpoint` field, and the API server refuses a NodeProvider that sets both.
If yours sets `endpoint`, as the one in [NVIDIA Infra Controller](./overview.mdx) does, move its value to `endpoints.api.url` and remove `endpoint` in the same edit.
If it sets `insecureSkipTLSVerify`, move that to `endpoints.api.insecureSkipTLSVerify`.
`bmcProxy.url` is an absolute HTTPS URL that carries the port.
The port is `1079` unless the site changed it, or the node port if the proxy is exposed through a `NodePort` Service, as described in [Configure nico-bmc-proxy](#configure-nico-bmc-proxy).
`bmcProxy.caBundle` is the base64 encoding of the PEM of the CA that issued the proxy's serving certificate.
Save that CA's PEM as `proxy-ca.pem` and encode it on one line:

<InterpolatedCodeBlock
  code={'base64 < proxy-ca.pem | tr -d \'\\n\''}
  language="bash"
/>

Paste the output as `caBundle`:

<InterpolatedCodeBlock
  language="yaml"
  title="NodeProvider excerpt"
  code={'spec:\n' +
    '  nico:\n' +
    '    endpoints:\n' +
    '      api:\n' +
    '        url: [[GLOBAL:NICO_ENDPOINT]]\n' +
    '      bmcProxy:\n' +
    '        url: https://[[GLOBAL:PROXY_HOST]]:[[GLOBAL:PROXY_PORT]]\n' +
    '        caBundle: [[VAR:CA_BUNDLE:LS0tLS1CRUdJTi...]]'}
/>

Once the endpoint is set, the platform publishes what the proxy has to be configured with:

<InterpolatedCodeBlock
  code={'kubectl get nodeprovider [[GLOBAL:PROVIDER]] -o jsonpath=\'{.status.nico.bmcProxy}\''}
  language="bash"
/>

- `clientCA` is the PEM of the CA the proxy has to trust.
- `issuerCN` is that CA's common name, `vcluster-platform`.
- `principal` is the identity the proxy sees for this NodeProvider, `external-role/vcluster-platform-<provider>`.

Save `clientCA` to a file for the next section:

<InterpolatedCodeBlock
  code={'kubectl get nodeprovider [[GLOBAL:PROVIDER]] -o jsonpath=\'{.status.nico.bmcProxy.clientCA}\' > vcluster-platform-ca.pem'}
  language="bash"
/>

Copy `principal` rather than building it by hand.
It's derived from the NodeProvider's name, not from its display name.

## Configure nico-bmc-proxy

Run these steps against the NICo installation, not against vCluster Platform.
They change the NICo Helm values and end with a restart of the proxy.
If the platform runs outside NICo's cluster, they also need a DNS record, a route, and a firewall rule.

NICo installs the proxy as a subchart of its umbrella chart.
Every key in these steps goes under the `nico-bmc-proxy:` block of the umbrella values file.
A key written at the top level is ignored without an error.

Starting with NICo chart v2.3.0, the subchart always runs.
In earlier releases, `nico-bmc-proxy.enabled` defaults to `true`, so check that nobody set it to `false`.

<Flow>
<Step>

**Mount the platform's certificate authority**

The proxy reads the CA it trusts as an issuer from `admin_root_cafile_path`.
The chart doesn't mount a file there, so add a Secret that holds `vcluster-platform-ca.pem` and mount it at that path.
The default path is `/etc/forge/carbide-bmc-proxy/site/admin_root_cert_pem`.

Verify that the file exists in the running container.
The proxy skips a file it can't read without logging it.
A file with no PEM block in it also adds no CA, without an error.
Only a malformed PEM block fails, which stops the proxy at start.

</Step>
<Step>

**Trust the issuer and grant the reads**

`configFiles.nicoBmcProxyConfig` replaces the whole configuration file.
Start from the configuration the release renders, keep every table it contains, and add the platform to it.
The `[tls]` table is required, and the proxy doesn't start without it.

Add the issuer, the principal, and an ACL for the principal:

<InterpolatedCodeBlock
  language="toml"
  title="nico-bmc-proxy configuration excerpt"
  code={'# append to the existing allowed_principals\n' +
    'allowed_principals = ["...", "external-role/vcluster-platform-[[GLOBAL:PROVIDER]]"]\n' +
    '\n' +
    '[auth.trust]\n' +
    '# keep the existing settings\n' +
    'additional_issuer_cns = ["vcluster-platform"]\n' +
    '\n' +
    '[auth.acls]\n' +
    '# keep the existing entries\n' +
    '"external-role/vcluster-platform-[[GLOBAL:PROVIDER]]" = [\n' +
    '  "GET /redfish/v1/Systems",\n' +
    '  "GET /redfish/v1/Systems/*",\n' +
    '  "GET /redfish/v1/Systems/*/Bios",\n' +
    '  "GET /redfish/v1/Systems/*/Bios/*",\n' +
    ']'}
/>

The chart sets `additional_issuer_cns` to an empty list.
While it's empty, no client certificate becomes an external identity.

The ACL uses wildcards because the platform follows the links the BMC returns.
It reads the system collection, then each member in order until it finds the one with a `Bios` link and the machine's serial number.
A refused read of any member fails the whole check.
The system ID and the name of the pending settings resource vary between hardware.

</Step>
<Step>

**Expose the proxy outside NICo's cluster**

Skip this step if vCluster Platform runs in NICo's cluster.

The proxy's Service is a ClusterIP on port 1079.
Set `externalService.enabled` to `true`, and add the proxy's DNS name to `certificate.extraDnsNames`.
By default, `externalService` creates a Service of type `LoadBalancer`, which exposes the proxy outside the cluster.
If your site doesn't use load balancers, set `externalService.type` to `NodePort`.
Kubernetes then assigns the Service a node port in place of 1079.
The chart also sets `externalTrafficPolicy` to `Local`, so the DNS name has to resolve to a node that runs a proxy pod.
`extraDnsNames` is used only while `certificate.dnsNames` is empty, so add the name to `dnsNames` if it's set.

<InterpolatedCodeBlock
  language="yaml"
  title="NICo umbrella values excerpt"
  code={'nico-bmc-proxy:\n' +
    '  externalService:\n' +
    '    enabled: true\n' +
    '  certificate:\n' +
    '    extraDnsNames:\n' +
    '    - [[GLOBAL:PROXY_HOST]]'}
/>

With a `NodePort` Service, read the assigned port after the upgrade:

<InterpolatedCodeBlock
  code={'kubectl get service --all-namespaces --field-selector metadata.name=nico-bmc-proxy-external \\\n' +
    '  -o jsonpath=\'{.items[0].spec.ports[?(@.name=="proxy")].nodePort}\''}
  language="bash"
/>

Set `PROXY_PORT` at the top of the page to that port, and update `spec.nico.endpoints.bmcProxy.url` on the NodeProvider to match.

The DNS record, the route, and any firewall rule are separate from the chart.
Open the firewall for the port in `url`.

</Step>
<Step>

**Restart the proxy**

The proxy reloads the CA file on the first connection after five minutes.
It reads the trust settings, the ACLs, and `allowed_principals` once at start, so restart it after you change them.
If Stakater Reloader runs in NICo's cluster, the proxy restarts on its own when its ConfigMap changes.

</Step>
</Flow>

## Verify the check

Run the commands in this section against the management API.
Pick a machine that a profile selects, and that the platform can read now.
The platform drops a request for a new check on a machine that no profile selects.
It reads a machine that no claim holds only while the machine is `Available`.
It doesn't read a machine that a claim holds or has reserved, unless that claim is the machine's own validation claim.
List the machines the example profile selects, and set `MACHINE` to one of them:

<InterpolatedCodeBlock
  code={'kubectl get machines -l nico.vcluster.com/instance-type-id=[[GLOBAL:INSTANCE_TYPE_ID]]'}
  language="bash"
/>

<PageVariables MACHINE="nico.fm100ht0example" />

A `Matched` or `Mismatched` result doesn't trigger a new read by itself, so ask for a new check.
NICo node types don't pick the machine for a new claim until the check records its results.

<InterpolatedCodeBlock
  code={'kubectl annotate machine [[GLOBAL:MACHINE]] machines.vcluster.com/rerun-validation-out-of-band='}
  language="bash"
/>

The check runs asynchronously, so results you read right away can still be the previous ones.
For a machine a profile selects, the platform removes the annotation only after it records the new results.
Wait until the annotation is gone:

<InterpolatedCodeBlock
  code={'while true; do\n' +
    '  annotations=$(kubectl get machine [[GLOBAL:MACHINE]] -o jsonpath=\'{.metadata.annotations}\') \\\n' +
    '    || { echo "could not read the machine" >&2; break; }\n' +
    '  printf \'%s\' "$annotations" | grep -qF machines.vcluster.com/rerun-validation-out-of-band || break\n' +
    '  sleep 5\n' +
    'done'}
  language="bash"
/>

If the loop prints `could not read the machine`, fix your access to the management API and run it again.
If the loop doesn't end, the platform can't read the machine now, for one of the reasons above.

Then read the result per profile:

<InterpolatedCodeBlock
  code={'kubectl get machine [[GLOBAL:MACHINE]] \\\n' +
    '  -o jsonpath=\'{range .status.validation.outOfBand.profiles[*]}{.name}{": "}{.result}{" "}{.message}{"\\n"}{end}\''}
  language="bash"
/>

| Result | Meaning |
| --- | --- |
| `Matched` | Every setting has the required value. |
| `Mismatched` | A setting has another value or is missing. |
| `RebootRequired` | The required value is pending and takes effect at the next reboot. It's read again after five minutes. |
| `ReadFailed` | The platform couldn't read the BIOS. The message says why. It's read again after five minutes. |
| `Unsupported` | The NodeProvider isn't a NICo provider, or has no `bmcProxy` endpoint. A NICo node type doesn't pick the machine for a new claim. |
| `Reading` | A check is running. |

## Fix a machine that doesn't match

The check reports a mismatch but never changes a BIOS setting or reboots the machine.
To see each setting's required, current, and pending values, read the per-setting results:

<InterpolatedCodeBlock
  code={'kubectl get machine [[GLOBAL:MACHINE]] \\\n' +
    '  -o jsonpath=\'{range .status.validation.outOfBand.profiles[*].groups[*].settings[*]}{.name}{": "}{.result}{" expected="}{.expected}{" current="}{.current}{" staged="}{.staged}{"\\n"}{end}\''}
  language="bash"
/>

A setting reads `Missing` when the BMC doesn't report its attribute at all.
That usually means the profile describes another class of hardware, or the attribute name is wrong.

To bring a machine into line:

1. Change the setting through NICo or the hardware vendor's tooling.
2. If the new value is only pending, reboot the machine through NICo or the BMC.
3. Ask for a new check, as described in [Verify the check](#verify-the-check).

When every profile that selects the machine reads `Matched`, NICo node types can pick it again.

## Troubleshoot

The Machine's `Validated` condition reports the worst of the profiles that select it.
It also reflects the machine's in-band validation attempt, and a request for a new check that hasn't run yet.

A profile's message names what went wrong.
In the messages below, a value in angle brackets stands for one from your site, and `...` marks text left out.

| The message reads | Check |
| --- | --- |
| `the BMC proxy did not answer for "<serial>": ...` | That the DNS name resolves, the port in `url` is 1079 or the node port, routing and firewall allow it, `caBundle` is the right CA, and then the mounted CA file. |
| `GET <path> for "<serial>" was refused: ...` | The ACL and `allowed_principals` first. If they're right, the BMC rejected the credential the proxy holds, which is on the NICo side. |
| `the BMC proxy knows no BMC for serial "<serial>": ...` | The Machine's `status.hardware.serial`, and NICo's inventory. |
| `the BMC proxy reached neither the BMC of "<serial>" nor its credential: ...` | NICo's credential for the BMC, or the proxy's route to the BMC. |
| `the BMC answered for serial "<reported>", not "<serial>": ...` | The BMC reported another serial than the one the platform routed by. |
| `node provider "<provider>" has no way of reading the machine's BIOS` | The NodeProvider isn't a NICo provider, or `spec.nico.endpoints.bmcProxy` isn't set. |
| `... caBundle of "<url>" holds no PEM encoded certificate` | `caBundle` isn't the base64 encoding of a PEM. |
| `the machine has no serial number, so its BMC cannot be reached` | The machine has no `status.hardware.serial` yet. |

A `caBundle` that isn't empty must hold at least one PEM encoded certificate.
Otherwise the API server rejects the NodeProvider with `must hold at least one PEM encoded certificate`.

The proxy's log shows the identity it computed for the platform.
`Request denied by BMC proxy principal allow-list` carries `present_principals`.
If it's empty, check `additional_issuer_cns`. If it's present but not listed, check `allowed_principals`.

## Limitations

- Only NICo can read a machine's BIOS.
  A Metal3 machine that a profile selects reads `Unsupported`, and its `Validated` condition is `False`, but Metal3 node types still pick it.
  Select by `nico.vcluster.com/instance-type-id` to keep Metal3 machines out of the check.
- The client CA is derived from the platform's license key. If the key changes, reads fail.
  They work again once you install the new `clientCA` from `status.nico.bmcProxy` on the proxy.
- A change to a profile's settings doesn't change a recorded result until the next check. Ask for a new check to apply it.
- A claim pinned with `spec.machineRef` bypasses the BIOS check.
