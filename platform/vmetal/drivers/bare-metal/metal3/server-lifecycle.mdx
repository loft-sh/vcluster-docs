vCluster Platform integrates [Metal3](https://metal3.io/) and [Ironic](https://ironicbaremetal.org/) for bare metal server lifecycle management. Physical servers are represented as `BareMetalHost` resources on a control plane cluster. The platform manages their detection, provisioning, configuration, and decommissioning for reuse.

## When to use bare metal

Bare metal servers are a good fit when workloads need direct hardware access or predictable performance that virtualization cannot provide. Common use cases include:

- **GPU and accelerator workloads**: Machine learning training, inference, or video processing that requires direct GPU passthrough without a hypervisor layer.
- **Performance-sensitive applications**: Latency-critical databases, real-time analytics, or high-frequency trading systems that benefit from eliminating virtualization overhead.
- **Hardware passthrough**: Workloads that need access to specific hardware such as FPGAs, NICs with SR-IOV, or storage controllers.
- **Compliance requirements**: Environments where dedicated physical isolation is mandated by regulatory or security policies.

## Prerequisites

Before managing bare metal servers, you need a [Metal3 node provider](./overview.mdx) configured on a control plane cluster.
The node provider can deploy Metal3, Ironic, and a DHCP server automatically, or you can install them yourself.

Metal3 and the Bare Metal Operator rely on admission webhooks, which require [cert-manager](https://cert-manager.io/) on the control plane cluster. Install cert-manager before deploying Metal3. The platform checks for it and warns when it is missing.

## Add servers

Bare metal servers are added by creating `BareMetalHost` resources on the control plane cluster, either through the platform UI or by applying them directly with kubectl. Each BareMetalHost represents a physical server and requires BMC (Baseboard Management Controller) configuration for out-of-band management.

### BMC configuration

Each BareMetalHost needs a BMC address and credentials. The address scheme determines which driver Metal3 uses to communicate with the server's BMC.

Common address formats:

- **Redfish**: `redfish://192.168.1.100/redfish/v1/Systems/1`
- **Redfish on a Dell iDRAC**: `idrac-redfish://192.168.1.100/redfish/v1/Systems/System.Embedded.1`
- **IPMI**: `ipmi://192.168.1.100:623`

A Redfish address needs the full system path, not just the host. `/redfish/v1/Systems/1` is what Lenovo, HPE, and Supermicro BMCs answer. Dell iDRACs use their own scheme and system ID, as shown above. Consult the server vendor for its Redfish system ID. See [BMC requirements](./requirements.mdx#bmc-requirements).

For the full list of supported BMC drivers and address formats, see the [Metal3 Bare Metal Operator documentation](https://book.metal3.io/bmo/introduction.html).

BMC credentials are stored in a Kubernetes Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: server-01-bmc
  namespace: metal3-system
type: Opaque
stringData:
  username: admin
  password: <BMC-PASSWORD>
```

### Add a single server

You can add servers through the platform UI under **Bare Metal Servers**, or by creating the resources directly:

```yaml
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: server-01
  namespace: metal3-system
  labels:
    role: compute
spec:
  online: false
  bmc:
    address: redfish://192.168.1.100/redfish/v1/Systems/1
    credentialsName: server-01-bmc
    disableCertificateVerification: true
  bootMACAddress: "aa:bb:cc:dd:ee:01"
```

Key fields:

| Field | Description |
|---|---|
| `spec.online` | Desired power state. Register servers with `false` and let Ironic power them on during provisioning. |
| `spec.bmc.address` | BMC endpoint URL. The scheme (`redfish://`, `ipmi://`, and so on) selects the driver. |
| `spec.bmc.credentialsName` | Name of the Secret containing `username` and `password` keys. Must be in the same namespace. |
| `spec.bmc.disableCertificateVerification` | Set to `true` for BMCs with self-signed certificates. |
| `spec.bootMACAddress` | MAC address of the NIC used for PXE boot. |
| `metadata.labels` | Used by node type selectors to match servers to node types. |

### Bulk registration

Add multiple servers at once by applying BareMetalHost and Secret resources together:

```yaml
---
apiVersion: v1
kind: Secret
metadata:
  name: server-01-bmc
  namespace: metal3-system
type: Opaque
stringData:
  username: admin
  password: <BMC-PASSWORD>
---
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: server-01
  namespace: metal3-system
  labels:
    role: compute
    rack: rack-a
spec:
  bmc:
    address: redfish://192.168.1.100/redfish/v1/Systems/1
    credentialsName: server-01-bmc
  bootMACAddress: "aa:bb:cc:dd:ee:01"
---
apiVersion: v1
kind: Secret
metadata:
  name: server-02-bmc
  namespace: metal3-system
type: Opaque
stringData:
  username: admin
  password: <BMC-PASSWORD>
---
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: server-02
  namespace: metal3-system
  labels:
    role: compute
    rack: rack-b
spec:
  bmc:
    address: ipmi://192.168.1.101:623
    credentialsName: server-02-bmc
  bootMACAddress: "aa:bb:cc:dd:ee:02"
```

```bash
kubectl apply -f servers.yaml
```

## Server lifecycle

BareMetalHost resources go through the following states:

| State | Description |
|---|---|
| `registering` | The server is being registered in the Ironic database and BMC credentials are verified. |
| `inspecting` | Hardware inventory is being collected, including CPU, RAM, NICs, disks, firmware, and PCIe devices such as GPUs. |
| `preparing` | RAID or firmware configuration is being applied. |
| `available` | Server is ready to be provisioned. |
| `provisioning` | OS image is being written and cloud-init is being configured. |
| `provisioned` | Server is running with the configured OS. |
| `deprovisioning` | Server is being cleaned and returned to available state. |

Errors appear separately in `status.operationalStatus`, `status.errorType`, and `status.errorMessage`. For example, `status.operationalStatus: error` can accompany `status.provisioning.state: provisioning`. See the upstream [Host state machine](https://book.metal3.io/bmo/state_machine.html).

When an instance claims a server, the platform writes the OS image, user data, and network data to the `BareMetalHost` and sets `spec.online: true`. The host moves from `available` through `provisioning` to `provisioned`. When the claim is removed, the platform clears the image, user data, and network data and sets `spec.online: false`. The Bare Metal Operator (BMO) then deprovisions the host, powers it off, and returns it to `available`.

Ironic controls server power through the BMC. Register a `BareMetalHost` with `spec.online: false` and let Ironic power the server on when an instance claims it. Ironic powers it off again when the claim is removed.

A host can be claimed only when BMO reports it `available`, powered off, with no image and no `consumerRef`. Two instances can't claim the same host.

### When a host fails during provisioning

An instance doesn't move to another host once it has claimed one. During `provisioning`, `inspecting`, or `preparing`, the platform keeps the instance `Pending` and checks the host again. This wait has no platform provisioning timeout.

A BMO operational error doesn't move the instance to `Failed`. The instance stays `Pending` with no timeout. Check the host's `status.operationalStatus`, and if it's `error`, fix the host or replace the instance. The instance fails with `HostProvisioningFailed` only if BMO reports the provisioning state itself as `error`.

While the instance waits, its Machine can report a fault. The platform reports `ramdisk not booted` when Ironic has waited more than 15 minutes for the deploy ramdisk to call back. During `provisioning`, `inspecting`, or `preparing`, the platform adds that fault to the instance's condition message and keeps waiting. Fix the host or [replace the instance](../../../concepts/machine-lifecycle.mdx#when-provisioning-fails). See [Stuck in `provisioning`](./troubleshooting.mdx#stuck-in-provisioning) and [Error state](./troubleshooting.mdx#error-state) for the checks.

### Reuse and reprovisioning

After an instance is released, its `BareMetalHost` returns to the `available` pool. The next instance to claim it follows the same placement rules as any other. A host assigned to a tenant serves that tenant's instances again. An unassigned host can serve any tenant whose node type uses the `OnDemand` policy, or an instance requested outside a tenant. See [Where an instance is placed](../../../concepts/machine-lifecycle.mdx#where-an-instance-is-placed).

During release, the platform undoes what it wrote to the host when it claimed it. It removes the host's project association and the instance data it generated. See [Prevent cross-project server access](./security.mdx#prevent-cross-project-server-access) for how the project association is set. If the platform wrote the host's DHCP annotations, it restores the values you set before the claim. See the per-host DHCP annotations on the **DHCP Server** tab of [Infrastructure deployment](./overview.mdx#infrastructure-deployment).

Tenant assignment labels stay on the host's Machine. Release doesn't return a tenant's host to the unassigned pool.

During deprovisioning, BMO follows the `BareMetalHost`'s `spec.automatedCleaningMode`. The default `metadata` mode removes partition tables from all disks, while `disabled` skips automated cleaning. Neither mode performs a full-disk data erasure, and vMetal doesn't override this setting. Before allowing hosts to move between projects, define any additional sanitization controls your security policy requires. See [Automated cleaning](https://book.metal3.io/bmo/automated_cleaning.html) for the upstream behavior.

When the host is provisioned again, it follows the same steps as the first time. Metal3 doesn't skip PXE boot or OS installation for a server it has provisioned before.

## DHCP and PXE boot

When the Metal3 node provider deploys a DHCP server, it automatically handles the PXE boot flow. The DHCP server acts as a proxy between the bare metal servers and Ironic, which may reside in a different network. It forwards the API communication needed for PXE boot and OS installation.

No manual DHCP or PXE configuration is required when using the provider-managed DHCP server.
