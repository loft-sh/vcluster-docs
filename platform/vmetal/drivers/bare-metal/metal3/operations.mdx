Day-2 operations for the Metal3 driver center on managing `BareMetalHost` resources on the control plane cluster. This page covers adding and removing servers, checking fleet capacity, and where to find guidance for other common tasks. Commands on this page use `<control-plane-context>`, the cluster referenced by `NodeProvider.spec.metal3.clusterRef.cluster`.

Set your namespace once. Every command on this page updates automatically.

  NAMESPACE="my-metal3-namespace"

## Add servers

A physical server joins the pool by creating a `BareMetalHost` resource and a Secret containing its BMC credentials, both in the NodeProvider's namespace on the control plane cluster. See [Add servers](./server-lifecycle.mdx#add-servers) for the full field reference and bulk registration.

After creation, the BMO begins registration immediately. The server moves through `registering` -> `inspecting` -> `available` automatically. Inspection collects hardware inventory and typically takes a few minutes. The server isn't eligible for provisioning until it reaches `available`.

### Verify a server is ready

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost server-01 -n [[GLOBAL:NAMESPACE]] \\
  -o jsonpath='{.status.provisioning.state}'`}
/>

A response of `available` means the server is ready to claim. See [Troubleshooting](./troubleshooting.mdx) if the server stalls in `registering` or `inspecting`.

### Check hardware details

After inspection, the BareMetalHost records the server's hardware inventory:

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost server-01 -n [[GLOBAL:NAMESPACE]] \\
  -o jsonpath='{.status.hardwareDetails}' | jq .`}
/>

This includes CPU count, memory, NIC information, and disk inventory. Verify it matches the expected hardware before the server is provisioned into production.

## Remove servers

### Permanent removal

If a Machine holds the server, delete it from the vCluster Platform UI, or delete its `NodeClaim` through the API, first. The platform deprovisions the server and returns it to `available`. Then delete the BareMetalHost.

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> delete baremetalhost server-01 -n [[GLOBAL:NAMESPACE]]`}
/>

After the normal sequence, the Machine and its `NodeClaim` are already gone and the platform has released the IP address. Deleting the now-unclaimed `BareMetalHost` only removes the server from inventory.

Also delete its BMC credential Secret if it is no longer needed.

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> delete secret server-01-bmc -n [[GLOBAL:NAMESPACE]]`}
/>

If the server is permanently unreachable and can't complete normal deprovisioning, delete the `BareMetalHost` first, then delete its Machine. During Machine deletion, the driver treats the missing host as already removed, releases the IP, and finishes deleting the `NodeClaim`. The server doesn't go through the normal deprovisioning cycle, so its disk isn't cleaned. Don't use this sequence for a reachable server that can be deprovisioned normally.

### Temporarily withhold a server

To stop an available server being claimed for new Machines, break the selectors that match it. Remove or change a label that every matching node type selector requires. The server stays registered. For example, if the server is eligible because its `role` is `compute`, remove that label:

```bash
kubectl --context <control-plane-context> label baremetalhost server-01 \
  -n <namespace> role-
```

Merely adding a `maintenance=true` label doesn't exclude a server unless every applicable node type selector explicitly requires that label not to exist. Label changes don't affect servers that are already provisioned. A server already claimed by a Machine remains claimed until that Machine is deleted.

Restore the selection label to return the server to the eligible pool:

```bash
kubectl --context <control-plane-context> label baremetalhost server-01 \
  -n <namespace> role=compute
```

## Check fleet capacity

Get a view of all servers and their current states:

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost -n [[GLOBAL:NAMESPACE]] \\
  -o custom-columns='NAME:.metadata.name,STATE:.status.provisioning.state,ERROR:.status.errorMessage'`}
/>

Count available servers:

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost -n [[GLOBAL:NAMESPACE]] -o json | \\
  jq '[.items[] | select(.status.provisioning.state=="available")] | length'`}
/>

A server in `available` is ready for a new Machine request. A server in `provisioning` or `provisioned` is claimed. A server in `error` needs attention before it can be used again. See [Troubleshooting](./troubleshooting.mdx) for how to resolve error states.
