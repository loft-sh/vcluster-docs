Day-2 operations for the Metal3 driver center on managing `BareMetalHost` resources on the control plane cluster. This page covers adding and removing servers, checking fleet capacity, and where to find guidance for other common tasks. Commands on this page use `<control-plane-context>`, the cluster referenced by `NodeProvider.spec.metal3.clusterRef.cluster`.

Set your namespace once. Every command on this page updates automatically.

  NAMESPACE="my-metal3-namespace"

## Add servers

A physical server joins the pool by creating a `BareMetalHost` resource and a Secret containing its BMC credentials, both in the NodeProvider's namespace on the control plane cluster. See [Add servers](./server-lifecycle.mdx#add-servers) for the full field reference and bulk registration.

After creation, the BMO begins registration immediately. The server moves through `registering` -> `inspecting` -> `available` automatically. Inspection collects hardware inventory and typically takes a few minutes. The server isn't eligible for provisioning until it reaches `available`.

### Verify a server is ready

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost server-01 -n [[GLOBAL:NAMESPACE]] \\
  -o jsonpath='{.status.provisioning.state}'`}
/>

A response of `available` means the server is ready to claim. See [Troubleshooting](./troubleshooting.mdx) if the server stalls in `registering` or `inspecting`.

### Check hardware details

After inspection, the BareMetalHost records the server's hardware inventory:

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost server-01 -n [[GLOBAL:NAMESPACE]] \\
  -o jsonpath='{.status.hardware}' | jq .`}
/>

This includes CPU count, memory, NIC information, and disk inventory. Verify it matches the expected hardware before the server is provisioned into production.

## Inspect the BMC

Redfish Explorer lets a platform admin inspect a server's BMC resources and run the actions its firmware exposes. Use it to investigate hardware health or BMC behavior.

Before you begin:

- The Metal3 UI requires a platform admin outside tenant scope, with the machine management and Metal3 features enabled. You also need permission to `create` the `metal3bmcs/redfish` subresource in `cluster.loft.sh`. The permission applies on the host's control plane cluster, in its namespace. Permission to read a Machine alone doesn't grant BMC access.
- The host needs a Redfish-compatible BMC address and a credential Secret. An `ipmi://` address doesn't support this explorer.
- The platform agent on the control plane cluster must be able to reach the BMC. See [BMC requirements](./requirements.mdx#bmc-requirements).

:::warning BMC actions affect running workloads
Redfish access includes actions that change hardware state. A reset or power action can interrupt workloads. Grant this access only to operators trusted to administer the physical server.
:::

<Flow>
<Step>
Open <NavStep>Bare Metal > Machines</NavStep> and click the <Label>Metal3</Label> tab, if shown.
</Step>
<Step>
Open the server, then click the <Label>Redfish</Label> tab. The entry appears only when your permissions allow Redfish requests for that host.
</Step>
<Step>
Browse the resource tree or enter a path beginning with `/redfish/`. Inspect the resource's properties and links. The BMC's firmware determines which resources appear. A successful request displays the selected resource's properties.
</Step>
</Flow>

To run an action, click it under <Label>Actions</Label>. Supply its parameters and any required JSON body, then click <Button>Continue</Button>. Review the target and request body before clicking <Button>Run action</Button>.

Read the response before retrying an action. A BMC can accept an asynchronous operation and return a task link. Follow that link to check progress. If a request times out, check the hardware state before sending the action again.

### Audit BMC requests

The platform agent sends requests using the credentials referenced by the BareMetalHost. Requests and responses can contain BMC account passwords and session tokens.

The built-in audit policies record `create` requests to `metal3bmcs/redfish` at `Metadata` level. This preserves attribution without logging request or response bodies. With a custom policy, keep this rule before broader rules that capture bodies. See [Metadata-only for sensitive data](../../../../administer/configure/platform-configs/audit-policy.mdx#metadata-only-for-sensitive-data).

## Check a server's address and power

Open <NavStep>Bare Metal > Machines</NavStep>. The inventory shows `On` or `Off` beside each machine's name. On the <Label>Metal3</Label> tab, each host's name carries a power badge that also shows transitions, and the <Label>IP address</Label> column shows the host's configured DHCP address.

### Interpret the IP address

The Metal3 host list reads `metal3.vcluster.com/ip-address` and omits its prefix length. It doesn't fall back to an address collected during hardware inspection.

Machine network details in the inventory combine inspected NIC information with the configured address. The Metal3 server details page shows inspected addresses only. On the NIC matching `spec.bootMACAddress`, the configured address replaces inspected addresses of the same family, except link-local addresses.

Treat these addresses as configuration information. They don't confirm that the server is reachable. Without NIC inventory, Machine network details are absent. With inventory but no valid annotation or matching boot MAC, they retain the inspected addresses. A custom network-data document that configures another address isn't reflected in this overlay. Address information can also lag a reset until power-off.

See [Set a host address](./networking.mdx#set-a-host-address) for configuration and [Unexpected or missing IP address](./troubleshooting.mdx#unexpected-or-missing-ip-address) for diagnosis.

### Interpret power status

The Metal3 tab's badge shows `On`, `Off`, `Powering On`, `Powering Off`, or `Rebooting`. It uses Ironic's power reading when available, with the BareMetalHost's reported power as a fallback. Transitional labels also consider pending power changes and the host's desired state.

Power is separate from provisioning phase. An `On` server can still be inspecting, provisioning, or failing to boot. BMO updates its own power reading in resting states, so fallback readings can lag during provisioning or deprovisioning.

Check the host's <Label>Ironic</Label> view, when your permissions expose it, to compare current and target power state. See [Unexpected power status](./troubleshooting.mdx#unexpected-power-status) if the badge disagrees with the server.

## Remove servers

### Permanent removal

If an instance holds the server, delete it from the vCluster Platform UI, or delete its `NodeClaim` through the API, first. The platform deprovisions the server and returns it to `available`. Then delete the BareMetalHost.

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> delete baremetalhost server-01 -n [[GLOBAL:NAMESPACE]]`}
/>

After the normal sequence, the instance and its `NodeClaim` are already gone and the platform has released the IP address. Deleting the now-unclaimed `BareMetalHost` only removes the server from inventory.

Also delete its BMC credential Secret if it is no longer needed.

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> delete secret server-01-bmc -n [[GLOBAL:NAMESPACE]]`}
/>

If the server is permanently unreachable and can't complete normal deprovisioning, delete the `BareMetalHost` first, then delete its instance. During instance deletion, the driver treats the missing host as already removed, releases the IP, and finishes deleting the `NodeClaim`. The server doesn't go through the normal deprovisioning cycle, so its disk isn't cleaned. Don't use this sequence for a reachable server that can be deprovisioned normally.

### Temporarily withhold a server

To stop an available server being claimed for new instances, break the selectors that match it. Remove or change a label that every matching node type selector requires. The server stays registered. For example, if the server is eligible because its `role` is `compute`, remove that label:

```bash
kubectl --context <control-plane-context> label baremetalhost server-01 \
  -n <namespace> role-
```

Merely adding a `maintenance=true` label doesn't exclude a server unless every applicable node type selector explicitly requires that label not to exist. Label changes don't affect servers that are already provisioned. A server already claimed by an instance remains claimed until that instance is deleted.

Restore the selection label to return the server to the eligible pool:

```bash
kubectl --context <control-plane-context> label baremetalhost server-01 \
  -n <namespace> role=compute
```

## Check fleet capacity

Get a view of all servers and their current states:

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost -n [[GLOBAL:NAMESPACE]] \\
  -o custom-columns='NAME:.metadata.name,STATE:.status.provisioning.state,ERROR:.status.errorMessage'`}
/>

Count available servers:

<InterpolatedCodeBlock
  code={`kubectl --context <control-plane-context> get baremetalhost -n [[GLOBAL:NAMESPACE]] -o json | \\
  jq '[.items[] | select(.status.provisioning.state=="available")] | length'`}
/>

A server in `available` is ready for a new instance request. A server in `provisioning` or `provisioned` is claimed. A server with operational status `error` needs attention before it can be used again. See [Troubleshooting](./troubleshooting.mdx) for how to resolve errors.
