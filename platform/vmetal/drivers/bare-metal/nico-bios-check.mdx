A node type can require that its machines have specific BIOS settings.
vCluster Platform reads each machine's BIOS through NICo's `nico-bmc-proxy`, records the result on the Machine, and places a claim of that node type only on a machine whose settings match.

The platform never holds a BMC credential.
It sends Redfish reads to `nico-bmc-proxy` and authenticates with a client certificate.
The proxy fetches the BMC credential from NICo and forwards the request.

This guide is for the platform administrator, and for whoever operates the NICo installation.
It assumes the NodeProvider is already connected, as described in [NVIDIA Infra Controller](./nico.mdx).

## How the check works

1. You describe the settings a kind of host must have in a `HostValidationProfile`.
2. A node type selects profiles by label.
3. The platform reads the BIOS of every machine a node type with profiles selects, and records a result per profile and per setting under the Machine's `status.hostValidation.outOfBand`.
4. A node type places a claim only on a machine that matched every profile it selects.

A machine is read while nobody outside the platform uses it.
That includes a machine that waits in a validation cluster, since the BMC answers while the operating system runs.
A machine is checked again after it's released from an instance and after it's taken back from a Tenant, because whoever had root on the host could have changed its BIOS settings.

A node type advertises capacity only for machines that matched its profiles.
A claim waits without a node type until at least one machine matches, rather than being bound to a node type that can't serve it.

## Prerequisites

- A NICo installation that runs `nico-bmc-proxy`, reachable from the control plane cluster that runs vCluster Platform.
- A DNS name for the proxy. Its serving certificate carries DNS names only, so the platform can't reach it by IP address.
- Access to change the NICo Helm values and to restart the proxy.

## Describe the required settings

A profile names the settings a kind of host must have, grouped by where they live.
For a Redfish `Bios` group, `attribute` is the name from the BMC's attribute registry.

```yaml
apiVersion: management.loft.sh/v1
kind: HostValidationProfile
metadata:
  name: dgx-b200
  labels:
    hardware-class: dgx-b200
spec:
  displayName: DGX B200
  outOfBand:
  - name: host-bios
    target: Host
    type: Redfish
    redfish:
      resource: Bios
    settings:
    - name: acs-off
      attribute: IIOS1E
      value: IIOS1EDisabled
      purpose: Let GPUs and NICs talk directly
```

The comparison is exact and case-sensitive.
Before it compares, the platform renders a string as it is, a boolean as `true` or `false`, and a number in decimal.

## Require the profile on a node type

Select profiles by label on the node type in `spec.nico.nodeTypes`.
A node type with no `hostValidationProfiles` requires nothing, and an empty selector selects every profile.

```yaml
spec:
  nico:
    nodeTypes:
    - name: dgx-b200
      machines:
        selector:
          matchLabels:
            nico.vcluster.com/instance-type-id: <instance-type-id>
      hostValidationProfiles:
        selector:
          matchLabels:
            hardware-class: dgx-b200
```

A node type requires the profiles its selector matches.
A selector that matches no profile requires none.

## Point the NodeProvider at the proxy

Set `spec.nico.endpoints.bmcProxy` on the NodeProvider.
`url` is an absolute HTTPS URL that carries the port, `1079` unless the site changed it.
`caBundle` is the base64 encoding of the PEM of the CA that issued the proxy's serving certificate.

```yaml
spec:
  nico:
    endpoints:
      bmcProxy:
        url: https://<proxy-dns-name>:1079
        caBundle: <base64 of the CA PEM>
```

Once the endpoint is set, the platform publishes what the proxy has to be configured with:

```bash
kubectl get nodeprovider <name> -o jsonpath='{.status.nico.bmcProxy}'
```

- `clientCA` is the PEM of the CA the proxy has to trust.
- `issuerCN` is that CA's common name, `vcluster-platform`.
- `principal` is the identity the proxy sees for this NodeProvider, `external-role/vcluster-platform-<provider>`.

Copy `principal` rather than building it by hand.
It's derived from the NodeProvider's name, not from its display name.

## Configure nico-bmc-proxy

Run these steps against the NICo installation, not against vCluster Platform.

### Use the subchart's keys

NICo installs the proxy as a subchart of its umbrella chart.
Every key below goes under the `nico-bmc-proxy:` block of the umbrella values file.
A key written at the top level is ignored without an error.

From NICo v2.3.0 the subchart always runs.
In earlier releases, check that `nico-bmc-proxy.enabled` is `true`.

### Mount the platform's CA

The proxy reads the CA it trusts as an issuer from `admin_root_cafile_path`.
The chart doesn't mount a file there, so add a Secret that holds `clientCA` and mount it at that path.
The default path is `/etc/forge/carbide-bmc-proxy/site/admin_root_cert_pem`.

Verify that the file exists in the running container.
The proxy ignores a missing file without logging it, and fails only on a file that exists and isn't valid PEM.

### Trust the issuer and grant the reads

`configFiles.nicoBmcProxyConfig` replaces the whole configuration file.
Start from the configuration the release renders, keep every table it contains, and add the platform to it.
The `[tls]` table is required, and the proxy doesn't start without it.

Add the issuer, the principal, and an ACL for the principal:

```toml
# append to the existing allowed_principals
allowed_principals = ["...", "external-role/vcluster-platform-<provider>"]

[auth.trust]
# keep the existing settings
additional_issuer_cns = ["vcluster-platform"]

[auth.acls]
# keep the existing entries
"external-role/vcluster-platform-<provider>" = [
  "GET /redfish/v1/Systems",
  "GET /redfish/v1/Systems/*",
  "GET /redfish/v1/Systems/*/Bios",
  "GET /redfish/v1/Systems/*/Bios/*",
]
```

The chart sets `additional_issuer_cns` to an empty list, and with it empty no client certificate becomes an external identity.

The ACL uses wildcards because the platform follows the links the BMC returns.
It reads the system collection, then each member in order until one has a `Bios` link, and a refused read of any member fails the whole check.
The system ID and the name of the pending settings resource vary between hardware.

### Reach the proxy

The proxy's Service is a ClusterIP on port 1079.
If vCluster Platform runs outside NICo's cluster, set `externalService.enabled` to `true`, and add the proxy's DNS name to `certificate.extraDnsNames`.
`extraDnsNames` is used only while `certificate.dnsNames` is empty, so add the name to `dnsNames` if it's set.
The DNS record, the route, and any firewall rule are separate from the chart.

### Restart the proxy

The proxy reloads the CA file on the first connection after five minutes.
It reads the trust settings, the ACLs, and `allowed_principals` once at start, so restart it after you change them.

## Verify the check

Pick a machine that's free.
The platform doesn't read a machine that's assigned to a Tenant, reserved for a claim, or not `Available`.

A result already recorded isn't read again on its own, so ask for a new check:

```bash
kubectl annotate machine <name> machines.vcluster.com/rerun-host-validation-out-of-band=
```

Then read the result per profile:

```bash
kubectl get machine <name> \
  -o jsonpath='{range .status.hostValidation.outOfBand.profiles[*]}{.name}{": "}{.result}{" "}{.message}{"\n"}{end}'
```

| Result | Meaning |
| --- | --- |
| `Matched` | Every setting has the required value. |
| `Mismatched` | A setting has another value or is missing. |
| `RebootRequired` | The required value is pending and takes effect at the next reboot. |
| `ReadFailed` | The platform couldn't read the BIOS. The message says why. It's read again after five minutes. |
| `Unsupported` | The NodeProvider has no `bmcProxy` endpoint. |
| `Reading` | A check is running. |

The Machine's `HostValidated` condition summarizes the profiles its node types require now.

## Troubleshoot

| The message says | Check |
| --- | --- |
| the BMC proxy did not answer | That the DNS name resolves, the port is 1079, routing and firewall allow it, `caBundle` is the right CA, and then the mounted CA file. |
| was refused | The ACL and `allowed_principals` first. If they're right, the BMC rejected the credential the proxy holds, which is on the NICo side. |
| knows no BMC for serial | The Machine's `status.hardware.serial`, and NICo's inventory. |
| reached neither the BMC nor its credential | NICo's credential for the BMC, or the proxy's route to the BMC. |
| answered for serial | The BMC reported another serial than the one the platform routed by. |
| has no way of reading the machine's BIOS | `spec.nico.endpoints.bmcProxy` isn't set. |
| caBundle holds no PEM encoded certificate | `caBundle` isn't the base64 encoding of a PEM. |
| has no serial number | The machine has no `status.hardware.serial` yet. |

The proxy's log shows the identity it computed for the platform.
`Request denied by BMC proxy principal allow-list` carries `present_principals`.
If it's empty, check `additional_issuer_cns`. If it's present but not listed, check `allowed_principals`.

## Limitations

- Only NICo can read a machine's BIOS. A Metal3 node type that selects profiles picks no machines.
- The client CA is derived from the platform's license key. If the key changes, reads fail until you install the new `clientCA` from `status.nico.bmcProxy` on the proxy.
- A profile that changes doesn't change a recorded result. Ask for a new check to apply it.
