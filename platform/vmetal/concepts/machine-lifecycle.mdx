A Machine is vMetal's claim on one server (physical or virtual, depending on the driver behind it). This page describes the Machine model at a driver-neutral level. For quick term definitions, see the [Glossary](../../reference/glossary.mdx).

## Machine and server

"Machine" and "server" refer to two different objects with two different lifetimes.

A **server** is the physical or virtual host that a driver hands out. Its lifecycle depends on the driver. Metal3 selects a pre-registered `BareMetalHost`, then cleans and returns that host to inventory after use. Create-on-demand drivers instead create infrastructure for a claim: for example, KubeVirt creates a `VirtualMachine`, and Terraform applies a node template.

A **Machine** is vMetal's record of one claim on capacity. It's created when a tenant cluster or administrator requests capacity, and it's deleted when that capacity is no longer needed. A Machine's identity doesn't outlive the claim. During teardown, the driver either releases reusable inventory or destroys infrastructure that it created for the claim.

This distinction matters because the two objects answer different questions. "Is the underlying infrastructure healthy" is a driver-specific question, answered from resources such as a Metal3 `BareMetalHost`, a KubeVirt `VirtualMachine`, or Terraform output. "Is this Machine ready" is a question about the current claim, answered by checking whether scheduling, provisioning, and joining have completed.

## Machine lifecycle

Every Machine, regardless of driver, passes through the same milestones:

<figure>
  <MachineModelLifecycle style={{width: '100%', height: 'auto'}} role="img" aria-label="Machine lifecycle from requested through scheduled, provisioned, joined, ready, and destroyed" />
</figure>

1. **Requested** - a tenant cluster or an administrator asks for capacity matching a node type, and the platform creates the Machine.
2. **Scheduled** - vMetal selects an eligible node type and driver. The driver either claims existing inventory or creates new infrastructure.
3. **Provisioned** - the driver finishes preparing the capacity, which can include creating a VM, installing an OS, configuring networking, and running startup automation.
4. **Joined** - for tenant-cluster capacity, the server has joined as a Kubernetes node. Machines requested directly by an administrator, outside a tenant cluster, skip this milestone.
5. **Ready** - every prior milestone has been reached. This is a single point in time, not a span. A Machine doesn't sit in "ready" before doing anything else. By the time a Machine reaches Ready, the server it claimed is already serving workloads.
6. **Destroyed** - the tenant cluster or administrator no longer needs the Machine, and the platform deletes it.

Teardown is driver-specific. Metal3 cleans the claimed physical server and returns it to the available inventory. KubeVirt deletes the `VirtualMachine`, and Terraform runs its destroy workflow. For the Metal3 driver's `BareMetalHost` states, see [Bare metal server lifecycle](../drivers/bare-metal/overview.mdx#server-lifecycle).

## How a Machine reaches a tenant cluster

<figure>
  <MachineTenantClusterFlow style={{width: '100%', height: 'auto'}} role="img" aria-label="A tenant cluster requests capacity through Private Nodes or Auto Nodes, becoming a NodeClaim that the platform matches to a server" />
</figure>

A tenant cluster requests dedicated capacity through [Private Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/), either directly or automatically through [Auto Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/auto-nodes/). That request becomes a `NodeClaim`, the Kubernetes resource that implements a Machine. The platform selects an eligible node type and driver. The driver claims or creates the underlying capacity, provisions it, and joins it to the tenant cluster as a standard Kubernetes node. Once joined, the Machine reaches Ready.

## Who owns what

| Layer | Owns |
|---|---|
| **vMetal** | Provisioning mechanics, driver dispatch, and the Machine and server lifecycles described above. |
| **vCluster Platform** | Which node types exist, who can request them, and quotas. See [Node types and node providers](./machine-types-and-nodetypes.mdx) and [Manage allowed node types](../../administer/projects/allowed/node-types.mdx). |
| **vCluster** | Requesting and releasing capacity for a tenant cluster through Private Nodes and Auto Nodes. |

## Security and ownership boundaries

Requesting a Machine is governed by project role and node-type restrictions rather than open to every tenant. The properties that shape how it's provisioned are constrained the same way. See [Manage allowed node types](../../administer/projects/allowed/node-types.mdx) for the current access model, and [Production and Security](../drivers/bare-metal/security.mdx#rbac-and-project-isolation) for the full RBAC and tenant-isolation picture on the Metal3 driver.
