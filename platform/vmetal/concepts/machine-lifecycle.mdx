An instance is the customer-facing concept for vMetal's claim on one server (physical or virtual, depending on the driver behind it). In the API, a `NodeClaim` represents that request and tracks its lifecycle. This page describes the instance model at a driver-neutral level, from request through placement, quotas, failure, and release. For quick term definitions, see the [Glossary](../../reference/glossary.mdx).

:::note Not to be confused with Machine
A `Machine` is a separate object: a read-only mirror of one machine in a provider's inventory, distinct from the claim described here. See [Machine inventory](./machine-inventory.mdx).
:::

## Instance and server

"instance" and "server" refer to two different objects with two different lifetimes.

A **server** is the physical or virtual host that a driver hands out. Its lifecycle depends on the driver. Metal3 selects a pre-registered `BareMetalHost`, then cleans and returns that host to inventory after use. Create-on-demand drivers instead create infrastructure for a claim: for example, KubeVirt creates a `VirtualMachine`, and Terraform applies a node template.

An **instance** is the customer-facing concept for one claim on capacity. The platform creates a `NodeClaim` when a cluster or administrator requests that capacity and deletes the `NodeClaim` when the capacity is no longer needed. An instance's identity doesn't outlive the claim. During teardown, the driver either releases reusable inventory or destroys infrastructure that it created for the claim.

This distinction matters because the two objects answer different questions. "Is the underlying infrastructure healthy" is a driver-specific question, answered from resources such as a Metal3 `BareMetalHost`, a KubeVirt `VirtualMachine`, or Terraform output. "Is this instance ready" is a question about the current claim, answered from the `NodeClaim` phase and conditions.

## Instance lifecycle

Every instance, regardless of driver, passes through the same milestones:

<figure>
  <MachineModelLifecycle style={{width: '100%', height: 'auto'}} role="img" aria-label="instance lifecycle from requested through scheduled, provisioned, joined, ready, and destroyed, where joined is satisfied without a worker join for independent and control plane instances" />
</figure>

1. **Requested** - a cluster or an administrator asks for capacity matching a node type, and the platform creates a `NodeClaim` for the instance.
2. **Scheduled** - vMetal selects an eligible node type and driver. The driver either claims existing inventory or creates new infrastructure.
3. **Provisioned** - the driver finishes preparing the capacity, which can include creating a VM, installing an OS, configuring networking, and supplying startup configuration. This condition doesn't prove that cloud-init or the services it starts succeeded inside the OS.
4. **Joined** - for worker capacity on a cluster, the server has joined as a Kubernetes node. For instances requested outside a cluster and instances that run a control plane, no worker join is required, so the platform marks this condition satisfied after provisioning.
5. **Ready** - the platform's required milestones are satisfied. For a worker, that includes joining the cluster. For an independent or control plane instance, `Joined` is satisfied without a worker join, so verify SSH access or cluster API health separately.
6. **Destroyed** - the cluster or administrator no longer needs the instance, and the platform deletes its `NodeClaim`.

Teardown is driver-specific. Metal3 cleans the claimed physical server and returns it to the available inventory. KubeVirt deletes the `VirtualMachine`, and Terraform runs its destroy workflow. For the Metal3 driver's `BareMetalHost` states, see [Bare metal server lifecycle](../drivers/bare-metal/metal3/server-lifecycle.mdx#server-lifecycle).

## How an instance reaches a cluster

<figure>
  <MachineTenantClusterFlow style={{width: '100%', height: 'auto'}} role="img" aria-label="A cluster requests capacity through Private Nodes or Auto Nodes, becoming a NodeClaim that the platform matches to a server" />
</figure>

A cluster requests dedicated capacity through [Private Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/), either directly or automatically through [Auto Nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/auto-nodes/). That request becomes a `NodeClaim`, the Kubernetes resource that represents the instance request and tracks its lifecycle. The platform selects an eligible node type and driver. The driver claims or creates the underlying capacity, provisions it, and joins it to the cluster as a standard Kubernetes node. Once joined, the `NodeClaim` reaches the `Available` phase.

## Instances that run a control plane

An instance can carry a cluster's control plane instead of joining one as a worker. The platform installs vCluster on the provisioned server as a systemd service. The cluster's API server runs there rather than as a workload on another cluster.

These instances reach Provisioned the same way as any other. They differ in ordering. A worker waits for its cluster to be online before provisioning, because it needs a live API server to join. A control plane instance doesn't wait, because it's what brings that API server up.

See [Control plane instances](../deploy/control-plane-machines.mdx).

## Independently provisioned instances

An administrator can request an instance directly, with no cluster attached. The instance goes through the same Requested, Scheduled, and Provisioned milestones, and the same server selection and cleanup. Because there's no cluster to join, the platform marks Joined satisfied after provisioning without running a join operation. What you get is a provisioned server reachable over SSH.

This is the same instance model, not a separate one. The only difference is what the platform appends to the cloud-init it generates. Every instance gets any SSH keys you configured. A worker also gets a Kubernetes join command, and a control plane instance gets the vCluster install script, while an independently provisioned instance gets nothing further.

See [Independently provisioned instances](../deploy/independently-provisioned-machines.mdx) for the walkthrough.

## Where an instance is placed

Drivers that draw from a machine inventory, such as Metal3 and NICo, place an instance on a `Machine` that the node type's `machines.selector` matches. Tenant assignment then narrows that set. Two labels on a `Machine` assign it to a tenant:

- `tenant.vcluster.com/owner` marks the machine as owned by the tenant.
- `tenant.vcluster.com/exclusive-to` assigns the machine exclusively to one tenant. Only a platform admin sets it. A machine can't carry both labels.

A machine with neither label is unassigned. Under the `Assigned` allocation policy, a tenant's instances use only the tenant's own machines. Under `OnDemand`, they use the tenant's machines first, then unassigned ones. An instance never lands on another tenant's machine. See [Machine allocation](./machine-types-and-nodetypes.mdx#machine-allocation) for defaults, configuration, and placement outside a tenant.

KubeVirt reads the same policy but places VMs differently. Under `Assigned`, VMs run only on the tenant's reserved nodes, and a request outside any tenant fails with the reason `TenantRequired`. Under `OnDemand`, VMs run only on nodes that aren't reserved for a tenant.

To place an instance on one specific machine, pin it with `machineRef`. See [Claim a specific machine](./machine-inventory.mdx#claim-a-specific-machine).

## Quotas

Two quotas limit how many instances can exist. A request has to fit both.

    ../../tenants/manage-tenants/create-and-configure-tenants.mdx once #2818 merges to next. */}

The **tenant node type quota**, `spec.nodeTypes.quota.byType` on the Tenant, caps how many instances of each node type a tenant holds across all its projects. It caps on-demand capacity only, so what counts depends on where an instance lands:

- A Metal3, NICo, or KubeVirt node type with the `Assigned` policy isn't limited, because it only draws on capacity assigned to the tenant. Metal3 and NICo node types use `Assigned` unless you set otherwise.
- Under `OnDemand`, an instance on a machine the tenant owns or is exclusively assigned doesn't count. Only instances on unassigned machines count.
- An instance pinned with `machineRef` never counts.
- A node type from a provider without a machine inventory, such as Terraform, counts every instance.

One exception applies under `OnDemand`. The platform checks the quota before it picks a machine, so a request that's over quota waits even when a machine assigned to the tenant is free. To use that machine, pin the instance to it with `machineRef`.

The **project instance quota** caps the number of `NodeClaim` resources in a project, optionally per provider and per user or team. It counts every instance, including instances on machines assigned to the tenant. See [Instance quotas](../../tenants/projects/quotas.mdx#instance-quotas).

The platform enforces the tenant quota in two ways, depending on the request:

- A request that names a node type directly is refused when it's created, with a `quota exhausted` error.
- A request that lets the platform choose the node type, such as one from an Auto Nodes pool, waits as `Pending` with the reason `TenantNodeTypeQuotaExceeded`. It proceeds without any action once a slot frees up.

The platform schedules a tenant's waiting requests one at a time. Requests that name a node type go through oldest first. Requests that let the platform choose have no guaranteed order.

An instance keeps counting against the quota until its `NodeClaim` is fully deleted, including while it's `Failed`. Delete failed instances to free their slots.

## Phases and conditions

A `NodeClaim` has one of three phases. The platform derives the phase from the `Ready` condition, which summarizes the `Scheduled`, `Provisioned`, and `Joined` conditions. The claim's `status.reason` and `status.message` repeat the reason and message of the milestone that isn't met.

| Phase | Meaning |
|---|---|
| `Pending` | A milestone isn't met yet. The platform is still working on it or waiting for something to change. |
| `Available` | Every milestone is met. |
| `Failed` | A milestone failed with an error. A provisioning failure isn't retried, and the claim stays `Failed` until you delete it. A scheduling or teardown failure keeps retrying. See [When provisioning fails](#when-provisioning-fails) and [Release and reclaim](#release-and-reclaim). |

The most common reasons are in the following table. The condition message names the specific node type, machine, or tenant involved.

| Condition | Reason | Phase | What happens next |
|---|---|---|---|
| `Scheduled` | `TenantNodeTypeQuotaExceeded` | `Pending` | The tenant's quota for the node type is used up. Retries every 10 seconds. See [Quotas](#quotas). |
| `Scheduled` | `FailedToSchedule` | `Pending` | No compatible node type has free capacity. Retries every 10 seconds, with no time limit. |
| `Scheduled` | `FailedToSchedule` | `Failed` | Scheduling hit an error, such as a missing node provider. Retries with a growing delay. |
| `Provisioned` | `WaitingForNetworkEnvironment` | `Pending` | Waits until the cluster's network environment is ready. |
| `Provisioned` | `PrivateNodesDisabled` | `Pending` | The cluster doesn't have private nodes enabled. Retries every minute. |
| `Provisioned` | `InsufficientCapacity` | `Pending`, then `Failed` | No eligible machine is free. Waits 30 minutes by default. See [When provisioning fails](#when-provisioning-fails). |
| `Provisioned` | `Provisioning` | `Pending` | The driver is still working. No time limit. |
| `Provisioned` | `ProvisioningError` | `Pending` | The driver returned an error. Retries with a growing delay, up to three minutes apart. |
| `Provisioned` | `InvalidConfiguration`, `MachineNotFound`, `NetworkEnvironmentNotAllowed`, `TenantRequired`, or a driver reason such as Metal3's `HostProvisioningFailed` | `Failed` | Not retried. Fix the cause and replace the instance. |
| `Joined` | `NotJoined` | `Pending` | The server hasn't registered as a node in its cluster yet. |

A node type is chosen once. After the `Scheduled` condition is met, the claim keeps that node type for the rest of its life, even while it waits for capacity.

## When provisioning fails

Most waits have no time limit. A claim waiting for its network environment, for the driver to finish, or for the server to join keeps waiting and reports progress in its conditions.

The wait for a free machine is the exception. When no eligible machine is free, the `Provisioned` condition reports `InsufficientCapacity` and the claim keeps checking. If no machine frees up within 30 minutes of scheduling, the claim moves to `Failed`, and its message starts with `no machine became available within 30m0s`. Time spent waiting for quota doesn't count toward the limit.

To change the limit, set the `machines.vcluster.com/provisioning-wait-timeout` property to a Go duration such as `2h`. You can set it on the node provider, node type, network environment, or `NodeClaim`. An invalid value falls back to 30 minutes, and the condition message says so.

A claim that failed during provisioning isn't retried. Fixing the cause, adding capacity, or raising the timeout doesn't restart it. To recover:

1. Read the reason and message on the `NodeClaim`, and fix the cause.
2. Delete the failed instance in the platform UI, or delete its `NodeClaim`.
3. Request a replacement through the workflow that created the original. For a cluster using Auto Nodes, vCluster records a `PlatformNodeClaimProvisioningFailed` event on the node claim inside the cluster, and its node pool requests the replacement.
4. Confirm that the replacement `NodeClaim` reaches `Available`.

For Metal3 causes and checks, see [Instance stays pending without a server](../drivers/bare-metal/metal3/troubleshooting.mdx#instance-stays-pending-without-a-server).

## Release and reclaim

Deleting a `NodeClaim` starts its teardown. Deleting a cluster deletes its instances too.

1. **Drain.** For a worker that joined a cluster, the platform first deletes the cluster's Node so its workloads evict gracefully, for up to 30 minutes. Control plane instances and instances that never joined skip this step. To skip the drain, set the `vcluster.com/skip-node-drain` annotation on the `NodeClaim`, or click **Force delete**. See [Graceful drain on deprovisioning](./machine-types-and-nodetypes.mdx#node-claims).
2. **Teardown.** The driver releases a server it drew from inventory, or destroys infrastructure it created for the claim. If teardown fails, the claim shows `Failed` with the reason `FailedToDestroy`. The platform keeps retrying every 30 seconds and deletes the `NodeClaim` only after teardown succeeds. Check the driver's resource, such as the `BareMetalHost` or `VirtualMachine`, for the teardown error.
3. **Reclaim.** For a driver with a machine inventory, the platform removes the `machines.vcluster.com/node-claim` annotation from the `Machine` once no claim holds it. The `Machine` is free for another claim once the driver reports the server available again.

Release doesn't change tenant assignment. A machine assigned to a tenant stays assigned after its instance is deleted, and its next instance comes from the same tenant. While an instance holds a machine, the API refuses changes to the machine's tenant assignment. Release the instance first to reassign the machine.

For Metal3, if a host disappears from the inventory while a provisioned instance holds it, the instance moves to `Failed` with the reason `MachineNotFound`.

## Who owns what

| Layer | Owns |
|---|---|
| **vMetal** | Provisioning mechanics, driver dispatch, and the instance and server lifecycles described above. |
| **vCluster Platform** | Which node types exist, who can request them, tenant assignment, and quotas. See [Node types and node providers](./machine-types-and-nodetypes.mdx) and [Manage allowed node types](../../tenants/projects/allowed/node-types.mdx). |
| **vCluster** | Requesting and releasing capacity for a cluster through Private Nodes and Auto Nodes. |

## Security and ownership boundaries

Requesting an instance is governed by role permissions and Tenant and Project resource boundaries. The properties that shape how it's provisioned are constrained the same way. The default Project Admin role can create instances directly. The default Project User role can only watch them, though a cluster that user creates still requests instances through Auto Nodes. See [Manage allowed node types](../../tenants/projects/allowed/node-types.mdx) for Project-level controls, and [Production and Security](../drivers/bare-metal/metal3/security.mdx#rbac-and-resource-boundaries) for the full RBAC and resource-boundary model on the Metal3 driver.
