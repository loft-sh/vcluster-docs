vCluster Platform holds the license for a deployment. The license determines which features are enabled and sets limits on how many of certain resources you can create.

Tenant clusters don't hold licenses of their own. They read a list of enabled features from the platform. Every licensing question therefore comes down to how the platform obtained its license and whether tenant clusters can reach the platform to read features from it.

This page explains how that works, what each component caches, and how licensing degrades when it becomes unavailable. For the setup procedures themselves, see the air-gapped guides for an [offline license key](../install/air-gapped/with-offline-license-key.mdx) or an [offline license server](../install/air-gapped/with-offline-license-server.mdx).

## How the platform obtains its license

The platform selects one of three licensing modes at startup, based on environment variables set on the platform deployment.

| Mode | Enabled by | Source of the license |
| --- | --- | --- |
| Online | Default, no configuration needed | `https://admin.loft.sh/license/v2` |
| Offline license key | `LICENSE_KEY` environment variable | The key itself, a signed token verified locally against a built-in public key |
| Offline license server | `LICENSE_SERVER` environment variable | An in-cluster license server that serves the same API as the hosted one |

Offline license key mode never contacts a license server. The platform decodes and verifies the key in-process, so use this mode when no egress is possible at all.

A fourth variable, `LICENSE_TOKEN`, doesn't change the mode. It supplies a static token that the platform sends when it requests a license, so the instance doesn't need interactive activation. The platform logs `LICENSE_TOKEN env var is set, platform activation is not required` at startup when it's present.

To find out which mode a running platform is in, see [Inspect and debug licensing](#inspect-and-debug-licensing).

### Instance identity

In online and offline license server modes, the platform identifies itself to the license server with:

- The UID of the `kube-system` namespace in the control plane cluster.
- A short-lived token signed with the private key from the `loft-cert` Secret, sent along with that Secret's certificate.

This pairing ties a license to one platform instance. If the `loft-cert` Secret is lost, the platform generates a new identity and the existing license no longer matches it. Preserve that Secret across reinstalls and migrations. See [Restore license](../maintenance/backup-restore/preserve-license.mdx) for the backup and restore procedure.

The `loft-license-cache` Secret isn't part of the platform's identity. It holds a cached copy of the license response and the platform rebuilds it automatically, so it doesn't need to be migrated.

## How tenant clusters receive features

A tenant cluster reads its enabled features from the platform rather than from a license server. The control plane detects which mechanism is available at startup and picks one.

| Type | Detected when | Features come from |
| --- | --- | --- |
| Online | A platform host and access key are both available | The platform's management API `Features` endpoint |
| Standalone | `controlPlane.standalone.enabled` is set | `Feature` resources in the control plane cluster |
| In-cluster API | `Feature` resources exist in the control plane cluster and the tenant cluster has RBAC to list them | `Feature` resources in the control plane cluster |
| Offline | A key is set but no platform host | A signed offline license key, verified locally |
| None | Nothing above is detected | No Enterprise features are enabled |

The control plane logs the type it chose at startup, for example `detected license type {"licenseType": "Online"}`.

Online is the common case. By default, the control plane reads the platform connection from the `vcluster-platform-api-key` Secret in the tenant cluster's host namespace. To point it at a different Secret, set `platform.apiKey.secretName` and `platform.apiKey.namespace` in `vcluster.yaml`.

Within whichever Secret applies, the control plane resolves the access key in this order.

1. The `LICENSE` environment variable.
2. The `LOFT_PLATFORM_ACCESS_KEY` environment variable.
3. The only key in the Secret, if the Secret holds exactly one key.
4. The `license` key in the Secret, then the `accessKey` key.

It resolves the host from `LOFT_PLATFORM_HOST` first, then from the Secret's `host` key.

:::warning Use an address the pod can reach
The host recorded in the Secret must be reachable from inside the control plane cluster. Logging in through a port-forward records a `localhost` address that the tenant cluster pod can't reach, so feature retrieval fails. See [Resolve Pro feature license errors](/docs/vcluster/troubleshoot/pro-feature-license-error).
:::

## Required network access

Only the platform contacts the license server. Neither connected cluster agents nor tenant clusters do.

| Source | Destination | Protocol and port | Purpose |
| --- | --- | --- | --- |
| Platform pods | `admin.loft.sh` | HTTPS, TCP `443` | License retrieval every 6 hours, and usage snapshots every 15 minutes |
| Tenant cluster control plane pods | Platform endpoint | HTTPS, TCP `443` | Feature retrieval and registration |
| Connected cluster agents | None for licensing | Not applicable | Agents don't perform license validation |

In offline license key mode, no egress to `admin.loft.sh` is required at all. In offline license server mode, the platform reaches the in-cluster license server instead, at the address given in `LICENSE_SERVER`.

The platform Service listens on port `443` and forwards to port `10443` on the platform pods. Kubernetes NetworkPolicy matches the pod port rather than the Service port, so an egress rule targeting platform pods directly has to allow `10443`.

The tenant cluster path is the same connection used for the rest of platform communication, so it needs no licensing-specific firewall rules. For the full connectivity model, see [Platform communication and connectivity](./platform_communication.mdx).

## Cache and refresh behavior

Every component caches what it last retrieved, so a licensing outage doesn't immediately take the deployment down.

| Component | Refresh trigger | Cache location | Cache lifetime |
| --- | --- | --- | --- |
| Platform in online or license server mode | Every 6 hours | `loft-license-cache` Secret in the platform namespace | Reloaded at startup, with a 7-day grace period after retrieval starts failing |
| Platform in offline license key mode | Re-evaluated locally every minute | None needed, the key is in the environment | Until the key expires, plus a 30-day grace period |
| Tenant cluster, online | At startup, and whenever the credentials Secret changes | `<vcluster-name>-features-list` Secret in the host namespace, encrypted | 7 days |
| Standalone control plane | At startup, and whenever the credentials Secret changes | `platform/feature-cache.json` in the data directory | Doesn't expire |
| Tenant cluster, in-cluster API | Polled with backoff starting at 30 seconds, capped at 5 minutes | None | Not applicable |
| Tenant cluster, offline | Re-checked locally every hour | None needed, the key is in the environment | Until the key expires |

The online tenant cluster path isn't polled. The control plane retrieves features at startup and then only when the credentials Secret changes. A license change made in the platform reaches a running tenant cluster on the next control plane restart, not on a timer.

The platform's one-minute cycle in offline license key mode doesn't contact anything. It re-reads current resource usage, so limits are enforced against live counts.

The tenant cluster feature cache is encrypted with a key derived from the vCluster Service UID. A tampered Secret therefore can't grant features the platform never returned.

## What happens when licensing is unavailable

Behavior depends on which component lost access and for how long.

**The platform can't reach the license server.** It keeps running on the cached license and retries every 6 hours. If no retrieval succeeds within 7 days of the last successful one, the platform process exits rather than running unlicensed.

**The platform's offline license key is near or past expiry.** Starting 90 days before expiry, the platform raises an expiration warning announcement. After the key expires, a 30-day grace period follows during which the platform keeps working. Once that grace period ends, the instance blocks all create requests.

**The platform is over a resource limit.** Creating more of that resource is blocked while usage stays above the limit. Deleting enough of the resource clears the block automatically. In offline license key mode, the platform evaluates limits itself and raises a warning announcement once usage passes 90%. In online mode, the license server decides which limits apply and which announcements to return.

**A tenant cluster can't reach the platform.** It falls back to its cached feature list, which stays valid for 7 days. A tenant cluster that has never retrieved features and has no cache fails at startup instead of falling back.

**A tenant cluster's own offline license key expires.** The control plane warns for the last 30 days and then exits once the key expires. This path has no grace period, unlike the platform's offline key mode.

**The licensed feature set changes.** The platform restarts itself to apply the new set.

Expiration, limit, and feature warnings surface in the platform UI. See [Inbox](../administer/inbox.mdx).

## Inspect and debug licensing

### In the platform

View the current license in the platform UI under **Admin > Platform Config > License and Billing**.

Retrieve the same data through the API. This reports the license the platform currently holds, without contacting the license server.

```bash title="Read the platform's current license"
kubectl get licenses.management.loft.sh license -o yaml
```

To make the platform retrieve a fresh license first, add the `extended=true` query parameter. It's a URL parameter rather than a field, so `kubectl get` can't set it and the request has to go through `--raw`.

```bash title="Force a license refresh, then read the result"
kubectl get --raw '/apis/management.loft.sh/v1/licenses/license?extended=true'
```

Confirm which license server the platform is using. The platform logs this once at startup, so this also tells you which mode it's in.

```bash title="Check the configured license server"
kubectl logs -n vcluster-platform -l app=loft | grep "Using license server"
```

Check the cached license and the instance identity Secrets.

```bash title="Inspect licensing Secrets"
kubectl get secret loft-license-cache -n vcluster-platform -o jsonpath='{.data.updatedAt}' | base64 -d
kubectl get secret loft-cert -n vcluster-platform
```

The `updatedAt` value is the timestamp of the last successful retrieval. The 7-day grace period is measured from it.

Look for retrieval failures in the platform logs.

```bash title="Check for license retrieval errors"
kubectl logs -n vcluster-platform -l app=loft | grep -i "license request failed\|error retrieving license"
```

### In a tenant cluster

Confirm which license type the control plane selected, and which features it enabled.

<InterpolatedCodeBlock
  code={'kubectl logs -n [[VAR:NAMESPACE:my-namespace]] [[VAR:NAME:my-vcluster]]-0 | grep -A5 "detected license type\\|Enabled features"'}
  language="bash"
  title="Check the tenant cluster's license type and features"
/>

A healthy online tenant cluster logs the host it connected to, followed by the features it enabled.

```text title="Startup log on a licensed control plane"
loader/loader.go  Using online license with host  loft.vcluster-platform
online/license.go  Enabled features:
online/license.go  dra-sync
```

Confirm the credentials Secret and the feature cache both exist.

<InterpolatedCodeBlock
  code={'kubectl get secret vcluster-platform-api-key -n [[VAR:NAMESPACE:my-namespace]]\n' +
        'kubectl get secret [[VAR:NAME:my-vcluster]]-features-list -n [[VAR:NAMESPACE:my-namespace]]'}
  language="bash"
  title="Verify the credentials Secret and feature cache"
/>

The feature cache is encrypted and can't be read directly. Its presence and age are what matter, because the cache expires 7 days after it was written.

A control plane can crashloop with an error naming a feature the license doesn't allow. The cause is usually a missing credentials Secret rather than a plan limitation. See [Resolve Pro feature license errors](/docs/vcluster/troubleshoot/pro-feature-license-error).
