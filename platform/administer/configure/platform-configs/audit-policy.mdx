Audit levels are preconfigured audit policies. Use this reference to see exactly what each level records, which requests the built-in rules always exclude or limit to metadata, and how to write a custom policy. To turn on auditing and choose a level, see [Audit logging](./audit.mdx).

## Request and response payload storage

Audit levels and custom policies both determine payload storage through one of four granularity settings. `Request` stores the request payload. `RequestResponse` also stores the response payload. See [Audit policy](#audit-policy) for the full list.

The platform stores payloads for resource requests only. Long-running requests, such as log streaming, never store payloads. Requests to create sensitive resources, such as access keys and cluster registrations, keep metadata-only events on every level. See [Default policy exclusions](#default-policy-exclusions) for the full list of affected resources and why. Independently of the level or policy, the platform never stores credentials from a payload. See [Credentials in payloads](#credentials-in-payloads).

The platform always stores payloads as JSON:

- Payloads that arrive as plain JSON are stored unchanged.
- Gzip-compressed request and response bodies are stored in their decompressed form.
- Payloads sent in the Kubernetes Protobuf format are converted to their JSON equivalent for known Kubernetes API types. The stored payload matches what a JSON client would have sent.

### Payload size limit

The platform captures at most 2 MiB per request or response payload. It doesn't store payloads above this limit.

### Omitted payloads

When the platform can't store a payload, it keeps the audit event with all of its metadata but leaves out the payload. The event then carries an annotation that names the omission reason:

- `audit.platform.vcluster.com/request-object-omitted` for the request payload
- `audit.platform.vcluster.com/response-object-omitted` for the response payload

The following reasons can appear as annotation values:

| Reason | Description |
|--------|-------------|
| `truncated` | The payload exceeded the capture limit, so the platform captured only a partial copy. |
| `too-large` | The payload exceeded the capture limit after decompression or conversion to JSON. |
| `decode-failed` | The platform couldn't decompress or decode the payload. |
| `unsupported-encoding` | The payload used a content encoding or media type that the platform can't convert to JSON. |
| `invalid-json` | The payload wasn't valid JSON and not in any recognized format. |
| `sensitive` | The resource carries credentials in its payload, so the platform never stores it. See [Credentials in payloads](#credentials-in-payloads). |
| `redaction-failed` | The platform couldn't find the credential fields of a redacted resource in the payload, for example in a JSON patch. |

### Credentials in payloads

Some request and response payloads carry credentials, such as access keys, tokens, passwords, and Kubernetes Secret data. The platform never writes these credentials to an audit event. It applies this protection after the audit policy picks the granularity of an event. The protection holds at every audit level and under a custom `policy.rules` list.

The platform handles the payload of each resource in one of three ways:

- **Omitted**: The platform stores no payload. The event keeps all of its metadata and carries the [omission annotation](#omitted-payloads) with the reason `sensitive`.
- **Redacted**: The platform stores the payload, but replaces the value of each credential field with `<REDACTED>`. A field that holds a map keeps its keys and loses its values.
- **Stored**: The payload carries no credentials, and the platform stores it unchanged.

An event with an omitted payload looks like this:

```yaml title="Audit event with an omitted response payload"
annotations:
  audit.platform.vcluster.com/response-object-omitted: sensitive
objectRef:
  apiGroup: management.loft.sh
  resource: clusters
  subresource: accesskey
verb: get
```

#### Omitted resources

The platform omits the request and response payloads of these resources:

| Resource | API group | Payload carries |
|---|---|---|
| `clusters/accesskey`, `virtualclusterinstances/accesskey`, `virtualclusterinstances/nodeaccesskey` | `management.loft.sh` | Agent and node access keys. |
| `virtualclusterinstances/kubeconfig`, `virtualclusterinstances/joinscript`, `virtualclusterinstances/standalone` | `management.loft.sh` | Kubeconfigs, bootstrap tokens, and private keys. |
| `virtualclusterinstances/externaldatabase`, `virtualclusterinstances/snapshotcredentials`, `virtualclusterinstances/observabilityconnector` | `management.loft.sh` | Database passwords, storage credentials, and metrics-writer tokens. |
| `configs`, `tenants/config`, `oidcclients` | `management.loft.sh` | SSO and OIDC client secrets. |
| `connectors` | `management.loft.sh` | Credentials for the external systems they connect to. |
| `users/profile` | `management.loft.sh` | A new password. |
| `redirecttokens`, `directclusterendpointtokens`, `ingressauthtokens`, `selves` | `management.loft.sh` | Tokens. |
| `apps/credentials` | `management.loft.sh` | Resolved project secret values, such as chart registry passwords. |
| `stackinstances/outputs` | `management.loft.sh` | Stack output values, including sensitive outputs. |
| `backups`, `backups/apply` | `management.loft.sh` | A raw copy of all platform objects. |
| `convertvirtualclusterconfig` | `management.loft.sh` | A full vCluster config. |
| `nodeproviders/exec` | `management.loft.sh` | Terraform state with the node join token. |
| `osimages/upload` | `management.loft.sh` | Upload targets that grant write access to the image. |
| `kiosk` | `management.loft.sh` | An embedded access key. |
| `metal3bmcs/redfish` | `cluster.loft.sh` | BMC passwords and session tokens. |

A resource of the `management.loft.sh` or `cluster.loft.sh` API groups that the platform doesn't know is also omitted. Resources of other API groups, other than core Secrets, are stored unchanged.

#### Redacted resources

The platform redacts the credential fields of these resources and stores the rest of the payload:

| Resource | API group | Redacted fields |
|---|---|---|
| `secrets` and its subresources, sent through the platform proxies or the agent | core (`""`) | `data`, `stringData` |
| `projectsecrets` | `management.loft.sh` | `spec.data` |
| `projects`, `projects/status` | `management.loft.sh` | Vault authentication token |
| `ownedaccesskeys`, `resetaccesskeys`, `users/accesskeys`, `teams/accesskeys` | `management.loft.sh` | Access key value, identity connector data, and OIDC tokens |
| `apps`, `appinstances`, `projects/chartinfo` | `management.loft.sh` | Chart passwords, Helm values, manifests, scripts, and parameter values |
| `spacetemplates`, `spaceinstances`, `virtualclustertemplates`, `virtualclusterinstances`, `projects/templates`, `rendervirtualclustertemplates`, `registervirtualclusters` | `management.loft.sh` | Chart passwords, Helm values, objects, parameter values, and the rendered objects in the status |
| `stacktemplates`, `stackinstances`, `argocdapplications`, `argocdapplicationtemplates` | `management.loft.sh` | Parameter values, Helm values, and plugin and Jsonnet variables |
| `nodeproviders`, `nodeproviders/status`, `projects/nodetypes`, `machineconfigtemplates` | `management.loft.sh` | Helm values, Terraform and machine templates, and cloud-init templates |
| `storageaccounts`, `storageprofiles`, `storagevolumes`, and their `status` subresources | `management.loft.sh` | Weka users, tenants, and file systems |
| `licenses/request` | `management.loft.sh` | `status.output` |
| `events`, `agentauditevents` | `management.loft.sh` | The request and response payloads that stored audit events embed |

For every redacted resource, the platform also replaces the `kubectl.kubernetes.io/last-applied-configuration` annotation, because `kubectl apply` writes a full copy of the object, credentials included, into it.

For omitted and redacted resources, the platform also replaces the messages of a failure `Status` with `<REDACTED>`, because a validation error can repeat the rejected value.

The agent applies the same protection to the events it records and sends to the platform. An agent on an older version keeps recording Secret data until you upgrade it.

:::warning Review audit events written before the fix
vCluster Platform versions before 4.12.8 and 5.0.1 stored these credentials in audit events. Audit stores, log files, and webhook targets that hold events from those versions can contain access keys, tokens, passwords, and Secret data. Review who can read them, and purge the events you don't need. Rotate the credentials that someone could have read, starting with cluster access keys. See [Persist audit logs](./audit.mdx#persist-audit-logs) for where the platform stores events.
:::

## Audit policy

Audit policy is a more complex alternative to audit levels, letting you define exact rules about what events should be recorded and what data they should include. When an event is processed, it's compared against the list of rules in order. The first matching rule sets the audit granularity of the event. The defined audit granularity options are:

- `None`: Don't log events that match this rule.
- `Metadata`: Log request metadata (requesting user, timestamp, resource, verb, and so on) but not request or response body.
- `Request`: Log event metadata and request body but not response body. This doesn't apply for non-resource requests.
- `RequestResponse`: Log event metadata, and request and response bodies. This doesn't apply for non-resource requests.

:::warning Custom rules replace the defaults entirely
Setting a non-empty `policy.rules` list under `config.audit` replaces the resolved default policy outright, and the platform then ignores the `level` field. None of the [default policy exclusions](#default-policy-exclusions) apply automatically. Authentication events and connector requests then follow your rules too, so a policy without the built-in rules can drop sign-in events or record connector request bodies. Start from the [default rules for a level](#default-policy-rules-by-level) and add to them, rather than writing a custom policy from scratch. An empty `rules: []` list doesn't count as a custom policy. The platform still resolves and applies the configured level's defaults. A custom policy doesn't turn off [credential protection](#credentials-in-payloads). Credentials stay out of payloads, whatever the rules say.
:::

An example policy that catches all requests:

```yaml title="Example audit policy in values.yaml"
config:
  audit:
    enabled: true
    policy:
      rules:
        - level: Metadata
          omitStages:
            - RequestReceived
```

See the [complete policy reference](../../../api/resources/config.mdx#status-audit-policy).

## Default policy exclusions

Before a request reaches an audit level's own rules, six built-in rules run first, in this order. Because the platform uses the first matching rule, these built-ins take priority over anything the level would otherwise log. They apply to all four audit levels.

These rules decide only whether an event is logged and at which granularity. Which payloads may hold credentials is decided separately, at every level and under a custom policy. See [Credentials in payloads](#credentials-in-payloads).

1. [Never logged](#never-logged)
1. [Authentication activity](#metadata-only-for-authentication-activity)
1. [Tenant configuration and connectors](#metadata-only-for-tenant-configuration-and-connectors), as two separate rules
1. [Sensitive data](#metadata-only-for-sensitive-data)
1. [Long-running requests](#metadata-only-for-long-running-requests)

### Never logged

The platform never logs these requests, at any level, including level 4:

| Resource | API group | Why |
|---|---|---|
| `selfsubjectaccessreviews`, `subjectaccessreviews` | any | Permission checks the UI and CLI issue continuously to decide what to show. They aren't an action on a resource, and logging them would flood the audit log. |
| `agentauditevents` | `management.loft.sh` | The endpoint agents use to send their own audit events back to the platform (see [Audit logging for Regional Cluster Endpoints](./audit.mdx#audit-logging-for-regional-cluster-endpoints)). Logging it would create an audit event about receiving an audit event. |
| `licensetokens`, `directclusterendpointtokens`, `ingressauthtokens` | `management.loft.sh` | Internal tokens validated on nearly every request. |
| `selves` | `management.loft.sh` | The endpoint the UI and CLI call to resolve the current user, requested on nearly every page load. |
| `virtualclusterinstances/kubeconfig` | `management.loft.sh` | Retrieving the kubeconfig for a cluster. |

:::info No audit record of kubeconfig retrieval
Because `virtualclusterinstances/kubeconfig` is on the never-logged list, there's no audit record of who retrieved a cluster's kubeconfig, or when, at any level. To get a `Metadata` record of these requests instead (who, when, which cluster, without the returned credentials), remove `virtualclusterinstances/kubeconfig` from the never-logged resources in a [custom policy built from the defaults](#default-policy-rules-by-level). The [sensitive data rule](#metadata-only-for-sensitive-data) then takes over and audits it at `Metadata`, since it already lists this resource.
:::

### Metadata-only for authentication activity

For `create` requests only, the platform logs sign-in events, and the access keys a sign-in creates, at `Metadata` regardless of the configured level. Both carry credentials in their bodies. See [Authentication events](./audit-events.mdx#authentication-events) for what these events contain.

| Resource | API group | Why |
|---|---|---|
| `users/login` | `management.loft.sh` | The sign-in request carries a password or an SSO token. |
| `accesskeys` | `storage.loft.sh` | The access key a successful sign-in creates. The key value is never recorded. |

### Metadata-only for tenant configuration and connectors

These are two separate rules, one for each resource. For every verb, including reads, the platform logs these resources at `Metadata`. Reads are recorded too, even at level 1, which otherwise drops reads.

| Resource | API group | Why |
|---|---|---|
| `tenants/config` | `management.loft.sh` | The request and response carry decrypted per-tenant SSO client secrets. Changes to a tenant's sign-in configuration still leave a record of who made them. |
| `connectors` | `management.loft.sh` | Connector requests and responses can carry credentials for the external systems they connect to. |

### Metadata-only for sensitive data

For `create` requests only, the platform always logs these resources at `Metadata`, never `Request` or `RequestResponse`, regardless of the configured level:

| Resource | API group | Why |
|---|---|---|
| `ownedaccesskeys`, `resetaccesskeys` | `management.loft.sh` | The response contains the access key value. |
| `clusters` | `management.loft.sh` | Cluster registration includes a kubeconfig or connection token in the request. |
| `users/profile` | `management.loft.sh` | The request can contain a new password. |
| `virtualclusterinstances/kubeconfig` | `management.loft.sh` | The response contains a working kubeconfig. This rule only applies if you remove the resource from the never-logged list above, since that rule matches first. |
| `virtualclusterinstances/snapshotcredentials` | `management.loft.sh` | The response contains sensitive storage credentials. |
| `virtualclusterinstances/observabilityconnector` | `management.loft.sh` | The response contains the metrics-writer token a cluster uses to reach the [Fleet Observability](../../../fleet-operations/observability/overview.mdx) write gateway. |
| `osimages/upload` | `management.loft.sh` | The response contains upload targets, each of which grants write access to the image until it expires. |
| `metal3bmcs/redfish` | `cluster.loft.sh` | Proxied BMC requests and responses carry BMC account passwords and session tokens. |

This keeps the event auditable (who did it, when, on which object) without writing the credential itself into the audit log, which is typically retained longer and read more widely than the underlying secret store.

### Metadata-only for long-running requests

| Resource | API group | Why |
|---|---|---|
| `pods/log`, `pods/exec`, `pods/portforward` | core (`""`) | Streaming requests inside a cluster or connected cluster. There's no discrete response body to capture, and exec or port-forward would mean logging the interactive session traffic. |
| `virtualclusterinstances/log`, `appinstances/log` | `management.loft.sh` | Same reasoning, for log streaming through the platform API. |
| `metal3bmcs/console` | `cluster.loft.sh` | Interactive serial console sessions to a bare metal server's BMC. |

## Default policy rules by level

Each audit level resolves to a fixed list of policy rules, evaluated in order, where the first match sets an event's granularity. Copy the rules for a level below as a starting point for a custom policy, then add, remove, or reorder rules to fit your needs. All four levels start with the same six rules, covered in [Default policy exclusions](#default-policy-exclusions), followed by level-specific rules for everything else.

A `Request` or `RequestResponse` rule doesn't store credentials. The platform omits or redacts them after the rule matches, as described in [Credentials in payloads](#credentials-in-payloads).
