<GlossaryTerm term="vcluster">vCluster</GlossaryTerm> Platform offers three paths to fleet-wide metrics, each solving a different
problem well. They aren't interchangeable: each stamps a different set of identity labels,
so a dashboard or alert built for one won't return data on another. This page helps you
pick the right one before you build anything on top of it.

## Decide with four questions

1. Do different tenants or customers need dashboards scoped to only their own metrics, with Platform enforcing that boundary? If yes, use [Fleet Observability](../observability/overview.mdx). It's the only path with authenticated writes and scoped, per-tenant reads.
2. Are your tenant clusters on vCluster Standalone, or does vCluster Platform run on embedded Kubernetes (the mode backing the external-database and multi-region features)? If yes, Fleet Observability's bundled Argo CD collector deploy doesn't cover you (Standalone still works with a manual collector config; embedded Kubernetes can't run the gateway at all) — use [Fleet monitoring with OpenTelemetry](./fleet-monitoring-otel.mdx) or [Aggregating Metrics](./aggregating-metrics.mdx) instead.
3. Do you need GPU utilization or fault observability? If yes, use [Fleet Observability](../observability/overview.mdx). DCGM and NVSentinel have no equivalent in the other two guides.
4. Do you want a documented Shared Nodes troubleshooting deep-dive, a golden-signals PromQL query library, and ready-made Grafana dashboards out of the box? If yes, use [Fleet monitoring with OpenTelemetry](./fleet-monitoring-otel.mdx). If none of the above apply and you just want the fastest path to a working dashboard, use [Aggregating Metrics](./aggregating-metrics.mdx).

:::info Shared Nodes support isn't a differentiator here
All three paths correctly handle Shared Nodes tenant clusters, each through the same
underlying pattern: a collector that scrapes its own local node directly rather than
discovering scrape targets through the Kubernetes API, so none of them are affected by
vCluster's kubelet virtual-IP proxying. See
[Prometheus node metrics on shared nodes](./prometheus-shared-nodes.mdx) for the
background on why that proxying matters for hand-rolled Prometheus setups. Pick a path
based on the questions above, not on Shared Nodes support.
:::

## Compare the three paths

<!-- vale off -->
| | Fleet Observability | Fleet monitoring with OpenTelemetry | Aggregating Metrics |
|---|---|---|---|
| Identity labels | `vcluster_platform_*`, authenticated | `vcluster_*`/`cluster`, self-reported | `loft_*`, self-reported |
| Read access control | Scoped per tenant or cluster, Platform-authorized | None, any reader sees all data | None, any reader sees all data |
| GPU observability | DCGM, NVSentinel | Not covered | Not covered |
| Requires Argo CD for the bundled deploy path | Yes (manual config available for Standalone) | No | No |
| Runs on embedded Kubernetes platform deployments | No | Yes | Yes |
| Golden-signal PromQL library and ready dashboards | A handful of example queries | Full latency/traffic/errors/saturation library, two downloadable Grafana dashboards | A few example queries, one bundled dashboard |
| Setup effort | Gateway, connector, access keys, then collectors | Register and deploy per-tenancy-model collector Apps | One built-in collector App plus standalone Prometheus/Grafana |
<!-- vale on -->

## Examples

- **A provider giving different customer teams their own Grafana view of only their tenant clusters** needs Platform-enforced scoping. Use Fleet Observability.
- **An internal platform team running vCluster Standalone with no Argo CD, wanting one shared internal dashboard** can't use Fleet Observability's bundled deploy path. Use Fleet monitoring with OpenTelemetry or Aggregating Metrics, depending on how much Shared Nodes troubleshooting depth and dashboard tooling you want out of the box.
- **A GPU-heavy fleet that needs to catch node faults before they take down inference jobs** needs NVSentinel. Use Fleet Observability.
- **A small internal team doing a quick proof of concept before committing to a monitoring stack** doesn't need scoped access or GPU support yet. Use Aggregating Metrics, and revisit this page once real requirements show up.
