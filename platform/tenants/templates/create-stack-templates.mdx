A Stack template defines applications that vCluster Platform deploys as one unit. It also defines the order in which those applications become ready. Use a Stack when applications have dependencies, need health gates, or pass values to later tasks. Each application is a task, tasks declare which other tasks they wait for, and the platform rolls them out in that order.

A `StackTemplate` is a reusable, cluster-scoped blueprint. A `StackInstance` applies that blueprint to one cluster or control plane cluster. Each task creates either an AppInstance or an ArgoCDApplication.

## Understand licensing

Stacks don't have a separate license feature. Each task requires the feature for the resource it creates:

- An App task requires the Apps feature.
- An Argo CD Application task requires the Argo CD Integration feature.
- A Stack that mixes task types requires both features.

Both features are available on every plan, including the free plan. If a task's feature is ever removed from the active plan, the StackInstance remains blocked with the `FeatureNotAllowed` reason. Learn more about [Apps](./what-are-apps.mdx) and the [Argo CD integration](../../integrations/gitops-cicd/argocd/overview.mdx).

## Create a Stack template in the UI

<Flow id="create-stack-template-ui">
  <Step>
    Go to <NavStep>Tenant Management > Stacks & Apps</NavStep>, and select the **Stacks** tab.
  </Step>
  <Step>
    Click <Button>Create Stack Template</Button>.
  </Step>
  <Step>
    Enter a name, display name, and description for the template.
  </Step>
  <Step>
    Add App or Argo CD Application tasks. Configure dependencies between tasks in the graph.
  </Step>
  <Step>
    Add parameters and published outputs when the Stack needs configurable or returned values.
  </Step>
  <Step>
    Click <Button>Create Stack Template</Button>.
  </Step>
</Flow>

You can also apply the resource through the management API using the **YAML** editor.

Each template in the list has **Edit**, **Duplicate**, and **Delete** actions, shown when you have the `update`, `create`, and `delete` permissions for them. A template you can't edit shows **View** instead of **Edit**. Certified Stack templates are read-only and can't be deleted. Deleting a template leaves existing StackInstances running, but a StackInstance that references it reports `TemplateNotFound`.

Tenant users can't author StackTemplates. A tenant consumes only the templates that its `templates` capability grants, and the **Stacks & Apps** page is hidden from tenant users.

## Define a stack template

The following example deploys a database App before an API App. Create the referenced `postgresql` and `example-api` Apps before you create this template.

```yaml title="stack-template.yaml"
apiVersion: management.loft.sh/v1
kind: StackTemplate
metadata:
  name: example-platform
spec:
  displayName: Example application platform
  description: Deploys a database before the API that uses it.
  parameters:
    - variable: databaseStorage
      label: Database storage
      description: Persistent storage allocated to the database.
      type: string
      defaultValue: 10Gi
  tasks:
    - name: database
      app:
        templateRef:
          name: postgresql
        parameters:
          storage: "{{ .Values.databaseStorage }}"
    - name: api
      # Wait until the database AppInstance reports Healthy.
      dependsOn:
        - database
      timeout: 20m
      app:
        templateRef:
          name: example-api
```

Apply the template through the vCluster Platform management API:

```bash
vcluster platform connect management
kubectl apply -f stack-template.yaml
```

Tasks without dependency edges can run concurrently. A dependent task starts only after every task in `dependsOn` becomes healthy. The following sections explain the task, parameter, and output syntax used in this example in detail.

## Configure tasks

Give each task a unique DNS-label-safe `name`. A duplicate name is rejected when the Stack is applied. A Stack supports up to 20 tasks. Each task can set its own `timeout`. A task without one uses the Stack's `defaults.taskTimeout`, or 10 minutes if that isn't set either. Set exactly one task type:

- `app` creates an AppInstance.
- `argoCDApplication` creates an ArgoCDApplication.

Within the selected type, set either an inline `template` or a reusable `templateRef`. Don't set both. Parameters are valid only with `templateRef`. They pass through to the referenced template.

An inline App must deploy exactly one of a chart, manifests, or a bash script. Setting more than one, or none, is rejected.

### Helm release names

An `app` task generates a Helm release name from the task name and a hash, and the generated name always fits Helm's 53-character limit. An inline App task can set its own release name in `app.template.spec.releaseName`. An explicit release name must follow these rules:

- It must be a valid DNS subdomain of at most 53 characters.
- `app.template.spec.defaultNamespace` must also be set.
- It can't contain output references, because the release is claimed before any output is captured.
- Two `app` tasks in one Stack can't deploy the same release into the same namespace.

After a task deploys, its release can't move. Changing `releaseName` or `defaultNamespace` on a deployed inline task fails the task with `ReleaseIdentityChanged`. Revert the change, or recreate the child.

### Chart credentials from project secrets

A chart can read its repository credentials from a project secret, through `usernameRef.projectSecretRef` or `passwordRef.projectSecretRef`. Whoever saves an App, or a StackTemplate with inline App tasks, must have `get` on each project secret the chart newly references. The same check applies when a referenced secret is sent to a different repository URL or chart. Installing a Stack doesn't require access to the secret.

When a chart in a StackTemplate uses a project secret, the chart's `repoURL` and the secret reference's `project`, `name`, and `key` can't contain parameters or outputs. An inline StackInstance template checks both the caller and the StackInstance owner for access to the secret.

This task uses a reusable ArgoCDApplicationTemplate:

```yaml
tasks:
  - name: workloads
    argoCDApplication:
      templateRef:
        name: application-workloads
      parameters:
        environment: production
```

:::note
The Argo CD connector must be enabled before an Argo CD Application task can become healthy. See [Connect Argo CD](../../integrations/gitops-cicd/argocd/connect-argocd.mdx).
:::

There's no field to skip a task based on a parameter. A Stack always resolves its full task set. To make a task a no-op under some condition, interpolate the `templateRef` name so it points at an App or ArgoCDApplicationTemplate that does nothing:

```yaml
- name: gpu
  app:
    templateRef:
      name: 'gpu-operator{{ if eq .Values.gpuProvider "gke" }}-skip{{ end }}'
```

## Pass parameters to tasks

Declare optional parameters under `spec.parameters`. Tasks read their values with `{{ .Values.<variable> }}`. A parameter declaration renders as a labeled form field in the UI, with a default value, and can enforce validation such as `required`, a `min`/`max` range, or a `validation` regular expression.

Values that don't have declarations are still available to tasks. However, vCluster Platform can't validate those values or supply defaults.

## Pass outputs between tasks

Each output captures one scalar value from a Secret or namespaced Kubernetes resource. A later task reads the value with `{{ .Outputs.<task>.<output> }}` and must list the source task in `dependsOn`. See [Template values and outputs in Stacks](./use-go-template.mdx#template-values-and-outputs-in-stacks) for more Go template examples.

```yaml
tasks:
  - name: database
    app:
      templateRef:
        name: postgresql
    outputs:
      - name: password
        fromSecret:
          namespace: database
          name: database-credentials
          key: password
      - name: serviceip
        fromResource:
          apiVersion: v1
          kind: Service
          namespace: database
          name: postgresql
          # Select one scalar field with kubectl JSONPath syntax.
          jsonPath: "{.spec.clusterIP}"
  - name: api
    dependsOn:
      - database
    app:
      templateRef:
        name: example-api
      parameters:
        databasePassword: "{{ .Outputs.database.password }}"
        databaseAddress: "{{ .Outputs.database.serviceip }}"
publishedOutputs:
  # Expose the service address without exposing the database password.
  - name: databaseAddress
    fromTask:
      task: database
      output: serviceip
```

A `jsonPath` must use kubectl JSONPath template syntax, wrapped in braces, such as `{.metadata.name}`, and must select one scalar value.

Output names and the names of tasks that declare outputs can contain only lowercase letters and digits. Other task names can also contain hyphens. Resource outputs can't read cluster-scoped resources, and `fromResource` rejects `kind: Secret` outright. Read a Secret value with `fromSecret`, which also keeps it flagged as sensitive. The source namespace must be a namespace this Stack has already deployed an App or Argo CD Application into. vCluster Platform rejects a resource output whose source is in any other namespace before it reads the resource, even if the controller could otherwise reach it.

Output references support template functions and pipelines. For example, `{{ .Outputs.database.password | quote }}` is valid. Keep the reference in the canonical `.Outputs.<task>.<output>` form. An output reference can't control an `if`, `range`, or `with` action, declare a variable, or share one action with a `.Values` reference because parameters and outputs are rendered at different times. Parameter-driven control flow can contain output references in its body:

```yaml
endpoint: '{{ if .Values.tls }}https://{{ .Outputs.api.hostname }}{{ else }}http://{{ .Outputs.api.hostname }}{{ end }}'
```

The text `<%` is reserved for internal output rendering and isn't valid in a task payload.

### Capture and refresh outputs

A task captures its outputs after its child becomes healthy. Until capture finishes, the task stays `Progressing` with the reason `CapturingOutputs`, and dependent tasks keep waiting. A task captures all of its outputs or none of them. Capture has its own timeout, equal to the task timeout, which starts when capture begins.

The controller reads each output source as the StackInstance owner, not with the platform's own access. A task that declares outputs therefore needs an owner, like an App task does. If the owner no longer exists, has lost access to the destination, or can't read the source object, the task fails right away with the reason `OutputReadForbidden`. It doesn't wait for the capture timeout.

A healthy task doesn't read its sources again, so a later change to a source value isn't picked up on its own. A task captures again in these cases:

- It becomes healthy again after leaving the `Healthy` phase, for example when its child redeploys or recovers.
- You retry the task. See [Retry a stack](../troubleshoot/stacks.mdx#retry-a-stack).
- The output's declared source changes, or the stored value is dropped.

When a captured value changes, the tasks that read it render again and redeploy.

The platform stores captured values in a Secret named `stack-outputs-<stackinstance-name>` in the project namespace. Each value can hold at most 64 KiB, and all values together must fit in that one Secret. A captured value that contains `{{` is refused.

### Publish outputs

Published outputs are available through the StackInstance outputs subresource. They aren't written to `status`. See the [StackInstanceOutputs reference](../../api/resources/stackinstanceoutputs.mdx) for the response schema.

Reading any published output requires `get` on the `stackinstances/outputs` subresource. The response marks values captured with `fromSecret` as `sensitive`, but the same permission returns them. There's no separate permission for sensitive values. Task status messages replace output values with `[redacted]`, and withhold an error that could quote a secret output or a password parameter. See [Stack permissions](../users-permissions/permissions/stacks.mdx).

The `stackinstances/outputs` permission doesn't guard every copy of a value. When a task consumes another task's output, the platform writes the value as plain text into the AppInstance or ArgoCDApplication it generates. That child copies the StackInstance's `spec.access`, so anyone with that access can read the value on the child. Pass a value captured with `fromSecret` to another task only when everyone with the StackInstance's access may read it.

## Test a stack template

Create a StackInstance that references the template. A destination and, once set, an owner are both immutable after creation. A `virtualCluster` destination must be a cluster in the same project as the StackInstance. A `cluster` destination must be a control plane cluster in the project's allowed clusters. There's no cross-project form of this field, so deploying the same Stack into clusters across several projects takes one StackInstance per project, all referencing the same template.

The project's [allowed templates](../projects/allowed/templates.mdx) must include the StackTemplate, or `*` for every StackTemplate. Otherwise the StackInstance is rejected with `template is not allowed in project <project>`. Both the caller and the owner also need access to the destination.

```yaml title="stack-instance.yaml"
apiVersion: management.loft.sh/v1
kind: StackInstance
metadata:
  name: example-platform
  namespace: p-example
spec:
  displayName: Example application platform
  # App tasks deploy as this user or team, so an owner is required.
  owner:
    user: admin
  destination:
    virtualCluster:
      name: development
  templateRef:
    name: example-platform
  parameters:
    databaseStorage: 20Gi
  defaults:
    # Apply this timeout to tasks that don't set their own timeout.
    taskTimeout: 15m
  # Delete children removed from the resolved task graph.
  prunePolicy: Prune
```

```bash
kubectl apply -f stack-instance.yaml
kubectl get stackinstance example-platform -n p-example
```

The default `prunePolicy` is `Retain`. If a task is removed from the template, its existing child remains and appears in `status.orphanedApplications`. Retained children are still owned by the StackInstance, so deleting the StackInstance deletes them too. Set `Prune` to delete removed children in reverse dependency order.

A task's timeout counts only the time the task spends `Progressing`. A task that's `Waiting` or `Blocked` never times out. While a task is progressing, `status.tasks[].timeoutAt` shows when it will time out. A task that times out stays `Failed` until its child becomes ready or fails, or until you retry it.

On every reconciliation, the controller reapplies the fields it manages on each child. Manual edits to those fields revert, so change the StackTemplate or StackInstance instead.

:::warning
A referenced StackTemplate is resolved during every reconciliation. Stack templates don't have Stack revisions. Review template changes before applying them, to avoid an unwanted rollout to existing StackInstances.
:::
