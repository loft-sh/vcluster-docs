Effective access is the intersection of three layers, so start by working out
which one is denying.

| Layer | Symptom | Where to go |
|-------|---------|-------------|
| Tenant boundary | A whole kind is missing, or specific instances are | This page |
| Project boundary | The tenant can reach it but a project member can't | [allowed node types](../projects/allowed/node-types.mdx), [clusters](../projects/allowed/clusters.mdx), [templates](../projects/allowed/templates.mdx) |
| Quotas and admission | The object is visible but creating it is refused | [Troubleshoot quota denials](./quota-admission.mdx) |

The rest of this page covers the tenant boundary. It assumes platform admin
access, since a tenant can't read tenants.

Start with the resolved boundary report. The tenant controller writes it to the
tenant's status, one entry per resource.

```bash
kubectl get tenant acme -o jsonpath='{.status.boundary}' | jq
```

Each entry reports whether the tenant can create its own instances, what happens
to the platform's instances that no selector matches, and which selectors are in
effect. Selector changes don't wait for this report to update. The derived node
provider grant is the exception and changes when the tenant controller
reconciles it. See the [boundary reference](../manage-tenants/tenant-boundary-reference.mdx)
for what each field means.

## A Tenant can't see something you granted

Work down this table. The first two causes account for most reports.

| Symptom | Cause | Fix |
|---------|-------|-----|
| Capability is on, nothing visible | No `allow` is set, or its selectors match nothing | Add an `allow`, or widen the selector |
| Some instances visible, others not | The missing instances don't carry the label your selector requires | Label them, or grant by name where the capability supports it |
| Nothing of that kind is visible, not even the tenant's own instances or ones you assigned | The capability is absent or `enabled: false`, which withholds the whole resource | Set `enabled: true` |
| A whole resource is missing, and no capability covers it | The shipped default hides the platform's instances of that kind | Assign an instance to the tenant, or share it with every tenant. Projects, users, and teams can't be shared. See [ownership labels](../manage-tenants/tenant-boundary-reference.mdx#ownership-labels) |

Two rules cause most of the confusion.

**Enabling a capability grants nothing on its own.** `enabled: true` with no
`allow` means the capability is available and no instance is selected, so the
tenant sees an empty list rather than an error.

**Label selectors match all specified pairs.** With a non-empty selector, an
instance has to carry every pair. An empty selector matches every admin-owned
instance, including those without labels. Check the labels on the instance, not
just the selector on the tenant.

```bash
kubectl get osimage ubuntu-2404 -o jsonpath='{.metadata.labels}' | jq
```

## A Tenant can see a node provider you didn't grant

This is expected. Granting a node type makes the node provider that node type
belongs to reachable, because the grant would be unusable otherwise.

It appears in the tenant's status boundary as a derived grant rather than as
something you wrote.

```bash
kubectl get tenant acme -o jsonpath='{.status.boundary}' \
  | jq '.[] | select(.resource == "nodeproviders")'
```

Derived grants are recalculated, so revoking the node type removes the provider
when the tenant controller reconciles it. Don't edit `derived` by hand. The
request path reads it, and the controller overwrites manual changes during its
next reconciliation.

## A write is refused

### Name must start with the Tenant prefix

```text
SSHKey.management.loft.sh "build" is invalid: metadata.name: Invalid value:
"build": must start with "acme--": this kind is cluster-scoped, so its name is
shared with every tenant on the platform
```

Tenant-owned cluster-scoped resources are named `<tenant>--<name>`, including
when a platform admin creates them. The error names
the exact prefix required. Namespace-scoped resources and platform-owned
inventory granted or assigned to tenants aren't affected.

### A resource's tenant can't be changed

```text
projects.management.loft.sh is forbidden: a resource's tenant cannot be changed
(this resource belongs to the platform, and the write assigns it to tenant
"acme"); delete and recreate the resource instead
```

The write added, changed, or removed the `tenant.vcluster.com/owner` label on a
resource that already exists. Ownership is set at creation and never moves, for
platform admins too. Revert the label, and recreate the resource under the
tenant instead. A GitOps sync that adds the label to an existing manifest fails
this way. See
[Move existing resources into tenants](../manage-tenants/move-existing-resources.mdx).

### A GitOps service account's write is forbidden

```text
projects.management.loft.sh "acme--team-a" is forbidden: User
"system:serviceaccount:argocd:argocd-application-controller" cannot update
resource "projects" in API group "management.loft.sh" at the cluster scope
```

A Kubernetes service account can update a tenant's existing cluster-scoped
resources through the management API when RBAC allows it. It doesn't need a
Platform access key for that. Check the resource, API group, and verb named in
the refusal against the service account's RBAC permissions.

Once RBAC allows the request, Platform validates the write within the resource
owner's tenant limits. Check that the tenant can own the resource kind and use
its references. Ownership can't change on an update.

A service account can't create a tenant-owned cluster-scoped resource. Platform
refuses the owner label from it, and refuses a `<tenant>--` name without that
label. Create the resource with a platform admin's access key instead. See
[Choose the identity](../manage-tenants/move-existing-resources.mdx#choose-the-identity).

### A label is maintained by the platform

```text
label "tenant.vcluster.com/owner" is maintained by the platform and cannot be set
```

A patch that tries to modify a managed label can also report this refusal,
depending on the patch type.

```text
the patch would modify a label the platform maintains
```

A tenant identity sent a `tenant.vcluster.com/` label. Platform sets the owner
label on a tenant's resources itself, and a tenant can't set the others. Remove
the label from the request or the manifest.

A Kubernetes identity, such as a GitOps service account, gets the same refusal
when it sends the owner label on a create. Create the resource with a platform
admin's access key instead. Kubernetes identities and platform admins can repeat
an existing owner label unchanged on updates and patches. They still can't
change which tenant owns the resource.

### A username, email, or subject is unavailable

A tenant that creates or updates a user with a username, email, or identity
subject already in use elsewhere on the platform gets a `422` error. The detail reads
`value is unavailable`. Platform doesn't say who holds the value, because one
tenant isn't entitled to know about another's users. Choose a different value.

### A role can't be bound

```text
clusterroletemplates.management.loft.sh "loft-cluster-admin" is forbidden: role
is not a management role template
```

Inside a tenant, a user or team can only receive a cluster role template that's
marked as a management role. A role that isn't one, such as
`loft-cluster-admin`, would grant rights outside the tenant boundary. The same
refusal applies when a platform admin edits a tenant's user or team. Choose a
management role instead. See
[Roles inside a tenant](../concepts/what-are-users-and-teams.mdx#roles-inside-a-tenant).

`role is not an existing management role template` means the named template
doesn't exist. Check the spelling.

### A connector isn't usable

A cluster that names a connector the tenant can't use is refused with this
message.

```text
does not name a usable connector
```

An OS image that names an image store connector the tenant can't use is refused
with this message.

```text
does not name a usable image store
```

The connector might not exist, might be the wrong type, or might not be granted
to the tenant. The error is the same in each case, so it doesn't reveal which
connectors exist. Grant the connector through the tenant's `connectors`
capability, or name one the tenant already has.

Platform checks a cluster's connector again after the write. A cluster that
hasn't finished setting up its database reports the `DBConnectorSynced`
condition as `False` with the reason `ConnectorUnusable`. A cluster that already
set up its database keeps it.

### A network environment can't be created

```text
tenant "acme" may not own instances of this resource
```

A tenant can't own a network environment, so Platform refuses one created by
the tenant, or by a platform admin with the tenant as owner. A platform admin
creates it as a platform resource and assigns it to the tenant with
`tenant.vcluster.com/exclusive-to` at creation.

### An assignment is refused

```text
tenant "acme" has this resource switched off, so it would never be served the
assignment; enable the capability first
```

You assigned a resource to a tenant with the `tenant.vcluster.com/exclusive-to` label
while the governing capability is switched off for that tenant. Enable the
capability first, then assign.

Projects, users, and teams can't be assigned at all. Trying returns a refusal
like this one.

```text
projects cannot be assigned to a tenant with tenant.vcluster.com/exclusive-to
```

### A hostname is already claimed

```text
hostname is already claimed by another Tenant
```

Each hostname resolves to one tenant. The error doesn't say which tenant holds
it, because one tenant isn't entitled to know about another. As a platform admin
you can find it:

```bash
kubectl get tenants -o json \
  | jq -r '.items[] | select(.status.hostnames[]?.hostname == "acme.example.com") | .metadata.name'
```

The check is best effort. Two writes claiming the same hostname seconds apart
can both be accepted. Requests on a hostname held by more than one tenant then
return `404`. If a tenant's hostname returns `404`, run the query above and
remove the duplicate claim.

## A tenant user doesn't get a team's roles

Team membership only counts inside the user's own tenant. A platform team can
list a tenant user, and Platform accepts the write, but that user never gets the
team's roles. Add the user to a team in their own tenant instead.

## A tenant user can't reach a cluster they can see

A tenant user can see a control plane cluster granted to their tenant, but a
`kubectl` request through Platform returns `403` with
`no cluster access: access denied`.

Seeing a cluster doesn't grant access into it. The user also needs a cluster
access that lists the cluster and names them, one of their teams, or all users.
Tenants can't create cluster accesses, so a platform admin has to create it.
The admin must also assign the cluster access by setting
`tenant.vcluster.com/exclusive-to` to the tenant name. Alternatively, share it
with every tenant by setting `tenant.vcluster.com/all` to `"true"`.
These labels go on the `ClusterAccess` object's `metadata.labels`.
An unlabeled platform-owned access doesn't reach tenant users, even when it names them.
See [Cluster access and tenants](../users-permissions/permissions/cluster.mdx#cluster-access-and-tenants).

## NICo onboarding doesn't finish

Platform onboards a tenant to NICo once it has a NICo node type granted or a
NICo network environment assigned. Check the tenant's conditions.

```bash
kubectl get tenant acme -o jsonpath='{.status.conditions}' \
  | jq '.[] | select(.type | startswith("NICo"))'
```

| Condition is `False` | Cause | Fix |
|----------------------|-------|-----|
| `NICoNodeProviderFound` | A referenced node provider is missing or isn't a NICo provider, or the tenant's grants point at more than one | Grant node types and assign network environments from a single NICo node provider |
| `NICoSiteCredentialsAvailable` | Platform couldn't load the tenant's credentials for the NICo endpoint | Check the node provider's NICo endpoint configuration |
| `NICoOnboarded` | The NICo org, which is the tenant name, isn't ready yet or failed to be created | Read the condition's reason and message |

## A Tenant can't be created

### License limits

```text
cannot create tenant, because tenant license limit of 10 would be exceeded
```

```text
cannot create tenant, because its bootstrap admin user would exceed the user
license limit of 50
```

Two separate limits apply. Creating a tenant always creates its admin user, so
the user limit is checked as well as the tenant limit.

Both are checked on create only, so reaching either limit still leaves the
tenants you have editable and deletable.

### The Multi-Tenancy feature isn't licensed

Creating or changing a tenant needs the Multi-Tenancy feature. Click
<NavStep>Platform > Platform Config</NavStep> and check the
<Label>License and Billing</Label> tab.

### The name is rejected

A tenant name is a DNS label, capped at 32 characters, and can't contain `--`.
A `generateName` prefix is capped at 27 characters to leave room for the
generated suffix. See
[name rules](../manage-tenants/tenant-boundary-reference.mdx#tenant-names).

A name that matches the NICo org of an existing NICo node provider is refused
as reserved for platform workloads. Choose another name.

## A Tenant is stuck deleting

A tenant that's already being deleted can still have its finalizers removed
without the Multi-Tenancy feature, so a lapsed license can't strand it. That
exemption covers metadata-only updates. A change to the tenant's spec is still
refused, even during deletion.

Once deletion starts, the platform management API refuses requests from the
tenant's users with `403` and a message like this one. The same applies to
users whose tenant no longer exists.

```text
user "acme--jane" is labeled for tenant "acme", which cannot be resolved:
tenant is terminating
```

The reason reads `no such tenant` when the tenant is gone.

The agent proxy caches allowed cluster access decisions for 15 seconds.
Requests with a cached allowance can continue until it expires. See
[Cluster access and tenants](../users-permissions/permissions/cluster.mdx#cluster-access-and-tenants).

## A tenant admin can't do something they should

A tenant admin holds full rights inside the boundary, so a refusal usually means
the action reaches outside it rather than that a role is missing.

The quickest check is to look at the platform as they do. Click
<NavStep>Platform > Tenants</NavStep>, open the tenant's row menu, and click
<Button>Impersonate</Button>. Choose the tenant's admin user in the
<Label>Switch to Tenant</Label> dialog. A banner shows while you're impersonating. Impersonation needs
the management admin role or the `Impersonator` management role. See
[Impersonate a user](../users-permissions/managing-users/impersonate.mdx).

Things that are outside the boundary by design, whatever the role:

- Registering a control plane cluster
- Creating templates or stacks
- Creating connectors
- Creating network environments
- Creating cluster accesses
- Seeing or editing any other tenant

See [current limitations](../manage-tenants/overview.mdx#current-limitations).
