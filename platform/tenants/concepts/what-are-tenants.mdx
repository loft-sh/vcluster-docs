A tenant is a customer organization. It's the boundary that separates one
customer from another inside vCluster Platform, and it sits above projects.

For an AI cloud operator, a tenant is the customer account. For an internal
platform, it's the business unit or the subsidiary. Everything that customer
can see, provision, and configure is decided by their tenant.

:::info Tenant, not cluster
A tenant is an organization. A cluster is the Kubernetes environment a project
user creates. They're different things, and a tenant contains many clusters.
:::

## Tenants in the hierarchy

Platform hands responsibility down a chain. Each role delegates a narrower
boundary to the next.

| Step | Who | What they do |
|------|-----|--------------|
| 1 | System admin | Installs Platform onto a Kubernetes cluster. That cluster becomes the control plane cluster. |
| 2 | Platform admin | Creates tenants and grants each one the inventory it may consume. |
| 3 | Tenant admin | Divides that boundary across one or more projects. |
| 4 | Project user | Creates clusters inside a project. |

A platform admin never hands a customer raw infrastructure. They grant a tenant
a slice of what the platform already has, and the tenant admin decides how to
split that slice across their own teams.

## Tenants are optional

A platform with no tenants behaves exactly as it did before tenants existed.
Projects remain the organizing unit, and project permissions still scope project
admins and members. Platform admins aren't constrained by a tenant boundary.

Create tenants when more than one organization shares your platform and those
organizations shouldn't see each other. If you're running a single internal
platform where every admin is trusted with the whole inventory, projects alone
are enough.

## The Tenant boundary

Every tenant starts with no grants to platform inventory. A platform admin has
to say what the tenant may reach. This matters for upgrades too. A capability
added in a later release can't silently widen what an existing tenant is
allowed to reach.

The boundary is built from capabilities. Each one covers a class of platform
resource and answers two questions. Is this capability available at all? Which
instances of it may the tenant use? The boundary reference answers the same pair
per resource, as whether the tenant can author its own and what happens to the
platform's.

| Capability | What it governs |
|------------|-----------------|
| [Control plane clusters](./what-are-clusters.mdx) | Which clusters the tenant can place workloads on |
| [Node types](../vmetal/concepts/machine-types-and-nodetypes.mdx) | Which node types the tenant can provision from, and how much NICo capacity is reserved for it |
| [OS images](../vmetal/images/os-images.mdx) | Which images the tenant can boot machines from |
| [SSH keys](../vmetal/images/ssh-keys.mdx) | Whether the tenant can register keys for machine access |
| [Templates](./what-are-templates.mdx) | Which templates the tenant can instantiate |

[Read the full boundary reference →](../administer/tenants/tenant-boundary-reference.mdx)

Alongside capabilities, a platform admin can assign individual resources to one
tenant exclusively. A physical machine or a network environment is handed to a
single tenant this way, rather than being selected from a shared pool.

## What a Tenant comes with

Creating a tenant also creates two things, so the customer has somewhere to
start.

- **An admin identity**, named `<tenant>--admin`. This is the tenant admin, and
  it holds full administrative rights inside the tenant boundary.
- **A default project**, named `<tenant>--default`.

Both carry the tenant's name as a prefix. Cluster-scoped resources are shared
across the whole platform, so a tenant's resources live under their own
prefixed names and can't collide with another tenant's.

## Effective access

A user's real permissions are the intersection of three things.

1. **Their role.** Ordinary Kubernetes RBAC, unchanged.
2. **The tenant boundary.** What the platform admin granted the tenant.
3. **The project boundary.** What the tenant admin allowed in that project.

Narrowing any one of them narrows the result. A tenant admin holds broad rights,
but those rights stop at the edge of their tenant. They can't widen their own
boundary, because only a platform admin writes it.

The tenant boundary applies only to identities that belong to a tenant. A
platform admin belongs to none, so a platform admin session, and any automation
that uses its credentials, isn't narrowed by any tenant. To keep automation
inside one customer's boundary, have it act as a user in that customer's
tenant.

## Tenant isolation across the stack

Tenant isolation depends on controls at more than one layer.

The tenant boundary described on this page separates inventory, identities, and
configuration in the management plane.

Running workloads need their own isolation mechanisms.
[Private nodes](/docs/vcluster/deploy/worker-nodes/private-nodes/),
[vNode](https://www.vnode.com/docs/), and
[network policy](/docs/vcluster/configure/vcluster-yaml/policies/network-policy)
operate in and around the clusters a project user creates.

These controls are independent. A narrow tenant boundary doesn't isolate
workloads at runtime. Private nodes don't stop a platform admin from
over-granting inventory to a tenant.

## Per-tenant configuration

A tenant carries configuration of its own, separate from the platform's.

- **Hostnames** route requests to the tenant. A request arriving on a tenant's
  hostname resolves to that tenant before anyone signs in. Only a platform admin
  sets these.
- **UI customization** brands the tenant's view of Platform. A platform admin can
  set this, and can delegate it so the tenant admin sets it themselves.
