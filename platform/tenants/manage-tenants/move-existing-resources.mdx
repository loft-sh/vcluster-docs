Upgrading to Platform 5.0 doesn't move anything into a tenant. Everything you
created before the upgrade still belongs to the platform and keeps working the
way it did. This page covers what to change when you start giving some of it to
tenants. For background on the model, see
[What are tenants](../concepts/what-are-tenants.mdx).

## Before you begin

- Confirm the **Multi-Tenancy** feature is active in your license. See
  [Tenants overview](./overview.mdx).
- Decide which tenants you need and create them. See
  [Create and configure a tenant](./create-and-configure-tenants.mdx).
- Plan for downtime on any cluster you move. Clusters can't change tenant in
  place, so each one is recreated. Users and teams are recreated too, and lose
  their access keys. See [Decide what to move](#decide-what-to-move).
- If Argo CD or Flux manages these resources, read
  [Rename without deleting](#rename-without-deleting) before you change the
  repository.

## What the upgrade changes

**Existing resources stay with the platform.** A resource without the
`tenant.vcluster.com/owner` label belongs to the platform. Nothing written before
5.0 carries that label, so no migration runs and none is needed. Platform admins
see and manage everything as before.

**Tenant objects from 4.12 start with nothing granted.** Platform 4.12 accepted
Tenant objects, but enforced none of their fields. In 5.0, a capability that's
absent withholds its whole kind. An upgraded Tenant therefore grants no platform
inventory until you set its capabilities. Kinds no capability governs, such as
projects, follow the shipped defaults.

**Tenant users can't import externally deployed clusters until you allow it.**
`spec.externalClusters.enabled` is off for every Tenant, including upgraded
ones. Clusters already imported keep working, but a tenant user's new import is
refused. If you move projects whose users import clusters deployed with
vCluster Standalone, Helm, Argo CD, or Terraform, turn the setting on for that
tenant. See
[Allow importing externally deployed clusters](./create-and-configure-tenants.mdx#allow-importing-externally-deployed-clusters).

**Three Tenant fields are gone.** `spec.resourceAllowances`,
`spec.resourceQuotas`, and `spec.hostnames` were removed, and no conversion
carries their values over. Re-create what you need with the 5.0 fields before
anyone relies on the tenant.

Platform creates the tenant admin user, the admin team, and the default project
for each existing Tenant, the same as for a new one. If an object with one of
those names already exists, Platform leaves it alone, and it stays
platform-owned. Check that each existing Tenant name meets the
[5.0 name rules](./tenant-boundary-reference.mdx#tenant-names).

## Replace `resourceAllowances`

Skip this section if you didn't create Tenant objects on 4.12.

In 4.12, `resourceAllowances` listed each resource kind with a visibility scope
for platform-owned instances. Platform 5.0 replaces the list with one field per
capability, and moves per-instance assignments onto the instances as labels.

| 4.12 | 5.0 |
|------|-----|
| An entry for `clusters`, `nodetypes`, `osimages`, `sshkeys`, or a template kind | The matching capability field: `controlPlaneClusters`, `nodeTypes`, `osImages`, `sshKeys`, or `templates` |
| `tenant.enabled`, for the tenant's own instances | `allow.custom.enabled` on `sshKeys` or `osImages`. Tenants can't author the other kinds |
| `admin.scope: shared` | `allow.byLabels: {}`, which matches every platform-owned instance not assigned to another tenant. SSH keys have no equivalent |
| `admin.scope: hidden` | `enabled: true` with no `allow`, so the tenant sees only the platform's instances assigned to it with `exclusive-to` or shared with `all` |
| `admin.scope: rbac` | Same as `hidden`. Leave `allow` unset |
| An exception with `scope: shared` | Label the instances and select them with `allow.byLabels`. Control plane clusters, node types, OS images, and connectors also accept `allow.byName`, but not together with a non-empty `byLabels` |
| An exception with `scope: hidden` on a `shared` baseline | No equivalent, because a grant can't exclude instances. Select the instances to share with labels or names instead |
| An exception with `scope: exclusive` | The `exclusive-to` [ownership label](./tenant-boundary-reference.mdx#ownership-labels) on the instance |
| An entry for any other kind, such as `projects` | No equivalent. Those kinds follow the [shipped defaults](./tenant-boundary-reference.mdx#shipped-defaults) |
| `spec.resourceQuotas` | `nodeTypes.quota.byType`. Node types are the only capability with a tenant quota |
| `spec.hostnames` | The tenant configuration. See [Hostnames](./create-and-configure-tenants.mdx#hostnames) |

In 5.0, every capability needs `enabled: true` before the tenant sees
anything of that kind. Absent means disabled.

Templates now span every template kind with one label selector. Grants select
templates by label, without a kind or name selector. Give every template you
want to grant the same label, whatever its kind.

The 4.12 example shares every control plane cluster and one template, assigns
one node type to the tenant, and sets a quota. These fields had no runtime
effect in 4.12. The 5.0 example enables and enforces the corresponding grants
and quota. The `byType` quota caps on-demand node claims only. Claims on
machines the tenant owns or holds with `exclusive-to` don't count against it.

Customize the tenant, template, node type, and project suffix for the examples
and commands on this page.

## Decide what to move

How a resource reaches a tenant depends on its kind. Inventory the platform
shares can be granted in place. Ownership is set when a resource is created and
can't change afterward, so anything the tenant must own has to be recreated.

| Resource | How it reaches a tenant | Recreate? |
|----------|-------------------------|-----------|
| Control plane clusters, templates, node types, OS images, connectors | Grant through the capability, assign with `exclusive-to`, or share with the `all` [ownership label](./tenant-boundary-reference.mdx#ownership-labels) | No |
| Machines | Assign with `exclusive-to` while no node claim holds the machine. See [Assign dedicated resources](./create-and-configure-tenants.mdx#assign-dedicated-resources) | No |
| Network environments | Recreate with `exclusive-to` set at creation. An existing environment's assignment can't be added later | Yes |
| SSH keys | The tenant creates its own. The capability can't grant platform SSH keys | Yes |
| Projects | The tenant owns them | Yes |
| Clusters, spaces, and everything else inside a project | They belong to their project's tenant | Yes, with the project |
| Users and teams | The owner label, set at creation, decides a user's tenant | Yes |

Adding the owner label to an existing resource is refused. So is removing or
changing it.

```text
projects.management.loft.sh is forbidden: a resource's tenant cannot be changed
(this resource belongs to the platform, and the write assigns it to tenant
"acme"); delete and recreate the resource instead
```

Moving a cluster from a platform project into a tenant's project is refused too.
The cluster move endpoint is deprecated, and it never crosses a tenant boundary.

### Recreate a project for a tenant

A tenant admin can create the project, or a platform admin can create it for
them. Automation that creates the project needs a Platform access key. A
Kubernetes service account can update the project afterward, but can't create
it. See [Choose the identity](#choose-the-identity).

<Flow id="recreate-project-for-tenant">
  <Step>
    Grant the tenant every template and control plane cluster the project's
    clusters reference. Writes inside a tenant's project are judged as that
    tenant's, whoever sends them, so a missing grant refuses the create.
  </Step>
  <Step>
    Create the project. As the tenant admin, name it `<tenant>--<name>`, for
    example `acme--team-a`, and Platform labels it for the tenant. As a platform
    admin, use the same name and set the owner label to the tenant name. The
    `<tenant>--` prefix is required for every tenant-owned cluster-scoped
    create, whoever sends it.
  </Step>
  <Step>
    Recreate the project's clusters in the new project.
  </Step>
  <Step>
    Redeploy the workloads onto the new clusters. This page doesn't cover moving
    workload data. Plan that separately for each cluster.
  </Step>
  <Step>
    Delete the old clusters and project once the new ones are serving.
  </Step>
</Flow>

### Recreate users and teams

A user's tenant is the owner label on the user, so an existing user can't join a
tenant. A new user takes its place. The same applies to teams. See
[Users and teams in a tenant](../concepts/what-are-users-and-teams.mdx).

A username, email, and identity subject must be unique across the whole
platform. If the new user keeps any of those identifiers, delete the old user
first. That person has no access until the new user exists. Otherwise, create
the new user, then delete the old one.

The new user starts with no access keys or project memberships. Issue new keys
and add the user to the tenant's projects.

## Update GitOps repositories

For each tenant, a repository that manages Platform resources through Argo CD or
Flux needs two decisions. Choose the identity that applies the manifests, then
the labels and names the manifests carry.

### Choose the identity

The identity your GitOps tool uses needs permission to write each resource.
For tenant-owned resources, Platform also checks the owning tenant's limits.

| Identity | Platform-owned resources | A tenant's resources |
|----------|--------------------------|----------------------|
| The tool's Kubernetes service account, or another control plane cluster identity | With the required RBAC permissions on the management API | Updates to existing cluster-scoped resources, and writes inside a tenant's project, with the required RBAC permissions. Not creates of cluster-scoped resources, such as projects |
| A platform admin user's [access key](../../administer/authentication/access-keys.mdx) | Within that user's permissions | Creates and updates. Writes are held to what the tenant may do |
| A tenant user's access key | No | Within that tenant and the user's permissions |

The [GitOps end-to-end guide](../../integrations/gitops-cicd/gitops-end-to-end.mdx)
uses the first identity. A Kubernetes identity isn't a Platform user, but it
doesn't need one to update a tenant's existing projects, users, or teams. Its
RBAC permissions still apply. An update uses the stored resource's owner, and
a write inside a project uses that project's tenant.

A Kubernetes identity can't create a tenant-owned cluster-scoped resource.
Platform refuses the owner label from it, and refuses a `<tenant>--` name
without that label. Create a tenant's projects, users, and teams with an
access key, then let the service account manage them.

These writes can't exceed the tenant's grants or bypass restrictions on roles
and resource kinds. A sync identity with access to several tenants is held to
each resource's owning tenant, rather than to one tenant selected for the sync.

If you choose a Platform access key, create a dedicated user for the tool, as
[Users and teams](../concepts/what-are-users-and-teams.mdx) recommends. A sync
that creates resources for several tenants needs a platform admin user. A
tenant user's key confines the sync to that tenant. Keep platform-owned
manifests in a separate sync with a platform identity.

Build the access-key kubeconfig as described in
[Manually create kube config](../../administer/authentication/access-keys.mdx#manually-create-kube-config),
then register it as an Argo CD cluster, or reference it from a Flux
Kustomization as a kubeconfig Secret.

### Rename without deleting

Changing a resource's `metadata.name` or namespace creates a different object.
Renaming only the manifest file keeps the same object. If the old project is
absent from the rendered manifests, pruning deletes it and everything in it,
including its clusters.

Before committing resource name or namespace changes, choose one approach.

- Disable pruning and confirm the change has taken effect in the controller.
  Keep pruning disabled until workload and data cutover is verified and the old
  resources are ready for deletion. See
  [Argo CD pruning controls](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/#no-prune-resources)
  or [Flux pruning controls](https://fluxcd.io/flux/components/kustomize/kustomizations/#prune).
- Keep the old manifests and add the new resources as separate manifests. Remove
  the old manifests only after workload and data cutover is verified.

Recreate the clusters and plan the workload and data cutover as described in
[Recreate a project for a tenant](#recreate-a-project-for-a-tenant).

### Change the manifests

What the manifests carry depends on the identity.

**With a platform admin's access key,** add `tenant.vcluster.com/owner` to each
cluster-scoped resource the tenant owns, such as its projects, users, and teams.
Add it only to resources that don't exist yet. Resources inside a tenant's
project take the tenant from the project, so they don't need the label.
Name each tenant-owned cluster-scoped resource `<tenant>--<name>`, including
when a platform admin creates it. A tenant-prefixed name without the matching
owner is also refused. Follow [Rename without deleting](#rename-without-deleting)
before changing names in Git.

<InterpolatedCodeBlock
  language="yaml"
  title="project.yaml"
  code={
    "apiVersion: management.loft.sh/v1\n" +
    "kind: Project\n" +
    "metadata:\n" +
    "  name: [[GLOBAL:TENANT]]--[[GLOBAL:PROJECT_SUFFIX]]\n" +
    "  labels:\n" +
    "    tenant.vcluster.com/owner: [[GLOBAL:TENANT]]\n" +
    "spec:\n" +
    "  displayName: Team A\n"
  }
/>

**With a tenant user's access key,** remove every `tenant.vcluster.com/` label
from the manifests. Platform sets the owner label itself and refuses one in a
tenant's write. Rename each cluster-scoped resource to start with
`<tenant>--`, following [Rename without deleting](#rename-without-deleting).
Platform hides these labels when the tenant reads, so the tool doesn't report
them as drift.

**With a Kubernetes identity,** keep the manifests of resources the tenant
already owns as they are. Platform admins and Kubernetes identities can repeat
an unchanged owner label when updating or patching an existing resource, but
they can't change its tenant. Tenant identities can't send managed labels, even
unchanged ones.

### What fails if a repository isn't updated

| Symptom in the sync | Cause | Fix |
|---------------------|-------|-----|
| `a resource's tenant cannot be changed` | The manifest added, changed, or removed the owner label on a resource that already exists | Revert the label. Recreate the resource under the tenant instead |
| RBAC `forbidden` for the service account | The sync identity lacks permission for the resource or operation on `management.loft.sh` | Grant the required RBAC permissions to the sync identity |
| `is maintained by the platform and cannot be set` or `the patch would modify a label the platform maintains` | A tenant identity sent a `tenant.vcluster.com/` label, or a Kubernetes identity sent the owner label on a create. The message depends on the patch type and the resulting labels | Remove the label from a tenant's manifest. Create the resource with a platform admin's access key instead of the Kubernetes identity |
| `owner tenant does not exist` | The owner label on a new resource names a tenant that doesn't exist, often a typo | Correct the label to the tenant's name |
| `must start with "acme--"` | A tenant-owned cluster-scoped create omitted the prefix, including one sent by a platform admin | Rename it with the prefix |
| `the object must be owned by it` | A tenant-prefixed name has no matching owner, for example a Kubernetes identity's create | Create the resource with a platform admin's access key and the matching owner, or use a name outside tenant name prefixes for platform-owned inventory |
| `may not own instances of this resource` | The tenant can't create that kind. Its capability is off, the capability doesn't allow the tenant its own, or tenants never author that kind | Create the resource as the platform, or enable `allow.custom` where the capability offers it |

## Verify

Check the tenant's view and the GitOps sync.

- **The tenant's view.** Sign in as the tenant admin, or
  [switch to the tenant](../concepts/what-are-users-and-teams.mdx#switch-to-a-tenant-by-impersonation).
  Confirm the moved projects and clusters are listed, and that the granted
  inventory appears where the clusters need it. See
  [Verify the boundary](./create-and-configure-tenants.mdx#verify-the-boundary).
- **The grants.** Read the tenant's resolved boundary to confirm each
  capability took effect. See
  [Read the resolved boundary](./tenant-boundary-reference.mdx#read-the-resolved-boundary).
- **The sync.** After cleanup, the Argo CD application reports Synced and Healthy,
  or the Flux Kustomization reports Ready. None of the errors above remain.
  During cutover, Argo CD can report OutOfSync because pruning is disabled and
  the old resources are still present. Confirm the pending deletions are only
  the resources you intend to retire.
- **The permissions.** Reapply an unchanged manifest, then sync an intended
  update with the tool's actual identity. Confirm ownership stays unchanged.
  In a test environment, confirm the same identity can't give one of the
  tenant's teams a role the tenant couldn't grant itself.
- **The ownership.** Use a platform admin's access-key kubeconfig to confirm the
  recreated project carries `tenant.vcluster.com/owner` with the tenant name.
  Tenant users' reads hide this label, so their keys can't verify it.

## Clean up

1. Verify the replacement clusters serve their workloads and that data cutover
   is complete. Confirm the replacement users and teams have the access they need.
2. Delete the old projects, clusters, users, and teams. For GitOps-managed
   resources, remove the old manifests.
3. If you disabled pruning, restore it only after confirming every pending
   deletion is intended.
4. Revoke access keys that belonged to deleted users, or that you issued only for
   the move.
