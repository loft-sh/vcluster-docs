[NVIDIA DSX OS](https://docs.nvidia.com/dsx) is a collection of modular software for operating AI infrastructure.
It covers infrastructure provisioning, accelerated Kubernetes, GPU health, observability, scheduling, and model serving.
vCluster Platform brings selected components into the workflows customer engineers use to build and operate an AI cloud.

## Choose an integration path

Start with the layer you need to operate. Each integration has its own prerequisites and deployment location.
Installing one component doesn't install the entire DSX OS collection.

| Your goal | Integration | Where it runs | Start here |
| --- | --- | --- | --- |
| Provision servers managed by NVIDIA Infra Controller (NICo) | The vMetal NICo driver connects Platform machine provisioning to a NICo site. | Platform controllers call your NICo installation. | [Infrastructure provisioning](#provision-infrastructure-with-nico) |
| Install an NVKE management plane from signed build artifacts | A Certified Stack consumes an NVIDIA Kubernetes Recipes (NVKR) release and installs NVIDIA Kubernetes Engine (NVKE) services. | Inside a cluster created by vCluster. | [Install the NVKE management plane](./cluster-workloads/certified-stacks/nvidia-nvke.mdx) |
| View existing NVKE-created clusters and deploy applications to them | Connect each Kubernetes cluster to Platform, then target it with Apps, Stacks, and observability collectors. | The Platform agent and selected applications run in the connected cluster. | [Manage connected NVKE clusters](./cluster-workloads/manage-nvke-clusters.mdx) |
| Collect GPU telemetry and detect node faults | Bundled GPU Operator, Fleet Intelligence Agent, and NVSentinel application templates. | In the cluster whose GPU nodes you observe. | [GPU observability templates](../fleet-operations/observability/gpu-observability-templates.mdx) |
| Deliver GPU scheduling or model serving | NVIDIA Run:ai and NVIDIA Dynamo application stacks. | In a cluster or on a connected control plane cluster, depending on the deployment model. | [AI workloads](#deliver-ai-workloads) |

## Understand build and deployment ownership

NVKR builds and publishes artifacts from pinned inputs. An operator supplies the release registry and signing configuration.
NVKE consumes those artifacts to run its management services and operate downstream Kubernetes clusters.

There are two independent ways to use NVKE with Platform:

1. **Host the management services.** Create a cluster with vCluster, then install the NVKE management-plane Stack into it.
   The Stack verifies the selected NVKR release before installing its services.
2. **Connect an existing cluster.** Let NVKE provision a workload cluster, then connect that Kubernetes cluster to Platform.
   Use Platform to view it and deploy applications or telemetry collectors into it.

The management-plane Stack installs services, including the NVKE controller, PostgreSQL, Temporal, SPIRE, and NVKE telemetry.
It doesn't install NICo, Cluster API, or the infrastructure configuration required to provision downstream nodes.
A healthy Stack confirms service installation. It doesn't prove that NVKE can provision a downstream cluster.

Connecting an existing NVKE-created cluster gives Platform an application deployment and visibility target.
NVKE retains ownership of that cluster's provisioning and lifecycle. Connection alone doesn't transfer upgrades, scaling, or node replacement to Platform.

For the initial management-plane evaluation, use private nodes. The shared-node variant omits the controller's SPIFFE identity and node-level telemetry.
Shared nodes are suitable for trusted tenants. Use private nodes for untrusted tenants with Kubernetes access or arbitrary workload execution.

## Provision infrastructure with NICo

[NICo](https://github.com/dsx-ai-factory/infra-controller) discovers and provisions bare metal and manages its infrastructure lifecycle.
The vMetal driver lets Platform use capacity from an existing NICo installation through its machine and node provisioning workflows.

Choose this path when you want Platform to allocate NICo-managed servers as instances or cluster nodes.
The direct vMetal driver and NVKE's Cluster API provider for NICo are separate provisioning paths.
Decide which system owns each allocation before configuring both against the same hardware inventory.

Start with [vMetal](../vmetal/overview.mdx) and [machine types and node types](../vmetal/concepts/machine-types-and-nodetypes.mdx).
The NICo-specific administrator and provisioning guides are still under review:
[NICo driver guide](https://github.com/loft-sh/vcluster-docs/pull/2821) and
[NICo provisioning task](https://github.com/loft-sh/vcluster-docs/pull/3020).

## Observe GPU health across clusters

Install the GPU components in the cluster that owns the GPU nodes.
The [GPU observability templates](../fleet-operations/observability/gpu-observability-templates.mdx) describe deployment order and dependencies.

Three names describe different parts of the telemetry system:

- **NVIDIA Fleet Intelligence Agent** collects node and GPU health information.
- **NVKE telemetry pipeline (NKTP)** is part of the NVKE management-plane installation.
- **Platform Fleet Observability** collects and queries telemetry across connected environments through configured collectors, gateways, and backends.

Installing an agent or connecting a cluster doesn't configure the entire Fleet Observability pipeline.
Follow the [Fleet Observability quickstart](../fleet-operations/observability/quickstart.mdx) to configure collection and storage.

The Platform v5.0.0-rc.1 NVSentinel template defaults to observation, with dry run enabled and quarantine, drain, and remediation disabled.
Enable actions deliberately after checking the provider and dependencies in
[Observe GPU nodes with NVSentinel](../fleet-operations/observability/nvsentinel-gpu-observability.mdx).
An upstream remediation component doesn't establish an automatic Platform workflow for replacing faulty GPU nodes through vMetal.

## Deliver AI workloads

Certified Stacks group applications with dependency ordering, health checks, and shared parameters.
A cluster template can include Stacks so an environment receives its applications during creation.

- [NVIDIA Run:ai](./cluster-workloads/certified-stacks/runai.mdx) provides GPU scheduling and workload management with dedicated or central deployment models.
- [NVIDIA Dynamo](https://github.com/ai-dynamo/dynamo) provides distributed model serving. Platform v5.0.0-rc.1 includes its Stack.
  The [Dynamo integration guide is under review](https://github.com/loft-sh/vcluster-docs/pull/2919).

Use [Certified Stacks](./cluster-workloads/certified-stacks/index.mdx) to understand the catalog and
[Use a Stack](../use-platform/apps/use-stacks.mdx) for installation options.
The presence of a Stack doesn't establish GPU capacity, model access, or a tested inference deployment in your environment.
